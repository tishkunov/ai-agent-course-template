# M1 — Бэкенд-фундамент

Приём обращений: HTTP-эндпоинт, PostgreSQL, миграции, Docker, аутентификация каналов и операторов, healthcheck. Это шаг S1 пайплайна (приём); корреляция треда — M3, извлечение полей — M2.

Стоит на: M0 (процесс работы с ИИ, промпт-контракты, `docs/decisions.md`). Сквозные правила сервиса — `../contracts.md`.

**Каркас модуля уже в репозитории.** Код всех одиннадцати пунктов написан (`app/`, `migrations/`, `tests/`, `docker/`, `Makefile`, `.env.example`). Работа M1 — поднять его, разобраться в поведении и закрыть расхождения, перечисленные в третьем столбце таблицы ниже. Наличие файла не равно сданному пункту: сдача идёт по сценариям `kriterii-priyomki.md`.

## Команды запуска

Перед первой сборкой выполни M1.1: `make lock` и сохрани `uv.lock` в репозитории студента.
Dockerfile копирует этот файл; готовность сборки нужно подтвердить, а не выводить из наличия
compose. После подготовки проверяется запуск с чистого клона уже доработанного проекта.

Compose лежит в `docker/`, и `build.context` в нём задан как `..`. Поэтому `docker compose up` из корня репозитория не работает — нужен путь к файлу или цель Makefile.

| Задача | Команда |
|---|---|
| Поднять весь стек | `make up` (= `docker compose -f docker/docker-compose.yml up --build`) |
| Остановить | `make down` |
| Приложение локально | `make migrate`, затем `make run`, если `DATABASE_URL` и `REDIS_URL` указывают на зависимости, доступные с хоста. Готовый compose не публикует порты БД и Redis на хост; `up postgres redis` сам по себе этот режим не обеспечивает. Основной путь — `make up`. |
| Тесты | `make test` (нужна отдельная БД; по умолчанию `postgresql+asyncpg://intake:intake@localhost:5432/intake_test`) |
| Гейты | `make lint`, `make typecheck` |

**Переменные окружения.** Два независимых пути: локальный запуск читает `.env` (через `Settings`), а compose подставляет значения, записанные прямо в `docker/docker-compose.yml` для локали.

| Переменная | Обязательность | Что писать в `.env` |
|---|---|---|
| `DATABASE_URL`, `REDIS_URL` | обязательна, дефолта нет | адрес окружения |
| `JWT_SECRET`, `API_KEYS` | обязательна, дефолта нет, секрет | только локальные значения; в git не попадает |
| `APP_ENV` (`local`), `JWT_TTL_MIN` (`60`), `LOG_LEVEL` (`INFO`), `DB_POOL_SIZE` (`5`), `DB_MAX_OVERFLOW` (`10`) | необязательна | либо валидное значение, либо **строки нет вовсе** |

Пустая строка (`LOG_LEVEL=`) — не «возьми значение по умолчанию», а невалидное значение: старт упадёт. Поэтому в `.env.example` необязательные переменные должны быть закомментированы, а не оставлены пустыми (доработка M1.1).

## Как проходить пункт (цикл M0.2)

1. Прочитать пункт в `zadanie.md` + его файл в `details/`.
2. Собрать промпт-контракт (раздел «Промпт-контракт к ИИ» в `details/`), передать ИИ.
3. Получить код или разбор существующего кода.
4. **Отдельным вызовом** ИИ в роли критика прогнать `detalnoe-review.md` по этому пункту.
5. Прогнать сценарии из `kriterii-priyomki.md`.
6. Своими словами записать в `docs/decisions.md`, что даёт пункт и что поймало ревью; ответить на вопросы пункта.
7. Отметить пункт закрытым.
