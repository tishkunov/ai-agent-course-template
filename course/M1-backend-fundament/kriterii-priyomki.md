# M1 — Бэкенд-фундамент · Критерии приёмки

> Задание — в `zadanie.md`. Здесь для каждой проверки указано: предусловия, вход, действие проверяющего, наблюдаемый результат, признак ошибки и что подменяется (мок, часы, конфиг). Формулировки вида «работает корректно» без сценария сдачу не закрывают.
>
> **Общие предусловия всех сценариев с БД.** Для ручного HTTP-прогона выполнен `make up` (сервис `migrate` применяет миграции). Для автотестов подготовлена отдельная доступная с хоста тестовая БД, схема применена миграциями; текущий compose порты PostgreSQL/Redis наружу не публикует. В локальном окружении заданы `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, `API_KEYS`. Сценарии, помеченные «автотест», студент реализует сам на своём коде — готовые тесты в `tests/` покрывают часть из них и являются образцом, а не сдачей.

## M1.7 — Приём обращения и повторы

Все сценарии — `POST /requests` с валидным `X-API-Key`; `N` — число строк в `requests` после сценария.

| # | Вход | Действие | Наблюдаемый результат | Признак ошибки |
|---|---|---|---|---|
| 7.1 **новый запрос** | `{"channel":"form","raw_text":"нужен сантехник на завтра утром","client_contact":"u@example.com"}` | один POST | 201; `status="new"`, `thread_key="form:u@example.com"`, `N=1` | 200 на первом запросе; `status` не `new` |
| 7.2 **повтор доставки** | то же тело с тем же `message_id` | POST дважды подряд | первый 201, второй 200 с тем же `id`; `N=1` | 201 дважды и `N=2`; или 409 |
| 7.3 **конкурентный повтор** | то же тело ×8 | `asyncio.gather` по 8 запросов | ровно один 201, остальные 200; все `id` одинаковы; `N=1`; ни одного 500 | 500 у проигравшего в гонке; `N>1` |
| 7.4 **другой заказ с тем же текстом** | тот же `raw_text` и контакт, **другой** `message_id` | два POST | оба 201, `id` разные, `N=2` | второй 200 — реальный повторный заказ потерян |
| 7.5 **тот же `message_id`, другой текст** | `message_id` совпадает, `raw_text` изменён | два POST | второй 200, тот же `id`, `N=1` (ключ — доставка, не текст) | 201 и `N=2` |
| 7.6 **граница календарного окна** | тело **без** `message_id`; часы приложения подменены на `23:59:30Z`, затем на `00:00:30Z` следующих суток | два POST | 201 и 201, `N=2` — поведение по календарному окну, а не по скользящим 24 часам; факт и его причина записаны в `docs/decisions.md` | сдача утверждает «TTL 24 часа», а наблюдается смена суток; или решение не записано |
| 7.7 **повтор через сутки** | то же тело без `message_id`, часы сдвинуты на +1 сутки | POST, затем POST | 201 и 201, `N=2` | сдача обещает дедуп «в окне суток» без оговорки о границе |

**Подменяется:** в 7.6 и 7.7 — источник времени в `build_idem_key` (подмена часов; календарная дата UTC). Больше ничего.

**Готово, когда.** Повтор доставки не создаёт второй записи даже при гонке; другой заказ с тем же текстом создаёт новую запись; граница суточного окна названа и записана в `docs/decisions.md`.

## Интеграционная приёмка M1

Один прогон, ручной, на поднятом стеке. Каждый шаг — наблюдаемый результат, а не «должно работать».

1. Чистый клон доработанного проекта (M1.1 завершён, lock-файл сохранён) → `make up` → `postgres` healthy, `migrate` успешно завершён, `app` healthy.
2. `GET /health` → 200, `status="ok"`.
3. `POST /requests` с валидным `X-API-Key` и `message_id` → **201**, `status="new"`.
4. Тот же запрос повторно → **200**, тот же `id`; в БД одна строка.
5. Тот же текст с другим `message_id` → **201**, новая строка (повторный заказ не съеден дедупом).
6. `GET /requests/{id}` с операторским токеном → 200; с токеном без полномочия → 403; без токена → 401.
7. `POST /requests` без `X-API-Key` → 401.
8. Остановить `redis` → `POST /requests` → 201, `/health` → `degraded`/200.
9. Остановить `postgres` → `/health` → `unhealthy`/503.
10. Поднять обратно, `restart` → созданные обращения на месте.

**Definition of Done M1.**

- Стек поднимается командой `make up` (или `docker compose -f docker/docker-compose.yml up`); миграции применяются с нуля отдельным шагом.
- Приём идемпотентен по доставке: повтор и конкурентный повтор дают одну запись, а другой заказ с тем же текстом — новую.
- Граница календарного окна запасного ключа названа и записана в `docs/decisions.md` (не выдаётся за скользящий TTL).
- Приём закрыт `X-API-Key`; операторская ручка проверяет подпись, срок **и** полномочие; матрица 8.1–8.8 зелёная.
- `anon`-тред не используется как основание объединять обращения; ограничение hash-дедупа для анонимов зафиксировано.
- Мягкая зависимость Redis выполняется и на старте (compose), и на ходу (`degraded`/200).
- `/health` различает критичную БД и некритичный Redis, ограничен по времени, liveness и readiness разведены.
- `make lint` и `make typecheck` чистые; секретов в git и в образе нет; lock-файл закоммичен.
- В записях понимания (`docs/decisions.md`, шаг 6 цикла M0.2) отвечены вопросы из `zadanie.md` по M1.7 и M1.8.

## Материалы сдачи и объяснение

Используй существующие артефакты M0: команда запуска с путём к compose, версия кода/конфига,
вывод рабочего приёма и повтора, вывод одного сбоя (отказ БД или отсутствие полномочия),
результат остальных обязательных сценариев. Не создавай отдельную папку отчётов на каждый пункт.
В записи понимания ответь на три вопроса:

1. Почему одинаковый текст с новым `message_id` создаёт новое обращение, а повтор доставки — нет?
2. Почему общий `form:anon` не доказывает, что два сообщения принадлежат одному человеку?
3. Почему наличие ORM-модели не заменяет проверку миграции на отдельной БД?

Демонстрация, значимый сбой и объяснение дополняют отдельное ревью и процесс M0, а не заменяют их.
