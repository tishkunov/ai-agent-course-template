# M1 — Бэкенд-фундамент · Задание

**Что строим.** Приём обращений: HTTP-эндпоинт, сохранение в PostgreSQL, миграции, контейнеры, аутентификация каналов и операторов, healthcheck. Это шаг S1 пайплайна (приём), остальная часть S1 — корреляция треда — появится в M3.

**Исходное состояние.** Каркас всех одиннадцати пунктов уже лежит в репозитории (`app/`, `migrations/`, `tests/`, `docker/`, `Makefile`, `.env.example`). M1 — не «напиши с нуля», а: **поднять, прочитать, объяснить, закрыть перечисленные ниже расхождения**. Что именно готово, что надо проверить и что доделать — таблица в `README.md` («Карта исходного состояния»). Наличие файла не означает, что пункт сдан: сдача — по `kriterii-priyomki.md`.

**Не входит.** LLM в M1 нет. Redis только подключается и пингуется — кеша, очередей и счётчиков нет (M8). Разбор форматов каналов (экспорты мессенджера, HTML-письма, фото, голосовые сообщения) в M1 не делается: приём принимает уже собранное JSON-тело, а нормализация вложений и OCR — шаг S2 (M5.2). Извлечение полей (услуга, адрес) — M2, склейка диалога — M3.

**Сквозные правила.** Статусы, идентификаторы, границы доверия и словарь значений — в [`../contracts.md`](../contracts.md). Формат этого файла задан там же в §1. При расхождении верен `contracts.md`.

## 0. Общие требования (действуют на все пункты M1)

**Слои и границы.** `api/` (роуты, зависимости, обработчики ошибок) → `services/` (доменная логика) → `db/` (сессии, репозитории) + `models/` (ORM), `schemas/` (pydantic DTO), `core/` (конфиг, безопасность, логи). Роут не ходит в БД напрямую. Схема запроса (`schemas/`) и таблица (`models/`) — разные объекты.

**Конфиг и секреты.** Только через `pydantic-settings` из окружения. Секретов в коде и в git нет; `.env` — в `.gitignore`. Отсутствие обязательной переменной → падение на старте с указанием, какой именно переменной не хватает. У секретов нет значений по умолчанию.

**Ошибки.** Один обработчик на приложение. Соответствие: валидация → 422, не найдено → 404, конфликт → 409, нет или негодный кредешл → 401, кредешл валиден, но полномочия не те → 403. Наружу — тело `{error, detail}` без стек-трейса. `except: pass` запрещён.

**Логи.** Структурные JSON с `request_id` из middleware. Секреты и контакты клиентов в открытом виде не логируются.

**Async.** Хендлеры и доступ к БД асинхронные; синхронных блокирующих вызовов внутри нет.

**Тесты.** pytest + `httpx.AsyncClient`, отдельная тестовая БД, схема применяется миграциями, изоляция между тестами. Внешних сетевых вызовов в M1 нет.

**Гейты.** `make lint` и `make typecheck` проходят до коммита.

**ID обращения.** `REQ-YYYY-NNNN` из последовательности `request_seq` — решение уже принято и зафиксировано в `contracts.md` §11. Заново не выбирается.

## M1.1 — Структура проекта и окружение

**Проблема.** Если конфиг читается из кода по месту (`os.environ[...]` в глубине), один и тот же образ нельзя запустить в тестах и в compose без правок, а секрет однажды попадает в git навсегда. Второй, менее очевидный сбой: сервис стартует с «полупустой» конфигурацией и падает через час на первом запросе.

**Что уже работает.** Дерево `app/{api,services,db,models,schemas,core}`, `app/core/config.py` с `Settings(BaseSettings)` и кешируемым `get_settings()`, `Makefile` с целями `run / test / lint / typecheck / migrate / lock / up / down`, `.env.example`, `pyproject.toml` (uv, Python ≥ 3.12).

**Что сделать.**
1. Прочитать `app/core/config.py` и перечислить: какие переменные обязательны (без дефолта) и какие имеют значение по умолчанию.
2. Проверить поведение на пустой строке. `.env.example` сейчас перечисляет **все** переменные со знаком `=` и пустым значением; при копировании его в `.env` без правок сервис не стартует: пустая строка — это не «возьми дефолт», а невалидное значение для `APP_ENV`, `JWT_TTL_MIN`, `LOG_LEVEL`, `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`.
3. **Доработка.** Привести `.env.example` к разделению: обязательные (`DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, `API_KEYS`) — строкой для заполнения; необязательные — закомментированы с указанием дефолта. Строку `LOG_LEVEL=` без значения оставлять нельзя.
4. **Доработка.** Сообщение об ошибке конфигурации сейчас называет только *отсутствующие* переменные; при невалидном значении выводится общий текст без имени поля. Дополнить так, чтобы в обоих случаях было видно имя переменной.
5. **Доработка.** Lock-файла в репозитории нет (`uv.lock` отсутствует). Сгенерировать `make lock` и закоммитить.

**Пример входа и результата.**

```
.env содержит DATABASE_URL, REDIS_URL, JWT_SECRET, API_KEYS; строки LOG_LEVEL нет
→ make run поднимается, get_settings().log_level == "INFO"

.env содержит LOG_LEVEL= (пустое значение)
→ старт падает; в сообщении названо поле LOG_LEVEL
```

**Контракт.** Имена полей `Settings` и дерево каталогов фиксируются здесь; в M2–M9 меняются только через запись в `docs/decisions.md`.

**Краевые случаи.** Обязательная переменная отсутствует → старт падает, имя названо. Лишняя переменная окружения игнорируется (`extra="ignore"`). У секрета нет дефолта.

**Пример входа и результата.** Конверт `data/course_pack/inputs/end_to_end.jsonl` — это **не** тело запроса. Преобразование:

| Поле конверта | Куда идёт | Почему |
|---|---|---|
| `input.channel` | `channel` | канал обращения |
| `input.text` | `raw_text` | текст без разбора |
| `input.client_contact` | `client_contact` | контакт канала, может быть null |
| `input.message_id` | `message_id` | идентификатор доставки канала |

Вход и ответ:

```http
POST /requests
X-API-Key: dev-key
{"channel": "email",
 "raw_text": "Добрый день, аврал! подтекает розетка в комнате... Звоните +7 311 952 63-59-84",
 "client_contact": "+7 311 952 63-59-84",

201 Created
{"id": "REQ-2026-0001", "status": "new", "created_at": "2026-02-01T09:55:00+00:00"}
```

Попытка отправить конверт набора целиком (с `case_id`, `family_id`, `split`, `input`) даёт `422` — это и есть смысл `extra="forbid"`: поля разметки физически не могут попасть в сервис.

**Контракт.**

**Краевые случаи.** Неизвестный `channel` → 422. `raw_text` из пробелов → 422. Длина > 20000 → 422. Лишнее поле → 422. Отсутствующий `client_contact` → запрос принимается (см. M1.8 про последствия для `thread_key`).

## M1.3 — Асинхронность

**Краевые случаи.** N одновременных приёмов сохраняются; ожидание I/O уступает управление. Размер пула БД может ограничивать параллельность и не доказывает блокировку loop.

## M1.7 — Приём обращения и повторы

**Проблема.** Каналы присылают одно и то же сообщение по несколько раз: вебхук повторил доставку после таймаута, пользователь нажал «отправить» дважды. Без защиты оператор разбирает одно обращение трижды. Обратная ошибка не менее вредна: если считать дублем всё похожее, второй реальный заказ того же человека исчезнет.

**Что уже работает.** `app/services/intake.py`: `thread_key`, `idem_key`, поиск по `idem_key`, создание со `status=new`, обработка `IntegrityError` при гонке. Роут возвращает 201/200. Unique-индекс `uq_requests_idem_key` в миграции 0001.

**Что сделать.**
1. Разобрать два способа получить `idem_key` и их разную надёжность (ниже).
2. Объяснить границу суточного окна у запасного ключа и записать решение по нему в `docs/decisions.md` — в коде оно помечено как «DECISION NEEDED» и не зафиксировано.
3. Показать на сценариях приёмки: повтор доставки, конкурентный повтор, другой заказ с тем же текстом.

**Контракт.**

| Ключ | Формула | Что означает |
|---|---|---|
| `thread_key` | `channel + ":" + (client_contact \| "anon")` | диалоговый тред канала; используется в M3.2 |
| `idem_key`, основной путь | `channel:message_id` | одна доставка одного сообщения |
| `idem_key`, запасной путь | `channel:hash:<sha256(channel\|contact\|нормализованный текст\|дата UTC)>` | когда канал не дал `message_id` |

Нормализация текста для хеша: `trim` → схлопывание пробелов → нижний регистр. Ответ: `201` — создано; `200` — уже было, тот же `id`, второй записи нет.

**Основной учебный путь — `message_id`.** Это идентификатор сообщения во внешней системе (Message-ID письма, id реплики мессенджера, id отправки формы). Он обязан быть стабильным при повторной доставке и уникальным в пространстве своего канала: ключ `channel:message_id` сравнивается только внутри канала, поэтому одинаковые id в разных каналах не сталкиваются. Канал, который генерирует новый id на каждую отправку, дедуп не обеспечивает — это дефект канала, а не приёма.

**Повтор доставки ≠ повторный заказ.**

| Ситуация | `message_id` | Что делает приём |
|---|---|---|
| вебхук доставил то же сообщение дважды | одинаковый | `200`, тот же `id`, одна запись |
| человек прислал новый заказ с тем же текстом («опять то же самое») | другой | `201`, новая запись |
| два разных клиента прислали идентичный текст | другой | `201` у каждого, две записи |

Пример: четыре обращения содержат одинаковый текст «мастер не приехал вчера, безобразие!» от **четырёх разных контактов**. Совпадение текста дублем не является.

**Краевые случаи.**
- Гонка: два одинаковых запроса одновременно → unique-индекс пропускает один, второй ловит `IntegrityError`, откатывается, читает существующую запись и отдаёт `200`. Не 500 и не вторая строка.
- Нет `message_id` и нет контакта → в ключ идёт `anon` (ограничение — M1.8 и `contracts.md` §12).
- Повтор через сутки: запасной ключ его не поймает — см. «Граница суточного окна» ниже. Склейка отложенных повторов — работа корреляции M3.2, а не приёма.

**Граница суточного окна (запасной ключ).** В хеш входит **календарная дата UTC**, а не скользящий TTL 24 часа. Отсюда два следствия, которые нужно уметь назвать:
1. Два одинаковых сообщения в `23:59Z` и `00:01Z` попадают в разные сутки → разные ключи → две записи, хотя прошло две минуты.
2. Тот же текст на следующий день — новая запись. Для повторного заказа это правильно, для отложенной повторной доставки — пропуск.

Строить TTL-инфраструктуру (отдельную таблицу дедупа, Redis-ключи со сроком жизни) в M1 **не нужно**. Нужно: описать выбранное поведение в `docs/decisions.md` как календарное окно, назвать его границу и указать, что надёжный путь — `message_id`.

Пример: два обращения (01.02, 20:54) и (02.02, 12:55) — тот же контакт, тот же текст. Календарное окно эту пару не склеит; третье обращение пришло другим каналом (`form` против `email`), а ключ начинается с канала — не склеится и по этой причине. Это ограничение приёма, а не ошибка: пара распознаётся позже, при корреляции треда.

**Проверка.** `kriterii-priyomki.md` § M1.7.

**Вопросы на понимание.**
1. Почему похожие (и даже дословно совпадающие) тексты не доказывают, что это дубль?
2. Чем входное сообщение отличается от обращения — и почему у них разные идентификаторы (`contracts.md` §11)?

## M1.8 — Аутентификация и анонимный контакт

**Проблема.** Приём открыт наружу: без ключа канала в базу пишет кто угодно. Операторская ручка отдаёт содержимое чужого обращения: проверки одной лишь подписи токена мало — подписанный тем же секретом токен может быть выдан не оператору.

**Что уже работает.** `app/core/security.py`: `require_api_key` (сверка `X-API-Key` с `settings.api_keys` через `hmac.compare_digest`), `require_operator` (декод `HS256`, алгоритм зафиксирован в коде, обязательные `exp` и `sub`), `issue_operator_token` для тестов. `POST /requests` закрыт ключом, `GET /requests/{id}` — токеном.

**Что сделать.**
1. Объяснить, почему у приёма и у операторской ручки разные механизмы (`contracts.md` §12: доверенная сторона — только приложение; содержимое обращения правами не управляет).
2. **Доработка.** `require_operator` сейчас проверяет подпись, срок и наличие `sub`, но **не проверяет полномочие**: `issue_operator_token` кладёт в токен `role: "operator"`, а проверка это поле игнорирует. Добавить проверку роли/полномочия и вернуть `403` для валидного токена без неё (`401` остаётся для отсутствующего, битого и протухшего).
3. Зафиксировать в `docs/decisions.md`, как называется поле полномочия и какие значения допустимы.

**Контракт.**

| Операция | Кредешл | Нет кредешла / негодный | Валиден, но полномочия нет |
|---|---|---|---|
| `POST /requests` | `X-API-Key` канала | 401 | — (ключи без ролей) |
| `GET /requests/{id}` | `Authorization: Bearer <JWT>` | 401 | 403 |

**Анонимный контакт.** Когда канал не дал контакт , `thread_key` получается видовой: `form:anon`, `messenger:anon`, `email:anon`. Отсюда правило, которое обязано соблюдаться дальше:

- `thread_key` с частью `anon` **не является** основанием объединить обращения. Все сообщения без контакта схлопываются в три ключа; это идентификатор «контакта нет», а не «это один и тот же человек».
- Новое анонимное сообщение не присоединяется к чужому открытому обращению. Корреляция M3.2 ищет открытое обращение только по доверенному идентификатору диалога; при его отсутствии создаётся новое обращение.
- Запасной hash-дедуп без идентичности отправителя ненадёжен в обе стороны: два разных анонима с одинаковым текстом в одни сутки дадут один `idem_key` (второе обращение вернётся как `200` и потеряется), а тот же аноним через сутки получит новую запись. Надёжно различает только `message_id` канала. Обещать различение одинаковых анонимных текстов нельзя — это ограничение, которое фиксируется, а не «лечится» подбором хеша.

**Краевые случаи.** Нет заголовка → 401. Неверный ключ → 401. Протухший токен → 401. `alg=none` или подмена алгоритма → 401. Токен подписан другим секретом → 401. Тело 401/403 не сообщает причину подробнее, чем `{error, detail}` — детали идут в лог, не клиенту.

**Проверка.** `kriterii-priyomki.md` § M1.8.

1. Почему корректной подписи токена недостаточно для доступа к операторской ручке?
2. Почему телефон, найденный в тексте обращения, не даёт прав на чужое обращение (`contracts.md` §12)?

## M1.9 — Redis: подключение и мягкая зависимость

## M1.10 — Docker и docker-compose

**Что уже работает.** `docker/Dockerfile` (multi-stage, non-root), `docker/docker-compose.yml`: `postgres` (named volume `pgdata`, healthcheck `pg_isready`), `redis` (healthcheck `redis-cli ping`), одноразовый сервис `migrate` (`alembic upgrade head`) и `app`, который ждёт `migrate: service_completed_successfully`. Цели `make up` / `make down`.

Простая замена на `service_started` всё ещё требует запуска контейнера. PostgreSQL остаётся жёсткой зависимостью (`service_healthy`) — без БД приём невозможен.

## M1.11 — Healthcheck и остановка

**Проблема.** Снаружи должно быть видно не только «процесс жив», но и «готов обслуживать». Если healthcheck при упавшей БД отвечает «мёртв», оркестратор бесконечно перезапускает здоровый процесс вместо того, чтобы подождать БД. Если отвечает «жив» — трафик льётся в 500.

**Что уже работает.** `GET /health` в `app/api/routes/health.py`: реальный `SELECT 1` в БД и `redis_ping()`, градация `ok` / `degraded` / `unhealthy`, формат `{status, deps: {db, redis}, version}`. Graceful shutdown в lifespan: `dispose_engine()` и `close_redis()`.

**Что сделать.**
1. Сверить правила градации: БД недоступна → `unhealthy` + 503; Redis недоступен при живой БД → `degraded` + 200; всё на месте → `ok` + 200.
2. **Доработка.** У проверки БД нет таймаута: при «зависшей» (не отказавшей) БД `/health` виснет вместе с ней и compose-healthcheck уходит в таймаут вместо явного 503. Добавить ограничение времени на проверку.
3. **Доработка.** Liveness и readiness сейчас не разделены — эндпоинт один. Развести их (два эндпоинта или параметр) и указать в compose-healthcheck именно readiness.

**Контракт.** `HealthOut`: `{status: ok|degraded|unhealthy, deps: {db: up|down, redis: up|down}, version: str}`. Коды: `unhealthy` → 503, остальные → 200.

**Краевые случаи.** БД легла на ходу → `/health` 503, приём отдаёт ошибку, а не зависает. Redis лёг → `degraded`, приём жив. Остановка по сигналу закрывает пул БД и клиент Redis.

**Проверка.** `kriterii-priyomki.md` § M1.11.

**Вопросы на понимание.**
1. Почему БД и Redis дают разный HTTP-код на `/health`?
2. Что именно сломается, если compose-healthcheck будет указывать на liveness вместо readiness?
