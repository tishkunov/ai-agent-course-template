# M1.11 — Healthcheck и остановка

## Что это и зачем

`/health` — эндпоинт, по которому снаружи понимают состояние сервиса: жив ли процесс и готовы ли его зависимости. Его дёргает docker-compose (`healthcheck`), позже — балансировщик и мониторинг. Ключевая мысль: не все зависимости одинаково важны. Без БД приём обращений невозможен (это `unhealthy`). Без Redis приём работает (это `degraded`, но HTTP 200).

## Что уже в каркасе

`app/api/routes/health.py`: реальный `SELECT 1` в БД и `redis_ping()`, градация `ok` / `degraded` / `unhealthy`, тело `{status, deps: {db, redis}, version}`, 503 только при отказе БД. Graceful shutdown — в lifespan `app/main.py` (`dispose_engine`, `close_redis`). Тесты трёх состояний — `tests/integration/test_health.py` (подменяют `_check_db` и `redis_ping`).

Чего нет: ограничения времени на проверку БД и разделения liveness/readiness — эндпоинт один.

## Теория простым языком

**Liveness (жив ли процесс)** — приложение отвечает вообще. Если нет — его нужно перезапустить.

**Readiness (готов ли обслуживать)** — процесс жив И зависимости на месте. Если не готов — на него не нужно слать трафик, но перезапуск не поможет (проблема во внешней БД).

Путать их вредно: если healthcheck при упавшей БД возвращает «мёртв», оркестратор начнёт бесконечно перезапускать здоровый процесс вместо того, чтобы подождать БД.

**Градация статуса:**
- всё на месте → `status: ok`, HTTP 200;
- Redis недоступен → `status: degraded`, HTTP 200 (приём работает);
- БД недоступна → `status: unhealthy`, HTTP 503.

**Реальная проверка, не заглушка.** `/health` должен действительно сходить в БД (`SELECT 1`) и пингнуть Redis, а не возвращать `{"status": "ok"}` константой. Заглушка бесполезна ровно тогда, когда что-то сломалось.

**Отказ и зависание — разные вещи.** Отказавшая БД отвечает ошибкой сразу, и `/health` честно отдаёт 503. Зависшая (сеть «чёрная дыра», перегруженный сервер) не отвечает вовсе — и проверка без ограничения времени виснет вместе с ней. Снаружи это выглядит не как «сервис не готов», а как «сервис не отвечает»: compose-healthcheck уходит в таймаут, причина теряется. Поэтому у проверки БД должен быть собственный предел времени, после которого зависимость считается недоступной.

**Graceful shutdown** — по сигналу `SIGTERM` приложение перестаёт брать новые запросы, доигрывает текущие, закрывает пулы БД и Redis, выходит. Без этого при остановке рвутся соединения и теряются недообработанные запросы.

## Что сделать по шагам

1. Прочитать `health()` и `_check_db()`; сверить градацию с правилами выше.
2. Ограничить время проверки БД: после предела `deps.db="down"`, `status="unhealthy"`, 503 — вместо ожидания.
3. Развести liveness и readiness (два эндпоинта либо один с параметром) и указать в compose-healthcheck именно readiness.
4. Проверить закрытие ресурсов при остановке: послать `SIGTERM`, убедиться, что пул БД и клиент Redis закрыты.
5. Дополнить тесты состоянием «БД зависла»: подменить проверку на функцию, которая ждёт дольше предела.

## Промпт-контракт к ИИ

Скоуп — только M1.11. Дать: текущий `health.py`, правила градации, требование предела времени и разделения liveness/readiness. Запросить: ограничение времени проверки БД, разделение эндпоинтов, тест на зависшую БД. Запретить: возвращать статус константой без проверки, ронять `/health` исключением при недоступной зависимости, делать redis критичным, раскрывать в ответе адреса и сообщения драйвера.

## Частые ошибки

- `/health` возвращает `ok` всегда, не проверяя соединения.
- БД недоступна, а `/health` отдаёт 200 — оркестратор считает сервис рабочим и льёт трафик в 500.
- Redis приравнен к БД по критичности — деградация превращается в полный отказ.
- Проверка БД без ограничения времени — `/health` виснет вместе с БД, и снаружи это выглядит как отказ приложения.
- Liveness указывает на readiness: оркестратор перезапускает здоровый процесс, пока недоступна внешняя БД.
- Нет закрытия пулов при остановке.

## Готово, когда
