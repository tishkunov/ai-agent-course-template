# M1.6 — Миграции (Alembic)

## Что это и зачем

Схема БД меняется по ходу проекта: M2 добавит колонки в `requests` и таблицу `llm_calls`, M4 — ещё колонки, M6 — новые таблицы. Нужен способ переводить БД из одной версии схемы в другую предсказуемо и обратимо. Это миграции: пронумерованные файлы «добавь колонку X», «создай таблицу Y», лежащие в git.

Почему не `Base.metadata.create_all()`. `create_all` создаёт таблицы по моделям с нуля. Он не умеет «добавить колонку в существующую таблицу с данными». В проде с живыми данными он бесполезен, а привычка им пользоваться приводит к тому, что схема на разных машинах разная.

## Теория простым языком

**Alembic** — инструмент миграций для SQLAlchemy. Хранит в БД номер текущей версии (`alembic_version`) и знает цепочку файлов-ревизий.

**`upgrade head`** — применить все миграции до последней. **`downgrade -1`** — откатить одну назад. Каждая миграция описывает и `upgrade()` (как накатить), и `downgrade()` (как откатить).

**autogenerate** — Alembic сравнивает модели в коде с реальной схемой БД и генерирует черновик миграции. Черновик всегда проверяют руками: autogenerate не видит переименования (видит «удалил колонку A, добавил колонку B»), не всегда ловит изменения типов и дефолтов.

**`env.py`** — конфиг Alembic. Его нужно научить брать `DATABASE_URL` из твоего `Settings` (а не из `alembic.ini`) и `target_metadata` из твоих моделей — тогда autogenerate видит модели.

**Дрейф схемы** — когда модель в коде и схема в БД разошлись. Проверка: после `upgrade head` запустить autogenerate ещё раз. Если он предлагает изменения — дрейф есть, миграция неполная.

**async-шаблон** — у Alembic есть отдельный шаблон `init` для async-движка (`alembic init -t async`). Нужен, потому что engine у нас asyncpg.

## Что сделать по шагам

1. Прочитать готовые `migrations/env.py` и `versions/0001_initial.py`. Повторный `alembic init` и новая начальная миграция не нужны.
2. Проверить в `migrations/env.py` получение URL из `Settings` и metadata из `app/db/base.py`.
3. Убедиться, что `naming_convention` из M1.5 подхватился (иначе имена индексов разойдутся).
4. В готовой `0001_initial.py` проверить: все поля, типы, индексы, unique на `idem_key`, дефолты БД (`created_at` server default).
5. `alembic upgrade head` на чистой БД → схема создалась. Повторный `--autogenerate` → пустой файл (нет дрейфа). `alembic downgrade base` → не падает.
6. Проверять downgrade только на отдельной пустой/тестовой БД; затем восстановить `upgrade head`. Новая миграция нужна только при доказанном расхождении.

## Промпт-контракт к ИИ

Скоуп — только M1.6. Дать: модель `Request` из M1.5, требование async-шаблона, требование читать URL из `Settings`. Запросить: ревью готовой миграции и проверку дрейфа на тестовой БД. Запретить: `create_all` где-либо, хардкод URL в `env.py`/`alembic.ini`, оставлять autogenerate без ручной выверки.

## Частые ошибки

- URL БД зашит в `alembic.ini` вместо чтения из `Settings`.
- Миграцию не проверили руками — в ней мусор от autogenerate или пропущен индекс.
- `naming_convention` не подхвачен в `env.py` → на каждом autogenerate «переименования» индексов.
- `downgrade()` оставлен пустым или с `pass`.
- Дефолт `created_at` только в модели (`default=`), не в миграции (`server_default=`) — при вставке в обход ORM колонка пустая.
