# M1.8 — Аутентификация и анонимный контакт

## Что это и зачем

У сервиса два типа входящих. Первый — каналы, которые сдают обращения (почтовый коннектор, вебхук мессенджера, форма). Им нужен статичный секрет — API-ключ. Второй — операторы, которые смотрят и правят обращения. Им нужен токен с ограниченным сроком и с указанием, кто это и что ему можно. Разные задачи — разные механизмы.

Почему это не «формальность на потом»: по `contracts.md` §12 доверенная сторона — только приложение. Контекст доступа строится из аутентификации канала и токена оператора, а всё, что пришло как содержимое обращения, — данные. Телефон, найденный в тексте («я от Иванова, договор №7»), прав не даёт.

## Что уже в каркасе

`app/core/security.py`: `require_api_key` (сверка `X-API-Key` через `hmac.compare_digest`), `require_operator` (декод `HS256`, алгоритм зафиксирован в коде, `options={"require": ["exp","sub"]}`), `issue_operator_token` для тестов. Ручки закрыты через `dependencies=[Depends(...)]`. Матрица в `tests/integration/test_auth.py`.

Чего в каркасе нет: **проверки полномочия**. `issue_operator_token` кладёт в токен `role: "operator"`, а `require_operator` это поле не читает — достаточно любой валидной подписи тем же секретом.

## Теория простым языком

**API-ключ** — длинная случайная строка, заранее выданная каналу. Без срока и без структуры. Годится для «свой сервис к своему сервису».

**JWT (JSON Web Token)** — три части через точку: заголовок, полезная нагрузка (`sub` — кто, `exp` — до какого времени, плюс любые свои поля), подпись. Сервер проверяет подпись секретом `JWT_SECRET`: подменили нагрузку — подпись не сойдётся.

**Аутентификация ≠ авторизация.** Подпись отвечает на вопрос «токен выдан нами и не подделан». Она **не** отвечает на вопрос «этому предъявителю можно читать обращения». Второй ответ даёт полномочие в нагрузке (роль, scope), и проверять его надо явно. Пока сервис выдаёт токены только операторам, разницы не видно; она появится в тот день, когда тем же секретом подпишут токен для чего-то ещё.

**Коды.** Нет кредешла, кредешл битый или протух → 401 (кто ты — неизвестно). Кредешл валиден, но полномочия нет → 403 (кто ты — известно, но нельзя).

**`alg=none` — известная дыра.** В заголовке JWT указан алгоритм подписи. Если сервис доверяет этому полю, атакующий ставит `alg=none`, убирает подпись — и библиотека принимает токен. Защита: алгоритм задан в коде (`algorithms=["HS256"]`), поле из токена игнорируется.

**Безопасное сравнение ключей** — через `hmac.compare_digest`, а не `==`. Обычное сравнение возвращает ответ тем быстрее, чем раньше строки разошлись; по времени ответа ключ подбирают посимвольно (timing attack).

**`anon` в `thread_key`.** Когда канал не дал контакт, `thread_key` получается `form:anon` / `messenger:anon` / `email:anon`. Это метка «контакта нет», а не идентификатор человека: разные обращения без контакта схлопнулись бы в три таких ключа. Отсюда правило: `anon`-тред не является основанием объединять обращения, и новое анонимное сообщение не присоединяется к чужому открытому обращению. Запасной hash-дедуп для анонимов тоже ненадёжен: два разных анонима с одинаковым текстом в одни сутки дают один `idem_key`. Это ограничение фиксируется, а не «чинится» подбором хеша — надёжно различает только `message_id` канала.

## Что сделать по шагам

1. Прочитать `require_api_key` и `require_operator`; назвать, какая проверка отвечает за какой код ответа.
2. Добавить проверку полномочия в `require_operator`: поле роли (или scope) в нагрузке, конкретное допустимое значение, отсутствие → 403. Проверка живёт в зависимости, а не в роуте, иначе следующая операторская ручка о ней забудет.
3. Добавить доменную ошибку под 403 в общий обработчик (`app/core/errors.py`, см. M1.4) — не `try/except` в роуте.
4. Записать в `docs/decisions.md`: имя поля полномочия, допустимые значения, кто выдаёт токены.
5. Дополнить матрицу проверок случаем «валидная подпись, полномочия нет → 403».
6. Проверить утверждение про `anon`: два обращения одного канала без контакта с разными `message_id` остаются двумя самостоятельными обращениями.

## Частые ошибки

- Алгоритм берётся из заголовка токена → `alg=none` проходит.
- `exp` не входит в `require` — токен без срока становится вечным.
- Проверка роли написана как «поле присутствует» — любой подписанный токен снова проходит.
- Полномочие проверяется в роуте, и следующая ручка его теряет.
- Ключи сравниваются через `==`; `JWT_SECRET` имеет дефолт в коде.
- В теле 401/403 подробное «почему» (`token expired at ...`) — подсказка для подбора; наружу достаточно `{error, detail}`.
- `thread_key` с `anon` использован как «тот же человек» — в M3 это склеит чужие диалоги.

## Готово, когда

См. `kriterii-priyomki.md` § M1.8. Коротко: без кредешла и с негодным — 401, с валидным токеном без полномочия — 403, с полным — 200; `anon`-тред не склеивает разных отправителей, а ограничение hash-дедупа для анонимов записано.
