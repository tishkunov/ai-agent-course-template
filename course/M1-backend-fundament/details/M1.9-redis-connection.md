# M1.9 — Redis: подключение и мягкая зависимость

## Что это и зачем

Redis понадобится в M8 — для кеша ответов, очереди, счётчиков бюджета. В M1 его поднимают заранее, чтобы инфраструктура была на месте, но никакой логики поверх него нет. Задача пункта: клиент подключается, `/health` его пингует, и — важно — если Redis лежит, приём обращений всё равно работает.

## Что уже в каркасе

`app/redis_client.py`: единый клиент из `REDIS_URL` (`get_redis()` создаёт его один раз), `redis_ping()` возвращает `False` вместо исключения, `close_redis()` вызывается в lifespan. Пинг включён в `/health` (`app/api/routes/health.py`).

Расхождение, которое предстоит закрыть: в коде зависимость мягкая, а в `docker/docker-compose.yml` сервис `app` объявлен через `depends_on: redis: condition: service_healthy` — то есть на старте жёсткая. Подробности и доработка — в M1.10.

## Теория простым языком

**Redis** — быстрое хранилище «ключ-значение» в памяти. Используется как кеш, брокер очередей, для счётчиков и блокировок.

**Пул соединений** — как с БД: клиент держит несколько открытых соединений и переиспользует их. Создавать клиент на каждый запрос — дорого и приводит к утечкам.

**Жёсткая vs мягкая зависимость.** Жёсткая: нет зависимости → сервис не работает. Мягкая: нет зависимости → сервис работает хуже, но работает. В M1 Redis ни на что не влияет, поэтому зависимость мягкая: недоступность Redis не должна ронять приём. Решение записывается в `docs/decisions.md` — в M8 часть Redis-функций станет важнее, и развилка будет обсуждаться заново.

**Мягкость проверяется в двух разных точках.** Это два сценария, и один не доказывает второй:
- *отказ после запуска* — сервис уже работает, Redis остановлен: приём отвечает 201, `/health` показывает `degraded`/200. Проверяется на работающем приложении (или подменой `redis_ping`);
- *отказ до запуска* — Redis не поднялся вовсе. Здесь решает не код, а `depends_on` в compose: с условием `service_healthy` приложение просто не стартует, сколько бы мягкости ни было в `redis_client.py`.

**`ping`** — команда Redis, которая отвечает `PONG`. Простейшая проверка «жив ли».

## Что сделать по шагам

1. Прочитать `app/redis_client.py`: убедиться, что клиент создаётся один раз, а не на запрос, и что `redis_ping` не выпускает исключение наружу.
2. Воспроизвести отказ после запуска: остановить контейнер `redis`, отправить `POST /requests` (ожидается 201) и запросить `/health` (ожидается `degraded`/200).
3. Воспроизвести отказ до запуска: поднять стек без сервиса `redis` — сейчас `app` не стартует. Это и есть расхождение, которое закрывается доработкой compose (M1.10).
4. Записать в `docs/decisions.md`, что зависимость мягкая в обоих сценариях, и как это отражено в compose.
5. Не писать кеш, очереди и `set/get` по бизнес-данным — только подключение и пинг.

## Промпт-контракт к ИИ

Скоуп — только M1.9. Дать: требование мягкой зависимости в обоих сценариях (до и после запуска), что пинг идёт в `/health`. Запросить: разбор `redis_client.py`, проверку обоих сценариев, формулировку решения для `docs/decisions.md`. Запретить: любую кеш-логику, пересоздание клиента на запрос, делать зависимость жёсткой, «чинить» compose-условие правкой кода приложения.

## Частые ошибки

- Клиент Redis создаётся внутри хендлера на каждый запрос.
- Ошибка пинга поднимается исключением и роняет `/health` целиком.
- Мягкость проверена только «на ходу», а на старте зависимость осталась жёсткой — сдача противоречит сама себе.
- Redis сделали жёсткой зависимостью — приём падает, когда кеш недоступен.
- «Заодно» добавили кеширование — это M8, сейчас лишний код и преждевременное решение.

## Готово, когда

См. `kriterii-priyomki.md` § M1.9 (и сценарий 10.4 про старт без Redis). Коротко: пинг реальный, отказ Redis после запуска даёт `degraded`/200 при живом приёме, отсутствие Redis на старте не блокирует приложение, кеш-логики нет.
