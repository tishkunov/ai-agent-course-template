# M1.10 — Docker + docker-compose

## Что это и зачем

Проект состоит из трёх процессов: приложение, PostgreSQL, Redis. Чтобы любой человек (и CI) поднял всё это одной командой и получил одинаковый результат, стек описывают в Docker: `Dockerfile` — как собрать образ приложения, `docker-compose.yml` — как запустить сервисы вместе и связать их.

Требование DoD модуля: с чистого клона стек поднимается одной названной командой, и данные переживают рестарт контейнеров.

## Что уже в каркасе

`docker/Dockerfile` (multi-stage, non-root) и `docker/docker-compose.yml` с четырьмя сервисами: `postgres` (named volume `pgdata`, healthcheck `pg_isready`), `redis` (healthcheck `redis-cli ping`), одноразовый `migrate` (`alembic upgrade head`) и `app`, который ждёт `migrate: service_completed_successfully`. Цели `make up` / `make down`.

Две особенности, которые надо знать до первого запуска:
- **Команда.** Compose лежит в `docker/`, а `build.context` в нём — `..`. Поэтому `docker compose up` из корня репозитория не сработает: нужен `make up` или `docker compose -f docker/docker-compose.yml up --build`.
- **Переменные.** Compose не читает `.env`: значения для локали записаны прямо в `docker-compose.yml`. Локальный запуск через `make run` читает `.env`. Это два независимых пути конфигурации.

Расхождение, которое предстоит закрыть: `app` ждёт `redis: condition: service_healthy`, хотя по M1.9 зависимость от Redis мягкая.

## Теория простым языком

**Образ vs контейнер.** Образ — слепок файловой системы с приложением и зависимостями (шаблон). Контейнер — запущенный экземпляр образа (процесс). Из одного образа можно поднять сколько угодно контейнеров.

**Multi-stage build.** `Dockerfile` в две стадии: в первой ставят зависимости и инструменты сборки, во второй копируют только готовое приложение в чистый slim-образ. Итог: финальный образ без компиляторов и dev-пакетов — меньше размер, меньше поверхность атаки.

**non-root.** По умолчанию контейнер работает от root. Если процесс скомпрометируют, root внутри контейнера — плохо. Добавляют пользователя и `USER app`.

**`.dockerignore`** — как `.gitignore`, но для сборки образа: не тащить в образ `.venv`, `.git`, `.env`, кеши. Иначе секреты и мусор попадут в слои образа.

**`healthcheck`** — команда, которой Docker проверяет, что сервис реально готов (не просто «процесс запустился»). Для postgres — `pg_isready`, для app — запрос к `/health`.

**`depends_on` и его условия.** `service_healthy` — стартовать после того, как healthcheck зависимости позеленел; `service_started` — просто после запуска контейнера; `service_completed_successfully` — после успешного завершения одноразового сервиса (так `app` ждёт `migrate`). Условие выбирается по критичности: без PostgreSQL приём невозможен, значит `service_healthy`; Redis в M1 ни на что не влияет, и ожидание его здоровья превращает мягкую зависимость в жёсткую.

**named volume** — именованный том для данных PostgreSQL. Без него данные лежат внутри контейнера и исчезают при его пересоздании. С volume — переживают `restart` и пересборку.

## Что сделать по шагам

1. Поднять стек: `make up`. Убедиться, что порядок соблюдён: `postgres` healthy → `migrate` завершился успешно → `app` healthy.
2. Прочитать `docker/Dockerfile` и проверить: multi-stage, финальный образ без dev-зависимостей и компилятора, `USER` не root, `.env` в образ не копируется.
3. Прочитать `depends_on` сервиса `app` и сопоставить с правилом M1.9. Сделать Redis мягкой зависимостью: убрать его из `depends_on` сервиса `app`, оставив `postgres` на `service_healthy`. Записать решение в `docs/decisions.md`.
4. Проверить старт без Redis: поднять `postgres`, `migrate`, `app` — приложение должно принимать обращения, `/health` — `degraded`/200.
5. Проверить сохранность данных: создать обращение → `docker compose -f docker/docker-compose.yml restart` → обращение на месте.
6. В материалах сдачи писать команду с путём к compose-файлу (или `make up`), а не `docker compose up` из корня.

## Промпт-контракт к ИИ

Скоуп — только M1.10. Дать: фактическое расположение compose (`docker/`, `context: ..`), список сервисов и порядок их старта, правило мягкой зависимости Redis из M1.9. Запросить: разбор `depends_on` и правку условия для `redis`, проверку сценариев «старт без Redis» и «рестарт с сохранением данных». Запретить: класть секреты в образ, healthcheck-заглушки (`test: ["CMD","true"]`), убирать `service_healthy` у `postgres`, переносить миграции в каждый старт `app`.

## Частые ошибки

- `COPY .env` или `ARG PASSWORD` в Dockerfile — секрет в слоях образа навсегда.
- Однослойный образ с компилятором и dev-зависимостями; нет `.dockerignore`.
- `depends_on` без условия у `postgres` → app стартует раньше БД и падает.
- Ожидание здоровья Redis → мягкая зависимость на бумаге, жёсткая на практике.
- Данные postgres без named volume → пропадают при пересоздании контейнера.
- `healthcheck`, который всегда зелёный.
- В отчёте осталась команда `docker compose up` из корня — она не работает.

## Готово, когда

См. `kriterii-priyomki.md` § M1.10. Коротко: стек поднимается названной командой до healthy в порядке `postgres → migrate → app`, отсутствие Redis старт не блокирует, данные переживают рестарт, секретов в образе нет.
