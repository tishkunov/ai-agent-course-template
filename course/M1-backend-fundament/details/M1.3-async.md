# M1.3 — Асинхронность

## Что это и зачем

Сервис почти всё время чего-то ждёт: ответа от БД, от Redis, позже — от LLM. Если во время ожидания процесс просто стоит, то при 10 одновременных запросах десятый ждёт, пока отработают первые девять. Асинхронность позволяет на время ожидания заняться другим запросом. Для сервиса, который в основном ходит по сети и в БД (I/O-bound), это разница между «держит 5 запросов» и «держит 500».

## Теория простым языком

**Event loop** — один поток, который крутит цикл: «есть готовая работа — выполни кусок; дошли до `await` (ожидание) — отложи эту задачу, возьми другую; пришёл ответ по сети — верни задачу в работу». Всё в одном потоке, переключение — только на `await`.

**ASGI** — стандарт, по которому асинхронный веб-сервер (uvicorn) общается с приложением (FastAPI). Пришёл запрос → сервер вызывает твой `async def` хендлер внутри event loop.

**`async` / `await`** — `async def` объявляет корутину. `await something()` означает «здесь можно ждать, отдай управление loop'у». Без единого `await` внутри async-функция ничего не даёт.

**Где async помогает:** ожидание сети, БД, диска, внешних API (I/O-bound). **Где не помогает:** тяжёлые вычисления в цикле (CPU-bound) — они занимают единственный поток, и весь loop встаёт. В M1 таких задач нет; когда появятся — их выносят в отдельный пул.

**Почему синхронный вызов внутри async ломает всё:** `time.sleep(2)` не отдаёт управление loop'у — весь сервис замирает на 2 секунды. То же с синхронным драйвером БД или `requests.get()`: пока он ждёт, event loop не может обслуживать другие запросы.

## Что сделать по шагам

1. Все хендлеры — `async def`. Все функции репозитория/сервиса, которые ходят в БД, — `async`.
2. Драйвер БД — `asyncpg` (через `create_async_engine` в SQLAlchemy). Не `psycopg2`.
3. Пройтись по коду и убрать из async-путей:
   - `time.sleep` → `asyncio.sleep`;
   - `requests` / `httpx.Client` → `httpx.AsyncClient`;
   - синхронные драйверы БД;
   - длинные CPU-циклы (в M1 не должно быть).
4. Запустить N параллельных `POST /requests` с разными ID, проверить сохранность всех записей.
   Отдельно подменить I/O на асинхронную заглушку с барьером: все задачи должны войти
   в ожидание до его снятия. Не требовать времени одного запроса от реальной БД: пул и нагрузка
   ограничивают параллельность (сценарий 3.1 приёмки).

## Частые ошибки

- `async def`, внутри которого нет ни одного `await` — выглядит асинхронно, работает синхронно.
- Синхронный драйвер БД под async SQLAlchemy.
- `time.sleep` в коде ретраев или тестовых заглушках.
- Попытка «ускорить» CPU-задачу через `async` — не работает, нужен пул.
