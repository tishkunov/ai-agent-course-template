# M1.1 — Структура проекта и окружение

## Что это и зачем

Проект разбивается на слои, и у каждого слоя одна работа:

- `api/` — принять HTTP-запрос, проверить вход, отдать ответ. Больше ничего.
- `services/` — доменная логика: «как принять обращение», «как посчитать idem_key». Не знает про HTTP.
- `db/` + `models/` — как данные лежат в PostgreSQL и как их достать.
- `schemas/` — формы данных на границе (что приходит в запросе, что уходит в ответе).
- `core/` — конфиг, безопасность, логирование. Общее для всех слоёв.

Зачем так. Когда роут сам лезет в SQL, а сервис сам читает заголовки запроса, через три модуля код превращается в клубок, где нельзя поменять одну вещь, не задев пять других. Слои — это дешёвая страховка: пока роут ходит в БД только через сервис/репозиторий, каждый слой можно менять и тестировать отдельно.

Конфиг из окружения, а не из кода. Один и тот же образ приложения должен подниматься на твоём ноуте, в тестах и на сервере — разница только в переменных окружения (`DATABASE_URL` и т.д.). Если адрес БД зашит в код, для сервера нужна пересборка. Это принцип «12-factor app»: конфиг живёт в среде, код везде одинаковый.

Секретов нет в коде и в lock-файле. `git` хранит всю историю. Один раз закоммиченный пароль остаётся в истории навсегда, даже если потом его удалить. Поэтому секреты только через переменные окружения, а `.env` — в `.gitignore`.

## Что уже в каркасе

Дерево `app/{api,services,db,models,schemas,core}` с `main.py`, каталоги `migrations/`, `tests/`, `docker/`. `app/core/config.py` — `Settings(BaseSettings)` и `get_settings()` под `lru_cache`. `pyproject.toml` (uv, Python ≥ 3.12, ruff + mypy). `Makefile` с целями `run / test / lint / typecheck / migrate / lock / up / down`. `.env.example`.

Чего не хватает: lock-файла в репозитории (`uv.lock` отсутствует) и аккуратного `.env.example` — сейчас в нём все переменные перечислены строкой `ИМЯ=` с пустым значением, включая необязательные.

## Теория простым языком

**`pydantic-settings` / `BaseSettings`** — класс, который читает поля из переменных окружения и сразу проверяет типы. `DATABASE_URL: str` — если переменной нет, приложение падает на старте с сообщением «поле обязательно», а не через час на первом запросе к БД.

**Пустая строка — это значение.** `LOG_LEVEL=` в `.env` не означает «возьми значение по умолчанию»: переменная задана и равна `""`, а пустая строка не проходит проверку типа (`Literal["DEBUG","INFO",...]`, `int`). Дефолт применяется только тогда, когда переменной нет вовсе. Отсюда правило для `.env.example`: обязательные переменные — строкой для заполнения, необязательные — закомментированы с указанием значения по умолчанию.

**Кешируемый геттер** — `Settings()` парсит окружение при создании. Делать это на каждый запрос — лишняя работа. Поэтому геттер оборачивают в `functools.lru_cache` (или аналог): первый вызов создаёт объект, дальше возвращается тот же.

**lock-файл** (`uv.lock` / `poetry.lock`) — фиксирует точные версии всех зависимостей, включая транзитивные. Без него «работает у меня» и «работает в CI» — разные наборы версий. Lock-файл коммитится в git.

## Что сделать по шагам

1. Прочитать `app/core/config.py` и выписать два списка: обязательные поля (без дефолта) и поля со значением по умолчанию.
2. Проверить на себе поведение пустой строки: положить в `.env` строку `LOG_LEVEL=` и запустить `make run`. Старт упадёт — понять, почему.
3. Привести `.env.example` к разделению: `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, `API_KEYS` — строками для заполнения; `APP_ENV`, `JWT_TTL_MIN`, `LOG_LEVEL`, `DB_POOL_SIZE`, `DB_MAX_OVERFLOW` — закомментированы с указанием дефолта.
4. Доработать сообщение об ошибке конфигурации: сейчас `get_settings()` называет только *отсутствующие* переменные, а при невалидном значении выдаёт общий текст. Имя поля должно быть видно в обоих случаях.
5. Сгенерировать lock-файл (`make lock`) и закоммитить его; убедиться, что он не попал в `.gitignore`, а `.env` — попал.

## Промпт-контракт к ИИ

Скоуп — только M1.1. Дать: содержимое `app/core/config.py`, различие «переменной нет» и «переменная пустая», требуемый вид `.env.example`. Запросить: правку `.env.example`, доработку сообщения об ошибке конфигурации, команду генерации lock-файла. Запретить: трогать БД/Redis/роуты (это другие пункты), добавлять поля `Settings` сверх существующих, давать секретам значения по умолчанию.

## Частые ошибки

- `os.environ["DATABASE_URL"]` где-то в глубине кода вместо чтения через `Settings`.
- Дефолт у секрета: `JWT_SECRET: str = "changeme"` — сервис молча запустится с небезопасным ключом.
- `.env.example` со строками `ИМЯ=` для необязательных переменных — копирование файла как есть ломает старт.
- lock-файл не закоммичен или в `.gitignore`.
- `Settings()` создаётся в нескольких местах вместо одного кешируемого геттера.

## Готово, когда

См. `kriterii-priyomki.md` § M1.1. Коротко: обязательные переменные без дефолтов, необязательные работают без строки в `.env`, при любой ошибке конфигурации названо имя поля, lock-файл в git.
