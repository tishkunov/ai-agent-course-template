# M1.5 — PostgreSQL + ORM

## Что это и зачем

Обращение нужно где-то хранить, и это PostgreSQL. ORM (SQLAlchemy) даёт писать `session.get(Request, id)` вместо строк SQL и защищает от SQL-инъекций «по умолчанию». Слой доступа (`RequestRepository`) прячет детали работы с сессией: сервис говорит «создай обращение», а не «открой сессию, сделай INSERT, закоммить».

Главная опасность здесь — утечка соединений. Соединений с БД конечное число (пул). Если сессия открылась и не закрылась (упало исключение, забыли `finally`), соединение не вернулось в пул. Несколько таких — и новые запросы висят в ожидании свободного соединения.

## Теория простым языком

**Engine** — фабрика соединений с настройками пула (сколько держать открытыми). Создаётся один раз на приложение.

**Сессия** — «рабочая область» для одной единицы работы: набор объектов, изменения, транзакция. Живёт коротко — на один запрос. Схема: открыть → поработать → `commit` (или `rollback` при ошибке) → закрыть. В FastAPI это делает зависимость `get_session` через `yield`: код после `yield` выполняется всегда, даже при исключении.

**`async_sessionmaker`** — фабрика async-сессий, привязанная к engine.

**Модель = таблица.** Класс `Request(Base)` с `Mapped[str]`-полями — это описание таблицы `requests`. Один экземпляр = одна строка.

**Репозиторий** — класс/модуль с методами под конкретные запросы: `create`, `get_by_id`, `get_by_idem_key`. Не «универсальный доступ к любой таблице», а именно те операции, что нужны.

**`naming_convention`** — шаблон имён для индексов, ограничений, внешних ключей (`ix_%(table)s_%(column)s` и т.п.). Задаётся в `MetaData`. Без него SQLAlchemy и Alembic генерируют имена по-разному, и autogenerate в M1.6 начинает выдавать ложные «изменения».

**Detached-объекты.** ORM-объект, полученный в сессии, после её закрытия «отсоединён»: обращение к ленивому полю кинет ошибку. Поэтому наружу сессии либо отдают уже загруженные данные, либо преобразуют в pydantic-схему внутри сессии.

## Что сделать по шагам

1. Прочитать уже существующий `app/db/session.py`: engine, `async_sessionmaker`, настройки пула.
2. Проследить в том же файле `get_session()` с `yield`, commit, rollback и закрытием сессии.
3. Прочитать `app/db/base.py`: `Base` с `MetaData(naming_convention=...)`.
4. Сверить существующую `app/models/request.py` — модель `Request` по таблице из `zadanie.md` § M1.5 (все поля, типы, индексы на `thread_key`, `status`, `created_at`, unique на `idem_key`).
5. Прочитать `app/db/repositories/request_repo.py`: `RequestRepository`, методы `create`, `get_by_id`, `get_by_idem_key` и выдачу ID через `request_seq`.
6. Тесты: создать и прочитать через репозиторий; проверить, что при исключении внутри сессии происходит rollback; `get_by_idem_key` находит существующее.

## Промпт-контракт к ИИ

Скоуп — только M1.5. Дать: таблицу полей `requests` дословно, список методов репозитория, требование `naming_convention`. Запросить: разбор готовых engine, модели и репозитория, проверку rollback; не создавать их заново. Запретить: SQL с конкатенацией пользовательских значений (фиксированный `SELECT nextval` в каркасе допустим), бизнес-логику в репозитории, менять состав полей таблицы.

## Частые ошибки

- Сессия не закрывается при исключении (нет `yield`/`finally`).
- Одна сессия на всё приложение вместо сессии на запрос.
- `naming_convention` не задан → autogenerate в M1.6 «дрейфует».
- Репозиторий возвращает живой ORM-объект, к нему обращаются после закрытия сессии → ошибка detached instance.
- Конкатенация значений в строку SQL.

## Готово, когда

См. `kriterii-priyomki.md` § M1.5. Коротко: запись создаётся и читается через слой доступа, при ошибке в транзакции — rollback, соединения не текут.
