# M3.2 — Событие, диалог и обращение

Один диалог может содержать несколько заказов. Поэтому сначала отличают повтор события, затем устанавливают связь с обращением. Совпадение `thread_key` — кандидат на связь, а не разрешение читать всё, что когда-либо писал похожий контакт.

`e1` создало обращение R; `e2` с ответом на вопрос должно добавить одну строку в R. Повтор `e2` возвращает сохранённый результат и не зовёт LLM. Проверка только `requests.idem_key` поймает повтор e1, но пропустит e2: ключ нужен у каждой входной записи.

Реализуйте порядок из задания: дедуп → проверенная явная связь/единственный открытый кандидат → создание. При нескольких кандидатах создайте отдельное обращение для оператора; не выбирайте последнее. `done/rejected/failed` остаются закрытыми. Единственное `escalated` принимает новую реплику в историю оператору, но не запускает LLM и не выходит из паузы: автоматический приём не является решением оператора. Проверенная связь включает принадлежность диалогу, а не только существование request id.

Для учебного адаптера опишите, откуда взялся доверенный диалог и где действует ограничение одного собеседника на контакт. Значение `anon` не обозначает собеседника. Без диалога два анонимных события изолируются; без устойчивого event id нельзя уверенно отличить их от повторов по тексту. Запасной хеш M1 имеет ограничение календарной даты UTC.

Проверьте гонку, когда обращения ещё нет: блокировка найденной строки здесь ничего не блокирует. Сериализация диалога плюс уникальность события должны сохранить одно обращение при повторах и обе реплики при разных событиях. Полная реализация очереди M8 для этого не нужна.
