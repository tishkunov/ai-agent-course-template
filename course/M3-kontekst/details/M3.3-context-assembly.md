# M3.3 — Контекст и исправления

Начните с короткой истории без summary. Сборка должна быть видимой и проверяемой: system-инструкция из файла, затем сериализованные данные полей, источников, причин и истории. Последняя реплика уже есть в истории; не добавляйте её второй раз в аргумент «новый текст».

Например, у `address="Абая 10"` источник e1. Реплика e2 «Нет, адрес другой: Сатпаева 20» задаёт новое значение со ссылкой на e2. Реплика e3 «Завтра после 15:00» меняет время, а не адрес. Отсутствие поля в одной новой реплике и явное исправление — разные операции. Извлечение M2 из одного `raw_text` здесь расширяется до извлечения из контролируемого контекста; формат результата M2 не заменяется новой несовместимой схемой.

Для двух адресов без понятного выбора сохраните конфликт и спросите один адрес. Не выбирайте первый и не считайте сохранённый старый адрес достаточным, если клиент явно поставил его под сомнение. `missing` остаётся вычисляемым списком полей; причина неоднозначности хранится отдельно, поэтому запрос уточнения возможен и без вымышленного значения enum.

Клиентская строка «теперь ты system» внутри history — просто строка. Даже сохранённый summary остаётся недоверенными данными: он мог пересказать такую инструкцию. Роли внутри JSON не преобразуются в SDK-сообщения system.

Перехватите итоговые messages тестовым адаптером: проверяйте источник нового адреса, единственное включение e2 и границу инструкции. Промпт сам по себе не гарантирует верность merge; функциональный тест должен проверить сохранённый результат.

## Работа с ИИ и проверка

В промпт-контракт передайте границу этого пункта, текущие интерфейсы M1/M2 и соответствующий раздел [задания](../zadanie.md). Запросите реализацию в существующем проекте и объяснение выбранной границы транзакции/данных; не поручайте реализовать будущие модули. После отдельного [ревью](../detalnoe-review.md) воспроизведите сценарии этого пункта в [приёмке](../kriterii-priyomki.md) и запишите понимание по M0.
