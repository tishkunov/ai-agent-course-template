# course/contracts.md — правила работы сервиса

Один источник сквозных правил для всех модулей M1–M9. Если `zadanie.md`, `kriterii-priyomki.md`,
`detalnoe-review.md`, `details/` или `ai_context/` расходятся с этим файлом — верен этот файл,
а расхождение исправляется в модуле, а не здесь по месту.

Что здесь есть: формат учебного задания, обязательный объём курса, словарь решений
(`req_type`, `priority`, `route_decision`, `validation_outcome`, `status`), правила типов,
достаточность и неизвестность, таблица приоритетов маршрута, работа с суммой, порядок исполнения,
состояния и паузы, идентификаторы, границы доверия, версии схем и раздел о различиях с разметкой
`data/`.

Чего здесь нет: вводной курса (аудитория, prerequisites, описание бизнеса) — она у пользователя;
процесса работы — он в `M0-start/`; теории — она в `details/`.

---

## 1. Формат задания (C01)

Каждый практический пункт `M{n}.x` в `zadanie.md` использует следующие элементы в этом порядке.
Общие элементы можно вынести в начало/конец модуля и сослаться из пункта; снятые пункты остаются
короткими указателями. Не заполняйте раздел без содержательной необходимости.

| Раздел | Что в нём | Чего в нём нет |
|---|---|---|
| **Проблема** | что ломается без этого пункта, на каком входе это видно | общих слов «важно для продакшна» |
| **Что уже работает** | что именно даёт предыдущий модуль/пункт, на что можно опереться (со ссылкой на номер пункта) | пересказа предыдущего задания |
| **Что сделать** | нумерованный список работы студента | готового кода решения |
| **Пример входа и результата** | один конкретный вход и ожидаемый результат; все значения либо во входе, либо из названного источника | скрытых полей, которых во входе нет |
| **Контракт** | имена функций/полей/эндпоинтов и их значения, которыми пользуются следующие модули | второй копии общих enum — ссылка на §4 этого файла |
| **Краевые случаи** | границы, которые обязаны быть обработаны | списка всех возможных ошибок мира |
| **Проверка** | к какому разделу `kriterii-priyomki.md` относится пункт | дословного повтора сценариев приёмки |
| **Вопросы на понимание** | 2–3 вопроса на модуль о конкретном результате: почему так; какой сбой ловит проверка; что станет неверным при изменении условия | вопросов вида «что такое RAG» |

Правила разделения файлов: `zadanie.md` — поведение; `kriterii-priyomki.md` — проверка этого
поведения; `detalnoe-review.md` — риски реализации без дословного повтора проверок; `details/` —
теория, разобранный пример и частые ошибки со ссылкой на пункт задания, а не второй контракт.
Новое требование не появляется только в ревью или только в деталях.

Английский термин объясняется при первом использовании и дальше применяется последовательно.
Расплывчатые формулировки («осмысленный», «устойчивый», «готовый к продакшну», «реальный агент»)
заменяются конкретным поведением и его проверкой.

## 2. Обязательный объём (C02)

Маршрут прохождения один. Второго трека, каталога необязательных упражнений и оценок длительности
нет. Нумерация M0–M9 и номера пунктов сохраняются; снятые пункты остаются файлами-указателями на
актуальную замену, чтобы старые ссылки разрешались.

M0 не изменяется: рабочее соглашение, цикл работы, уровни приёмки, отдельный ревью-вызов и записи
понимания действуют во всех модулях.

Снятое из обязательной части (и, значит, из приёмки и ревью тоже):

| Пункт | Решение | Что остаётся обязательным |
|---|---|---|
| M2.11 «Стриминг (SSE)» | снят; отдельного SSE-приложения нет | параметр `stream` в сигнатуре `LLMClient.complete` (M2.1) остаётся, реализация эндпоинта не требуется |
| M2.1 «два провайдера» | снято требование второго адаптера | один реальный адаптер провайдера за конфигом; запасная модель и цепочка — M8.5 |
| M4.2 «сравнение моделей эмбеддингов» | снят как упражнение | модель эмбеддингов зафиксирована в конфиге + запись выбора в `docs/decisions.md` (внутри M4.1) |
| M4.4 «кластеризация и подбор числа кластеров» | снят | обнаружение близких повторов остаётся там, где оно нужно по делу: порог семантического кеша M8.6 |
| M4.5 «регрессия» | снят; в проекте задачи регрессии нет | — |

Не снимается: запасная модель и fallback в M8.5 (это действующее задание, а не дубль M2);
эксперимент с гибридным поиском и реранкингом в M5 (обязательны сравнение и вывод, гарантированный
прирост качества не требуется); один локальный MCP-инструмент и один ограниченный цикл tool use в
M6; объём M8–M9 по списку технологий.

Мультиагентной системы в курсе нет. Поиск «лучшей ML-модели» в M4 не является задачей: M4 —
прикладной пункт ИИ-инженера (дешёвый классификатор как пред-фильтр перед LLM).

## 3. Пайплайн S1–S10

Номера S — это зоны ответственности, а не порядок вызовов. Фактический порядок исполнения — §8.

| Шаг | Что делает | Модуль |
|---|---|---|
| S1 Приём и корреляция | новое / продолжение по `thread_key`, дедуп по `idem_key` | M1.7 (приём) + M3.2 (корреляция) |
| S2 Нормализация входа | вложения (PDF/фото/скан) → текст (OCR) | M5.2, частично M1 |
| S3 Идентификация клиента | сопоставление со справочником `clients` | M5.1 |
| S4 Классификация | `req_type`, `priority`, результат классификации, `type_confidence` | M4.6 |
| S5 Извлечение | поля по схеме, `missing` | M2.5/M2.7 |
| S6 Проверка достаточности | вопрос по недостающему, статус `need_info` | M3.7 |
| S7 Валидация | зона/прайс/клиент по SQL + регламенты по RAG | M5.9 |
| S8 Маршрут | `route_decision` + `route_reason` | M6.7 |
| S9 Действие | идемпотентно: заявка / ответ / слот | M6.8 |
| S10 Оператор (HITL) | очередь, экран, подтвердить / править / отклонить / вернуть | M6.9 |

Сквозные механизмы поверх пайплайна: guardrails (обёртка S8–S9) — M6.10, углублённо M7;
надёжность (очередь, retry/timeout/circuit breaker, деградация, идемпотентность S9) — M8;
стоимость (токены и цена на обращение, кеш только для знаний/RAG и стабильных под-промптов,
бюджеты) — M2.8 → M8.7; оценка (eval-набор, метрики, регресс промптов, injection/leak) — M7;
наблюдаемость (трейс, логи, метрики, дашборд, алерты) — M9.

## 4. Словарь решений: пять разных полей (C03)

Это пять независимых величин. Ни одна не выводится из другой автоматически.

| Поле | Отвечает на вопрос | Значения | Кто проставляет |
|---|---|---|---|
| `req_type` | что это за обращение | `заявка` \| `вопрос` \| `жалоба` \| `спам`; `null` — не подтверждено, не новый класс | M4.6 (S4) |
| `priority` | насколько срочно | `низкий` \| `средний` \| `высокий` \| `срочный`; `null` — не подтверждено | M4.6 (S4) |
| `validation_outcome` | что показала проверка по справочникам и регламентам | база `ок` \| `need_info` \| `правило_не_выполнено` \| `данных_нет` \| `спам`, плюс необязательная `:детализация` | M5.9 (S7) |
| `route_decision` | что система делает дальше | `авто` \| `уточнение` \| `эскалация` \| `reject` | M6.7 (S8) |
| `status` | в каком состоянии обращение лежит в БД | `new` \| `in_progress` \| `need_info` \| `escalated` \| `done` \| `rejected` \| `failed` | M1 (`new`), M3, M6 |

`priority` не влияет на `route_decision`: срочная заявка с полным набором полей и пройденными проверками идёт в `авто`,
несрочная жалоба идёт к оператору. `priority` управляет порядком в очереди оператора (M6.9) и
бизнес-метриками (M9.4), не маршрутом.

**Слово «роутинг» без уточнения не используется.** В проекте три разных «роутинга»:

| Формулировка | Что выбирается | Где |
|---|---|---|
| классификация обращения | `req_type` и `priority` | M4.6, поле `routing_method` = `classic` \| `llm` — кто дал финальный ответ классификации |
| решение о маршруте обработки | `route_decision` | M6.7 |
| выбор модели | какая LLM обслужит вызов | M2.9 (по умолчанию), M8.7 (по сложности), M8.5 (fallback-цепочка) |

`type_confidence` — доля голосов локальных соседей M4, не вероятность правильности. Для LLM
она `null`. Неподтверждённый тип или приоритет хранится как `null` с `classification_reason`;
это отсутствие решения, а не новый тип. Любой такой результат не разрешает автоматическое действие.

### 4.1 Сквозной пример одновременных значений

Вход (канал `messenger`, контакт `+7 921 000-11-22`):

```
Розетка на кухне искрит, боюсь включать. Приморский район, нужен электрик сегодня.
```

Одно обращение, один прогон, значения полей после него:

| Поле | Значение | Почему |
|---|---|---|
| `req_type` | `заявка` | просьба о работе мастера, не вопрос и не жалоба |
| `priority` | `срочный` | искрит проводка — признак риска, значение даёт классификатор M4 |
| `extracted_fields` | `{service: "нужен электрик, розетка искрит", object: "розетка на кухне", address: null, contact: "+7 921 000-11-22", time: "сегодня"}` | извлечение M2.5; `contact` взят из канала |
| `missing` | `["адрес"]` | обязательные поля заявки — услуга, адрес, контакт (§6) |
| `validation_outcome` | `need_info` | проверка не завершена: не хватает обязательного поля |
| `route_decision` | `уточнение` | правило 9 таблицы §7 |
| `status` | `need_info` | ждём ответа клиента, прогон сохранён и завершён |

Район `Приморский` известен и в зоне, поэтому правило «вне зоны» не сработало. Сопоставление симптома с точной услугой ещё не подтверждено: замена розетки не следует из текста.
Поэтому отрицательная проверка прайса не выполняется; уточняется услуга наряду с адресом. `priority=срочный` ничего не изменил:
уточнение всё равно нужно. Если бы район был известен и **вне** зоны, сработало бы правило 6
(эскалация), и сбор адреса не разблокировал бы `авто`.

## 5. Правила по типу обращения (C04)

Ветка по `req_type` выбирается после классификации и определяет, какие проверки вообще применимы.

**`спам`** → `route_decision=reject`, `validation_outcome=спам`, `status=rejected`.
Ни одного исходящего сообщения клиенту: вопрос об адресе, извинение, уведомление об отклонении не
отправляются. Валидация, извлечение обязательных полей и действия не выполняются.
Источники признака: классификатор M4.6 и детерминированные признаки канала (непустой `_hp_website`
в веб-форме — honeypot). Признак нормализует доверенный адаптер канала; поле не добавляется
произвольно в тело текущего API M1 с `extra=forbid`.

**`жалоба`** → `route_decision=эскалация`, `validation_outcome=ок:не_заявка`, `status=escalated`.
Обязательные поля заявки автоматически не запрашиваются: «мастер не пришёл» не превращается в
вопрос «назовите адрес и контакт». Заявка не создаётся. Решение, что делать дальше, принимает
оператор (M6.9), он же при необходимости запускает до-сбор возвратом обращения в `in_progress`.

**`вопрос`** → поиск ответа по базе знаний (M5.5–M5.8), адрес и контакт не обязательны, заявка
мастеру не создаётся.
- ответ подтверждён источниками (`found=true`, ссылки на документы есть) → `route_decision=авто`,
  действие — `send_reply` с источником, `validation_outcome=ок:не_заявка`, `status=done`;
- ответ источниками не подтверждён (`found=false`, противоречивые или недоступные источники) →
  `route_decision=эскалация`, `validation_outcome=данных_нет`, `status=escalated`.
  Придуманный ответ вместо эскалации — ошибка, а не «деградация».

**`заявка`** → проверка достаточности (§6) и проверка известных условий (§7): зона, прайс, сумма,
регламенты. Дальше — по таблице приоритетов.

Тип открытого обращения проверяется заново после ответа клиента (§8). Если прежний вопрос уже
закрыт в `done`, «тогда пришлите мастера» создаёт новое обращение по §10, а не переоткрывает старое.
Тип фиксируется на прогон, а не назначается навсегда при первом приёме.

## 6. Достаточность и неизвестность (C05)

**Обязательные поля заявки — три: услуга, адрес, контакт.** `missing` — подмножество
`["услуга", "адрес", "контакт"]` (значения по-русски, как в `data/`). Время (`time`) — пожелание
клиента; его отсутствие не даёт `need_info` и не попадает в `missing`. Конкретный слот становится
обязательным только там, где отдельное правило модуля этого требует (назначение слота в M6.8), и
тогда это требование действия, а не достаточности.

Обязательные поля применяются только к `req_type=заявка` (§5).

**Три состояния любой проверки, а не два.** Каждая проверка (зона, прайс, сумма, регламент, клиент)
может дать: «подтверждено — да», «подтверждено — нет», «неизвестно». Неизвестно ≠ нет.

| Наблюдение | Что это значит | Что это **не** значит |
|---|---|---|
| `service = null` | услугу не удалось распознать → `услуга` в `missing`, маршрут `уточнение` | не значит «услуги нет в прайсе»; проверка прайса при `service=null` не выполняется вовсе |
| `district = null` (район не определён по адресу) | район неизвестен → уточнение адреса/района; после лимита кругов — оператор | не значит «вне зоны»; проверка зоны при неизвестном районе не выполняется |
| `contact = null` | `контакт` в `missing` | не значит, что клиент неизвестен системе: `client_id` может быть сопоставлен другим путём |
| справочник или retrieval недоступен | проверка не выполнена → контролируемый исход (правило 11 §7) | не значит «условие не выполнено» и не разрешает ответ по памяти модели |
| `type_confidence` ниже порога | локальный тип не подтверждён → LLM; если и после неё нет решения — оператор | не значит `спам` и не значит, что обращение неполное |

**Низкая уверенность классификации не разрешает автоматическое действие.** И обратно: отсутствие
адреса — это `missing`, а не причина искусственно занижать `type_confidence` всего обращения.
Уверенность относится только к шагу, который её выдал.

## 7. Таблица приоритетов маршрута (C06)

Правила проверяются сверху вниз. Применяется **первое**, чьё условие применимости выполнено и чей
триггер сработал. Правило, условие применимости которого не выполнено, **пропускается** — оно не
считается ни сработавшим, ни пройденным.

| № | Триггер | Применимо, когда | `route_decision` | `validation_outcome` | `status` | `route_reason` |
|---|---|---|---|---|---|---|
| 1 | спам | `req_type=спам` подтверждён классификатором или honeypot-признаком канала | `reject` | `спам` | `rejected` | `спам` |
| 2 | запрет действия guardrail | guardrail M6.10 заблокировал решение или инструмент | `эскалация` | `данных_нет` | `escalated` | `guardrail:<правило>` |
| 3 | жалоба | `req_type=жалоба` подтверждён | `эскалация` | `ок:не_заявка` | `escalated` | `жалоба` |
| 4 | тип не подтверждён | `req_type` или `priority` не подтверждены после LLM: невалидный/неоднозначный результат (M4.6) | `эскалация` | `данных_нет` | `escalated` | `тип_не_подтверждён` |
| 5 | вопрос | `req_type=вопрос` | `авто`, если ответ подтверждён источниками; иначе `эскалация` | `ок:не_заявка` / `данных_нет` | `done` после подтверждённого ответа / `escalated` | `ответ_по_источникам` / `ответ_не_подтверждён` |
| 6 | вне зоны | `req_type=заявка` **и** район известен **и** `service_zones.active = false` | `эскалация` | `правило_не_выполнено:вне_зоны` | `escalated` | `вне_зоны` |
| 7 | нет в прайсе | заявка **и** услуга распознана **и** в активном прайсе не найдена | `эскалация` | `данных_нет:нет_в_прайсе` | `escalated` | `нет_в_прайсе` |
| 8 | сумма выше порога | заявка **и** сумма подтверждена (§9) **и** `amount > 15000` | `эскалация` | `ок:сумма_выше_порога` | `escalated` | `сумма_выше_порога` |
| 9 | нужны сведения клиента | заявка; есть нехватка поля или устранимая клиентом неопределённость (район, услуга, объём); `round_count < MAX_CLARIFY_ROUNDS` и таймаут молчания не истёк | `уточнение` | `need_info` | `need_info` | `нет_поля:<поле>` или `уточнить:<причина>` |
| 10 | круги исчерпаны или молчание | заявка; сведения по правилу 9 всё ещё нужны; `round_count ≥ MAX_CLARIFY_ROUNDS` или истёк срок ожидания последнего вопроса | `эскалация` | `need_info` | `escalated` | `лимит_кругов` / `молчание` |
| 11 | обязательную проверку выполнить нельзя | заявка, поля собраны, но зона/прайс/сумма/регламент не проверяемы: справочник или retrieval недоступен, результат условия нельзя получить от клиента | `эскалация` | `данных_нет` | `escalated` | `проверка_недоступна:<что>` |
| 12 | иначе | заявка, все обязательные поля собраны, все применимые проверки пройдены | `авто` | `ок` | `done` только после подтверждённого действия (§10) | `ок` |

Для правил 9–10 `needs_clarification` объединяет отсутствующие поля и `clarification_reasons`
(например неизвестный район/объём/конфликт). `missing=[]` не означает, что все проверки выполнены.
Уже пришедший полный ответ проверяется до лимита: прежний последний вопрос не запрещает успешное
завершение. Таймаут применяется при `now >= last_question_at + timeout`, только если новой реплики нет.
Диалоговые причины `limit`/`silence` соответствуют `route_reason=лимит_кругов`/`молчание`;
`scope_change`, `context_limit`, `correlation_ambiguous` сохраняются как причины передачи оператору.

Пояснения, которые часто путают:

- Правило 6 стоит **выше** правила 9 намеренно: известный район вне зоны при отсутствующем телефоне
  даёт оператора, и последующий сбор телефона не разблокирует `авто`. Это ограничение по известному
  факту, а не нехватка данных.
- Правила 6, 7, 8 к `вопрос`/`жалоба`/`спам` неприменимы: зона, прайс и сумма — условия заявки.
  Поэтому правила 1, 3, 5 стоят выше них.
- Правило 4 (низкая уверенность) стоит выше проверок заявки: пока тип не подтверждён, ветка по типу
  не выбрана, и проверять условия заявки не на чем.
- Несколько триггеров сразу → применяется верхний; в `route_reason` пишется он, остальные
  сработавшие условия сохраняются в `validation_reason` (M5.9), чтобы оператор видел полную картину.

## 8. Порядок исполнения (C08)

**Текст для классификации продолжения.** Первое сообщение классифицируется по его тексту.
После уточнения M3 собирает `classification_text` из видимых реплик: исходная просьба и её
актуальные исправления, последний вопрос агента, новая реплика ровно один раз. Сериализация
отделяет роли/сообщения как данные; прежний `req_type`, gold и системные инструкции из истории
не добавляются. Используются отбор и лимит M3, без отдельного LLM-пересказа. При невозможности
сохранить необходимые реплики в бюджете действует `context_limit`, а не классификация обрывка.
`classify(text)` M4 получает эту строку; отдельное изменение сигнатуры не требуется.
«Адрес: Учебная 10» после просьбы заменить смеситель продолжает заявку; «Лучше скажите,
какая гарантия?» меняет намерение на вопрос. Один только последний ответ или неизменяемая
старая метка не дают корректной классификации. В M4 это проверяется на заданных текстах,
в M6 — на настоящем контексте M3 в T05/T14.

Фактический граф одного прогона:

```
приём и корреляция (S1)
  → нормализация входа (S2)
  → классификация типа и приоритета (S4)
  → ветка по req_type:
       спам    → reject (терминал)
       жалоба  → оператор (S10)
       вопрос  → поиск по базе знаний (S7 RAG) → ответ или оператор
       заявка  → извлечение полей (S5) → сопоставление клиента (S3)
               → достаточность (S6) и проверки известных условий (S7)
  → решение о маршруте (S8)
  → действие (S9) | уточнение клиенту (→ ожидание ответа) | оператор (S10)
```

Классификация выполняется до извлечения и уточнений. Спам и жалоба не проходят сбор полей заявки.
Номера S обозначают ответственность, а не хронологический порядок. Доверенный контекст доступа
передаётся сервером независимо от сопоставления контакта с клиентом.

Валидация выполняется только по **известным** условиям: неизвестное поле не проверяется, а
даёт `missing`/`clarification_reasons` для правил 9–10 либо недоступную проверку правила 11 (§7).

**Возврат из уточнения.** Ответ клиента приходит как новое входящее (S1) → корреляция M3.2 находит
открытое обращение по `thread_key` → `need_info → in_progress` → контекст обновляется (M3.3) →
**повторная классификация типа** (тип мог измениться, §5) → извлечение для заявки (M2.5) → повторная
проверка достаточности и валидация → новое решение о маршруте. Возврат — это новый прогон того же
обращения, а не продолжение прерванного шага.

**Зачем M2 и M3 строятся раньше классификатора.** Извлечение (M2) и цикл до-сбора (M3) —
самостоятельные компоненты: они работают на любом обращении и проверяются без M4. Пока M4 нет,
в изолированных сценариях явно задан тестовый тип `заявка`; это не правило обработки всех реальных входов. M4 добавляет развилку, M5 — проверку
условий, M6 — собирает это в граф с паузами и действиями. Ни один пункт M2/M3 не требует готового
классификатора, и ни один сценарий их приёмки не должен его требовать.

## 9. Сумма и порог (C07)

Три разные величины, которые нельзя смешивать:

| Величина | Откуда | Можно ли по ней принимать решение |
|---|---|---|
| цена услуги из справочника | `price.price` по подтверждённой услуге при `active=1` | источник доверенный, но для итоговой суммы нужны единица и объём |
| число в тексте клиента | `raw_text` («примерно тысяч двадцать») | нет — это пожелание/оценка клиента, не подтверждённая стоимость |
| подтверждённая стоимость `amount` | рассчитана из справочника по распознанной услуге (и объёму, если он известен) либо передана доверенной стороной | да |

**Порог: `amount > 15000` — строго.** `amount = 15000` порог **не** превышает и при прочих
пройденных проверках даёт `авто`. `amount = 15001` даёт правило 8. Порог — бизнес-константа, он
задан здесь и не «обосновывается экспериментом»; из конфига берётся значение, но менять его —
отдельное решение в `docs/decisions.md`.

**Если сумма неизвестна (`amount = null`)** — разбирается по причине, а не «авто по умолчанию»:

| Причина | Исход |
|---|---|
| услуга не распознана | правило 9: уточнение услуги (`missing` содержит `услуга`) |
| услуга распознана, в активном прайсе её нет | правило 7: `данных_нет:нет_в_прайсе` |
| справочник цен недоступен | правило 11: `проверка_недоступна:прайс` |
| услуга и объём подтверждены, цена и единица измерения известны | вычислить сумму с происхождением — правило 8 или 12 |
| цена за единицу известна, объём не указан | правило 9: уточнить объём; после лимита — правило 10 |
| стоимость требует подтверждения специалистом | правило 11: оператор; цена «от» не считается итоговой суммой |

Вычислять «скрытую» сумму по эталонной разметке запрещено: `_ground_truth.amount` — разметка
набора, а не вход сервиса. В сценариях `data/course_pack/inputs/validation.jsonl` сумма подаётся явно в
`input.state.amount` вместе с `amount_confirmed` — это доверенный вход теста, а не чтение эталона в рантайме.

## 10. Состояния и паузы (C09)

**Итог прогона ≠ завершение обращения.** Один прогон обработки заканчивается одним из результатов:
`завершён` (действие подтверждено), `ожидание_ответа`, `у_оператора`, `отклонено`, `ошибка`.
`need_info` и `escalated` — нормальные сохранённые результаты прогона, а не сбой и не «недоделанная
работа»: состояние графа сохранено чекпоинтером (M6.5), обработку можно продолжить.

Статусы и переходы:

```
new/in_progress → rejected  подтверждённый спам (M6 + правило 1)
new         → in_progress  принято в обработку
in_progress → need_info    не хватает обязательных полей (правило 9)
need_info   → in_progress  пришёл ответ клиента (S1 корреляция)
in_progress → escalated    решение «эскалация» (S8) или ошибка после ретраев (reason=error)
in_progress → done         актуальные проверки пройдены; все действия, включая ответ, подтверждены (S9)
escalated   → in_progress  confirm/edit/return: полномочия и версия проверены; далее повтор условий и маршрут
escalated   → rejected     оператор отклонил
need_info   → escalated    лимит/молчание, причина сохранена
new/in_progress/need_info → failed  неустранимая ошибка; терминальные записи не переписываются
```

| Статус | Значение | Вводится в |
|---|---|---|
| `new` | принято, ещё не в обработке | M1.7 (реализовано) |
| `in_progress` | в обработке | M3 |
| `need_info` | ждём ответа клиента на уточнение | M3.7 |
| `escalated` | у оператора (HITL), пауза | M3.7 (задел), M6.9 |
| `done` | действие выполнено и подтверждено | M6.8 |
| `rejected` | подтверждённый спам или отклонено оператором | M6.7 (`reject`), M6.9 (оператор); M4 только классифицирует |
| `failed` | неустранимая ошибка, терминал | M8 |

**`done` ставится только после подтверждённого действия.** `route_decision=авто` — это решение, а не
результат: пока `actions.status` не стал `done`, обращение остаётся `in_progress`. Сбой между
решением и действием оставляет обращение в `in_progress`, и возобновление доигрывает действие по
`actions.idem_key` без второй заявки.

**Терминальные статусы: `done`, `rejected`, `failed`.** Повторное событие в треде терминального
обращения не переоткрывает его произвольно: корреляция (M3.2) ищет **открытое** обращение
(`new`/`in_progress`/`need_info`/`escalated`) по доверенной идентичности; если такого нет — создаётся новое.
В `escalated` реплика сохраняется для оператора, но автоматическое действие не возобновляется.
Несколько кандидатов — отдельное обращение с `escalated`, причиной `correlation_ambiguous`; старые не меняются.
`escalated` — не терминал: это пауза, из неё обращение выводит только решение оператора.

## 11. Идентификаторы (C10)

Разные сущности имеют отдельные идентификаторы. Отдельный сервис для каждого не нужен — нужны
разные ключи в существующих таблицах.

| Идентификатор | Что идентифицирует | Где живёт | Форма | Статус |
|---|---|---|---|---|
| `request_id` (`requests.id`) | обращение | `requests` | `REQ-YYYY-NNNN` из последовательности `request_seq` | **реализовано** (`app/db/repositories/request_repo.py`) |
| `thread_key` | диалоговый тред канала | `requests.thread_key`, индекс | `channel:(client_contact\|anon)` в каркасе; в M3 доверенная идентичность диалога | **текущий каркас**, общий `anon` не разрешает корреляцию M3 |
| `idem_key` | входное событие (одна доставка одного сообщения на приёме) | `requests.idem_key`, unique | `channel:message_id`, иначе `channel:hash:<sha256(channel\|contact\|нормализованный текст\|дата)>` | **реализовано**; суточный date-bucket в хеше помечен в коде как решение, требующее записи в `docs/decisions.md` |
| `RequestCreate.message_id` | идентификатор сообщения во внешней системе (письмо, реплика мессенджера) | вход API | строка внешней системы | **реализовано** (`app/schemas/request.py`) |
| `messages.id` / `external_msg_id` | сохранённая реплика диалога | `messages` (M3.1) | PK / внешний id | будущая схема (M3) |
| `send_idem_key` | исходящая отправка | `messages.send_idem_key`, unique для `out` | `request_id + round + kind` для clarify; `request_id + kind + action_id` для ответов M6 | будущая схема (M3.8/M6.8) |
| `run_id` / связанный `trace_id` | один запуск обработки обращения | событие обработки; `llm_calls.run_id` добавляется в M6; визуализация M9.1 | id прогона | локальный ID запуска допустим в M2/M3; сохраняется в M6, визуализируется M9 |
| checkpoint `thread_id` | точка возобновления графа | `agent_checkpoints` (M6.5) | равен `request_id` | будущая схема (M6) |
| `call_id` (`llm_calls.id`, также называемый `llm_call_id` в описании) | фактический вызов модели | `llm_calls` (M2.8) | uuid, генерируется приложением до отправки провайдеру; запись идемпотентна по нему; уникального ключа `(request_id, step)` у журнала нет — два оплаченных вызова шага дают две строки | будущая схема (M2) |
| `actions.idem_key` | бизнес-действие | `actions`, unique | ticket: `request_id:create_ticket`; слот: `ticket_id:schedule_slot`; ответ: `request_id:kind:action_id` | будущая схема (M6.8) |
| `event_id` | логическое событие обработки | сообщение очереди и `processed_messages` (M8.2) | стабильный ID производителя, сохраняется при повторной публикации | будущая схема (M3/M6/M8) |
| `broker_msg_id` / delivery tag | конкретная доставка транспорта | диагностика очереди | технический ID; не бизнес-ключ дедупликации | M8 |

До выдачи случайного `action_id` логическое намерение резервируется с уникальностью
`(request_id, action_type, logical_intent)` по M6.8. Иначе два повтора получат разные UUID
и unique по ключу ответа не предотвратит дубль. Идентичность ticket/слота/ответа различается.

Что из этого следует:

- **Новая реплика клиента в прежнем обращении — новое событие.** Новый `idem_key`, новая запись
  `messages(in)`, но **тот же** `request_id` и `thread_key`. Для `new/in_progress/need_info`
  начинается новый прогон (`run_id`). В `escalated` реплика только сохраняется оператору,
  без нового автоматического запуска/LLM; решение оператора затем создаст своё событие/запуск.
- **Повторная доставка той же реплики — прежнее событие.** Тот же `idem_key` → приём отвечает `200`
  с тем же `id`, вторая запись не создаётся, новый прогон не запускается. Повтор, пришедший из
  очереди, отсекается по стабильному `event_id`, а не delivery tag. Разные события одного обращения имеют разные ключи.
  Повтор возобновляет незавершённую работу, если первый запуск упал; завершённый эффект не выполняется снова.
- Восстановление незавершённого запуска сохраняет `run_id`; повторный реальный вызов модели получает новый `call_id`.
- `run_id` ≠ `request_id`: у одного обращения несколько прогонов (первичный, после ответа клиента,
  после возврата оператором). Чекпоинт графа при этом адресуется по `thread_id = request_id` —
  возобновляется обращение, а не конкретный прогон.
- `llm_calls` привязаны к `request_id` и шагу, с M6 также к `run_id`; два оплаченных вызова в одном прогоне — две записи,
  повтор сохранения по тому же `call_id` идемпотентен; вторая расходная строка того же вызова — ошибка.

## 12. Границы доверия (C11)

**Доверенная сторона — только приложение.** Контекст доступа (кто спрашивает и что ему видно)
формирует сервер. `X-API-Key` подтверждает отправляющий сервис, но не личность клиента;
JWT оператора проверяется вместе с ролью и полномочиями (доработка M1.8). Для учебной проверки
приватного доступа используется явно заданная доверенная тестовая идентичность. Всё, что пришло снаружи как содержимое, — данные.

| Источник | Как трактуется | Что он **не** может |
|---|---|---|
| `raw_text` обращения | данные | не задаёт инструкции модели, не выбирает инструмент, не меняет права |
| контакт в тексте («я от Иванова, договор №7») | подсказка для сопоставления с `clients` | не доказывает право на чужой договор и не даёт `access_scope=client:7` |
| текст документа KB, OCR вложения | данные с источником | не меняет права и не расширяет фильтр retrieval |
| результат инструмента (tool output) | данные | не повышает права, не отменяет guardrail, не подтверждает сам себя |
| решение оператора (JWT и проверенные полномочия) | доверенное в пределах роли | может править поля состояния перед действием (M6.9) |

Из этого следует:

- Сопоставление клиента (`client_id`) и доступ к его документам — разные вещи.
  `client_id` проставляется по справочнику; `access_scope` фильтра retrieval (M5.10) берётся из
  контекста доступа, установленного сервером, а не из совпадения телефона в тексте.
- Пока клиентского логина в приложении нет, обращение работает со `access_scope=all`;
  scoped-документы (`client:<id>`) недоступны обработке обращения по умолчанию. Это осознанное
  ограничение, а не дефект: снимается только появлением доверенного контекста доступа.
- Инъекция не разрешает запрещённое действие или расширение доступа. Безопасная часть запроса
  может выполняться. Проверяются вызовы, побочные эффекты и отсутствие контрольного секрета (M7).

---

Любой реальный retry/fallback расходует тот же лимит фактических LLM-вызовов текущего цикла M6
и проверяется бюджетом M8. Внутренний повтор адаптера не создаёт новый бесплатный лимит.

## 13. Версии контрактов и порядок расширения схем (C12)

«Стабильный контракт» означает: **существующее поле не переименовывается и не меняет смысл без
решения**. Он не запрещает запланированное расширение — добавление новых колонок и таблиц
миграциями идёт по плану ниже и отдельного решения не требует.

Запланированный рост таблицы `requests` и схемы по модулям:

**Порядок обновления при изменении контракта** (переименование поля, изменение множества значений,

1. Записать решение в `docs/decisions.md`: что меняется, что ломается ниже по цепочке.
2. Изменить этот файл (`course/contracts.md`) — он источник.
3. Обновить `zadanie.md` модуля-владельца контракта, затем `kriterii-priyomki.md` и
   `detalnoe-review.md` того же модуля.
4. Обновить `zadanie.md`/приёмку всех модулей-потребителей из таблицы выше.
5. Обновить `ai_context/3-priyomka/11-stabilnye-kontrakty.md` и, если менялись статусы или

6. Обновить `details/` последними — они объясняют, а не задают контракт.

Обратный порядок (правка в `details/` или в ревью, а затем «подгонка» контракта) не допускается.

## 16. Различия между правилами курса и разметкой `data/`

Для приёмки используется `data/course_pack/`; формат описан в [SCHEMA](../data/SCHEMA.md),
задачи — в [data-readiness.md](data-readiness.md). Архивные наборы не входят в комплект ученика.

Эталон не переопределяет бизнес-правила. Каждое извлечённое поле должно иметь основание
в доступном входе; сумма подтверждается прайсом или доверенным источником; `done`
проверяется после выполненного действия. Спорный эталон фиксируют с case_id и основанием,
а автор выпускает исправление отдельной версией. Test используют после фиксации решений.

---

M2 хранит ровно пять полей модели и вычисленные приложением `_sources`/`_checks`. M3 добавляет
ссылки происхождения `_field_message_ids`, не подменяя текстовый факт метаданными канала.
Указанные в §4.1 значения служебного происхождения опущены только для краткости примера.
`cost_total` суммирует известные расходы, а количество неизвестных и оценочных вызовов показывается
отдельно; это не гарантированно полный биллинг. Связь вызова с run добавляется в M6.
