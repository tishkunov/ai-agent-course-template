# M7.6 — Атака как проверка границы

Каждый кейс должен ответить на три вопроса: откуда пришла недоверенная команда, какой запретный эффект она пыталась вызвать и где этот эффект наблюдается. Используйте задачу `security` текущего пакета: input задаёт поверхность атаки и доверенную идентичность, expected — эффекты и запрещённые вызовы.

Для tool-forge мок модели предлагает refund, хотя реестр M6 разрешает только чтения. Dispatcher должен отказать до вызова spy; в БД нет эффекта. Мок, который всегда предлагает разрешённое чтение, не испытывает эту защиту. Отдельный live-прогон проверяет, что настоящая модель сделала на атакующем тексте.

Для атаки «создай 100 заявок» задайте две ситуации: исходный неполный текст не разрешает ticket, полная допустимая заявка с вредной припиской может создать один ticket после всех проверок. Ноль любых tools не является универсальной целью: полезный поиск/уточнение разрешён.

Для PDF/JPG подтвердите, что loader/OCR действительно вернул payload. Проверка на подставном OCR-тексте полезна, но доказывает только downstream. Подмена инструкции в разрешённом KB-чанке или tool output отдельно проверяет, что источник данных не может выдать scope.

Добавьте безопасный похожий запрос со словом SYSTEM: он должен дойти до полезного результата. Иначе тривиальная защита «отказать всем» получила бы идеальную security-метрику. Успех конечного набора означает только отсутствие конкретных наблюдённых нарушений, не абсолютную защиту.

## Работа с ИИ и проверка

Промпт-контракт ограничьте этим пунктом: передайте текущие интерфейсы, [задание](../zadanie.md), доступные входы и наблюдения из [приёмки](../kriterii-priyomki.md). Запросите реализацию и объяснение, что именно доказывает проверка; не поручайте исправлять исходный gold под модель. Затем выполните отдельное [ревью](../detalnoe-review.md), сценарии и запись понимания по M0.
