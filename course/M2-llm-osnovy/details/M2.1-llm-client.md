# M2.1 — LLM-клиент и провайдер за конфигом

## Что это и зачем

Каждый SDK вызывается по-своему: разные имена методов, разный формат сообщений, разные поля в
ответе. Если размазать эти вызовы по сервисам, то «попробовать другую модель» или «начать считать
расходы» превращается в правку двадцати мест. `LLMClient` — это одна дверь: весь код проекта
вызывает `client.complete(...)`, а внутри клиент разговаривает с конкретным провайдером.

Это фундамент модуля: клиент из M2.1 используют M3 (сборка контекста), M4 (LLM-baseline
классификации), M5 (ответ по источникам), M6 (узлы графа), M7 (судья), M8 (цепочка переключения
моделей внутри клиента). Сигнатуру `complete` после этого пункта не меняют — порядок изменения
контракта описан в §13 `../../contracts.md`.

## Теория простым языком

**Адаптер (adapter pattern)** — класс, который приводит чужой интерфейс к твоему. Каждый адаптер
реализует один метод «выполни запрос и верни `LLMResult`», внутри переводя в формат своего SDK и
обратно.

**Сколько адаптеров нужно.** Для сдачи M2 — один адаптер реального провайдера плюс тестовый
(мок-)адаптер, который возвращает заранее заданный ответ без сети. Этого достаточно, чтобы
доказать сменяемость: переключение идёт конфигом, вызывающий код не меняется. Второй *реальный*
провайдер и переключение на запасную модель при сбое — это задание M8.5, а не M2.

**`LLMResult` как контракт.** Наружу клиент всегда отдаёт один и тот же объект, независимо от
провайдера. Важно, чтобы режим результата был однозначным:

| Что передали в вызов | Что смотрим в результате | Что остаётся `None`/пустым |
|---|---|---|
| ничего особенного | `text` | `structured`, `tool_calls` |
| `schema=...` | `structured` (словарь по схеме) | `text`; сырой ответ остаётся только в `raw` |
| `tools=[...]` | `tool_calls` — список предложенных вызовов | `structured`; при отсутствии вызова допустим `text` |

Одновременно `schema` и `tools` в M2 не передаются: клиент отклоняет такую комбинацию до сети.

**Клиент не знает про промпты.** Версия инструкции (`extract_v1`) — свойство шага, который собрал
сообщения, а не свойство вызова модели. Поэтому `prompt_version` в `LLMResult` нет: версию знает
вызывающий код и он же передаёт её в запись журнала (M2.8). Иначе получается странное: клиент
должен угадывать, из какого файла пришёл текст, который ему дали.

**Где живёт usage.** Провайдер возвращает счётчики токенов в ответе; клиент кладёт их в
`tokens_in`/`tokens_out` (и сырой ответ — в `raw`). Долговременно usage хранится не в результате
вызова, а в строке `llm_calls` (M2.8) — результат живёт секунды, журнал живёт всегда.

**Типизированная ошибка.** Сеть отвалилась, провайдер вернул 500, вышел таймаут, ключ неверен — всё
это клиент ловит и поднимает как `LLMError` с полем причины. Сервис ловит `LLMError` и решает, что
отдать наружу (обычно 502), но не показывает клиенту стек и внутренности SDK.

**Про `stream`.** Параметр есть в сигнатуре, потому что сигнатура зафиксирована для всех модулей.
Реализации потокового режима в курсе нет (§2 `../../contracts.md`): результат всегда собирается
целиком и проверяется схемой. Если адаптер потоковый режим не умеет — он обязан сказать об этом
ошибкой, а не принять параметр и молча его проигнорировать.

## Что сделать по шагам

1. `core/llm/base.py` — протокол `LLMClient` с методом `complete(...)` и схема `LLMResult`.
2. Адаптер реального провайдера + мок-адаптер для тестов.
3. `core/llm/factory.py` — по `Settings.LLM_PROVIDER` собрать нужный адаптер; кешируемый
   `get_llm_client()`, раздаваемый через `Depends`.
4. Поля в `Settings`: `LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_TIMEOUT`.
   Сейчас в `app/core/config.py` их нет — добавляются здесь, по правилам M1.1 (обязательные — без
   умолчаний).
5. `LLMError` в `core/llm/errors.py` с причиной (`timeout` | `provider_error` | `auth` |
   `unsupported` | `context_limit` | `invalid_output`); обернуть вызовы SDK. Ошибка `invalid_output`
   сохраняет доступные usage и сырой ответ для журнала; иначе неверный JSON станет «бесплатным».
   Автоматические сетевые ретраи SDK в M2 отключены; единственный повтор формата делает шаг извлечения.
6. Тесты: мок возвращает фиксированный `LLMResult`; таймаут и ошибка провайдера → `LLMError`;
   `stream=True` → `LLMError(unsupported)`.

## Промпт-контракт к ИИ

Скоуп — только M2.1. Дать: сигнатуру `complete` и поля `LLMResult` дословно, список полей
`Settings`, требование одного экземпляра клиента и `LLMError`. Запросить: протокол, один реальный
адаптер, мок-адаптер, фабрику, ошибки. Запретить: вызывать SDK провайдера где-либо кроме адаптера,
менять сигнатуру `complete`, добавлять `prompt_version` в `LLMResult`, реализовывать переключение
между моделями при сбое (это M8.5).

## Частые ошибки

- SDK-объект провайдера «протекает» наружу в `raw`, и код начинает на него завязываться.
- Клиент пересоздаётся в каждом хендлере — на каждый запрос новое соединение и новая конфигурация.
- Ошибка провайдера уходит наружу как 500 со стеком; ключ попадает в лог.
- `structured` и `text` заполняются оба «на всякий случай» — потребитель не знает, чему верить.
- `stream=True` принят и проигнорирован: позже кто-то решит, что потоковый режим работает.
