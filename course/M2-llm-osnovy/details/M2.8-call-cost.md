# M2.8 — Журнал вызовов и расходы

## Что это и зачем

«Сколько стоит обработать одно обращение» — ключевая цифра проекта, и считать её надо с первого же
вызова модели, а не прикручивать в M9. Каждый фактический вызов пишется строкой в `llm_calls`, а на
обращении держится агрегат `cost_total`.

## Теория простым языком

**Учётная единица — вызов, а не шаг.** Это главное отличие журнала от «таблицы стоимости шага».
Один шаг извлечения может стоить один вызов, а может два: первый ответ не прошёл схему, повтор
формата прошёл. Оба вызова оплачены провайдером — значит, обе строки должны быть в журнале.
Если ключом записи сделать «обращение + шаг», вторая строка бесшумно затрёт первую, и счёт
окажется вдвое меньше реального.

**`call_id` создаётся до вызова.** Приложение генерирует идентификатор (uuid), потом зовёт модель,
потом пишет строку с этим идентификатором. Порядок важен: если вызов прошёл, а запись сорвалась,
повторная попытка записи знает, про какой именно вызов она пишет, и не создаёт дубль. Это и есть
идемпотентность журнала — **по `call_id`**, а не по шагу.

**Два разных «повтора».** Их постоянно путают:

| Событие | Что происходит | Что с расходами |
|---|---|---|
| повторный вызов модели (второй запуск extract, повтор формата) | модель отработала ещё раз | новая строка, сумма растёт |
| повторная запись одного и того же вызова | строка уже есть | ничего не меняется |

Ни идемпотентность приёма входящего события (`idem_key`, M1.7), ни кеш ответов (M8.6) журнал не
подменяют: первая про доставку сообщения, второй про то, чтобы вызова не было вовсе. Если вызов
состоялся — он в журнале.

**Агрегат считается из журнала.** `requests.cost_total` = сумма известных `cost` строк этого обращения.
Если есть неизвестные строки, это только известная часть расходов; отчёт показывает их число
рядом с суммой. Оценённые значения также помечаются; сумма не выдаётся за точный счёт провайдера.
Пересчёт из журнала, а не `cost_total += cost`: слепой инкремент невозможно проверить и невозможно
починить после сбоя.

**Три состояния стоимости, а не два.** Здесь работает то же правило, что в §6 `../../contracts.md`
про проверки: «неизвестно» — это не «ноль».

| Что вернул провайдер | `tokens_in/out` | `cost` | `estimated` |
|---|---|---|---|
| usage есть и покрывает применённый тариф | из ответа | по таблице цен | `false` |
| usage нет, но ответ есть | посчитаны токенизатором (M2.2) | по таблице цен | `true` |
| ответа нет (сбой, таймаут) | `null` | `null` + заполнен `error` | `true` |

Строка с `cost = null` не складывается как ноль: в отчёте она показывается как «стоимость
неизвестна». Написать `0` — значит утверждать, что вызов был бесплатным, а это неправда. Точный
биллинг провайдера при недоступных данных не требуется; требуется не выдавать прикидку за факт.

**Зачем в строке модель и версия промпта.** Через два месяца вопрос будет звучать так: «после какой
версии промпта расход на обращение вырос в полтора раза». Ответить на него можно только если
`model` и `prompt_version` лежат рядом с ценой.

## Разобранный пример

Числа иллюстративные — это проверка арифметики, а не тариф провайдера.

```
вызов A, call_id=a, cost=0,01   → строк 1, cost_total = 0,01
вызов B, call_id=b, cost=0,02   → строк 2, cost_total = 0,03
повторная запись A (call_id=a)  → строк 2, cost_total = 0,03
```

## Что сделать по шагам

1. Функция `record_llm_call(request_id, step, attempt, call_id, prompt_version, llm_result | error)`:
   - взять `tokens_in/out` из результата или посчитать токенизатором с `estimated=true`;
   - `cost = pricing.cost(...)` или `None`, если считать нечего;
   - вставить строку `llm_calls` так, чтобы повтор по тому же `call_id` не создавал вторую;
   - сериализовать записи одного обращения (например, блокировкой его строки перед вставкой)
     и пересчитать `requests.cost_total` из журнала в той же транзакции; блокировку не держать
     во время сетевого вызова.
2. Вызывать её после каждого фактического вызова модели, включая неудачный по формату и сорвавшийся.
3. Тесты: один вызов → одна строка; два вызова → сумма; повторная запись → без изменений; нет
   usage → `estimated=true`; сбой без ответа → `cost = null` и `error`.

## Промпт-контракт к ИИ

Скоуп — только M2.8. Дать: поля `llm_calls`, правило идемпотентности по `call_id`, три состояния
стоимости, правило пересчёта `cost_total`. Запросить: `record_llm_call`, пересчёт агрегата, тесты.
Запретить: уникальный ключ `(request_id, step)`, слепой инкремент `cost_total`, `float` для денег,
запись `cost = 0` при неизвестном usage.

## Частые ошибки

- Upsert по `(request_id, step)` — второй оплаченный вызов исчезает из счёта.
- `cost_total += cost` — расходится с журналом после первого же сбоя.
- Неудачная попытка формата не записана: ошибка выглядит бесплатной.
- `cost = 0` вместо `null` при отсутствии usage.
- `float` вместо `Decimal`.
- Строка пишется до вызова, «чтобы не забыть» — в журнале оказываются вызовы, которых не было.
