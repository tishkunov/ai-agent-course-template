# M2.7 — Эндпоинт извлечения (склейка)

## Что это и зачем

Здесь всё собирается: `POST /requests/{id}/extract` берёт сохранённое обращение, гонит `raw_text`
через клиента со структурированным ответом, кладёт результат в `extracted_fields` /
`missing_fields`, ставит флаг `extracted`, пишет каждый вызов в журнал. Это первый шаг пайплайна,
работающий на реальной записи в БД.

## Теория простым языком

**Отдельный шаг, а не часть приёма.** Приём (M1.7) быстрый и синхронный — он не должен ждать
модель, иначе канал приёма падает вместе с провайдером. Извлечение — отдельный вызов, который можно
запустить позже, повторить, вынести в воркер (M8.2). Поэтому это `POST /{id}/extract`, а не часть
`POST /requests`.

**Только `raw_text`.** В M2 у шага один вход — текст самого обращения. История переписки, сводка
треда и ответы клиента на уточнения появятся в M3 (M3.3 контекст, M3.5 переизвлечение). Не стоит
«на будущее» подмешивать сюда предыдущие реплики: до M3 их просто нет в схеме, а логика выбора,
что именно подмешивать, — содержание того модуля.

**Повторный extract — это новая работа.** Переизвлечь после смены промпта, доиграть после сбоя,
перезапустить руками — нормальные сценарии. Каждый такой запуск может снова позвать модель, и тогда
это новый фактический вызов: новая строка в журнале, `cost_total` растёт (M2.8). Успешный результат
**заменяет** актуальные поля обращения.

Называть такой повтор «идемпотентным» неверно. Идемпотентность в проекте есть, но про другое:

| Механизм | Что гарантирует | Где |
|---|---|---|
| `idem_key` на приёме | повторная доставка одного сообщения не создаёт второе обращение | M1.7 |
| `call_id` в журнале | повторная запись одного вызова не задваивает расход | M2.8 |
| кеш ответов | одинаковый запрос может не дойти до модели вовсе | M8.6 |
| `actions.idem_key` | действие выполняется один раз | M6.8 |

Ни один из них не означает «повторный платный вызов бесплатен».

**Статус не трогаем.** В M2 обращение не двигается по машине состояний — маршрут появится в M6.
Единственное изменение, кроме полей извлечения, — флаг `extracted = true`.

**Сбой не должен стоить данных.** Типичная реализация «обнулить поля → вызвать модель → записать
результат» теряет данные на каждом сбое: было извлечено нормально, стало пусто. Правильный порядок —
проверить обращение, вызвать модель, и только при успехе записать поля. При `LLMError` прежние
значения остаются, а расход, если usage пришёл, уже записан в журнал.

**404 не должен стоить денег.** Проверка существования обращения — до вызова модели. Это же
относится к проверке прав: без токена оператора вызова быть не должно.

## Что сделать по шагам

1. Роут `POST /requests/{id}/extract` с `require_operator` (JWT из M1.8); приём остаётся под
   API-ключом.
2. Сервис `extract(request_id)`:
   1. загрузить обращение, нет → 404;
   2. собрать сообщения (M2.3), вызвать клиента со `schema=ExtractedFields` (M2.5);
   3. на каждый фактический вызов — строка журнала (M2.8), включая неудачную попытку формата;
   4. при успехе записать `extracted_fields`, `missing_fields`, `extracted = true`;
   5. пересчитать `cost_total`.
3. Ответ `200 {extracted_fields, missing_fields, cost_total}`.
4. `LLMError` или `ExtractionError` → 502; прежние поля и статус не меняются. Расходы
   фиксируются отдельно от откатываемого сохранения результата. При ошибке записи БД точный
   биллинг не гарантируется; это ошибка хранения, а не бесплатный вызов.
5. Тесты — сценарии из `kriterii-priyomki.md` § M2.7.

## Промпт-контракт к ИИ

Скоуп — только M2.7. Дать: контракт эндпоинта (200/401/403/404/502), правило «повтор — новая работа,
новый вызов учитывается», «статус не меняем», «404, 401 и 403 до вызова модели». Запросить: роут,
сервис, обработку ошибок, тесты. Запретить: менять `status` обращения, затирать прежние поля при
ошибке, объединять записи журнала по `(request_id, step)`, подмешивать историю диалога.

## Частые ошибки

- Повтор extract «дедуплицируется» по шагу — второй оплаченный вызов исчезает из счёта.
- `LLMError` уходит как 500, обращение помечается битым, поля затираются пустыми.
- Извлечение впихнуто в `POST /requests` — приём стал медленным и зависит от провайдера.
- Модель вызывается до проверки существования обращения — 404 стоит денег.
- Меняется `status` «заодно» — M6 потом получает обращение в неожиданном состоянии.
