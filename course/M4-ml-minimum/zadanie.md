# M4 — Прикладная классификация · Задание

**Проблема.** До проверки условий нужно различить просьбу о работе, вопрос, жалобу и рекламу. Похожие слова не гарантируют одинаковый тип. Определим тип и приоритет локально по примерам и явным правилам; если оснований мало, передадим классификацию LLM. Долю локальных решений, скорость, расходы и ошибки измеряем, заранее их не обещаем.

**Что уже работает.** M1 сохраняет обращения; M2 предоставляет `LLMClient` и журнал фактических вызовов. M4 проверяется самостоятельным запуском без графа M6. В итоговом графе классификация S4 идёт **до** извлечения S5; поля заявки извлекаются только в ветке заявки. Общие правила — [contracts.md](../contracts.md), особенно §4–§8 и §16.

**Маршрут работы.** M4.1 (с пояснением M4.2) → M4.3 → M4.6. M4.4 и M4.5 сохраняют старые ссылки, самостоятельных заданий нет. Обучение модели, поиск архитектуры, подбор embedding-моделей, кластеризация и регрессия не входят. Процесс M0, отдельное ревью и записи понимания сохраняются.

## 0. Данные и правила разметки

В `data/course_pack/eval/classification_train.jsonl`, `classification_dev.jsonl` и `classification_test.jsonl` строка содержит `id`, `input`, `type`, `priority`. В классификатор поступает только доступный текст `input`, без ID, метки, скрытой суммы или `_ground_truth`. Поле эталона `type` соответствует `req_type`; `category` обозначает услугу и здесь не предсказывается. Значения полей — [contracts.md §14](../contracts.md#14-значения-enum-полей).

| Тип | Правило и пример |
|---|---|
| `заявка` | Просит выполнить работу: «Нужен мастер починить розетку» |
| `вопрос` | Просит сведения, не заказывает работу: «Какая гарантия на ремонт?» |
| `жалоба` | Недовольство выполнением/качеством: «После вашего ремонта розетка опять искрит» |
| `спам` | Посторонняя массовая реклама: «Купите базу телефонов со скидкой» |

Приоритет — отдельное явное правило. Проверять смысл, отрицания и контекст, а не наличие одного слова. Правила применяются сверху вниз к **текущему состоянию**:

| Приоритет | Наблюдаемый признак |
|---|---|
| `срочный` | Действующая авария/опасность: «Розетка искрит сейчас», «Вода заливает квартиру» |
| `высокий` | Без признака аварии явно требуется быстрое восстановление существенной функции: «Нет электричества во всей квартире, нужен мастер сегодня» |
| `низкий` | Спокойный информационный вопрос, реклама или явно отложенная работа: «Какая гарантия?», «Через месяц планирую заменить кран» |
| `средний` | Обычная заявка или жалоба без признаков выше |

Если правило нельзя применить однозначно, вернуть отсутствие решения и вызвать LLM. «Срочно скажите срок гарантии» не описывает аварию. «Вчера искрило, сейчас всё спокойно, нужен осмотр» требует анализа контекста; одно ключевое слово не назначает `срочный`. «После ремонта снова течёт, пришлите мастера» может смешивать жалобу и новую заявку: LLM получает инструкцию учитывать претензию к прошлой работе; если двусмысленность осталась, результат неподтверждён и M6 передаст его оператору. Приоритет не вычисляется из суммы и не меняет бизнес-маршрут.

**Три выборки.** Train — только база соседей и источник большинства; dev — выбор порога и промпта;
test — одно итоговое сравнение после фиксации решений. Общий manifest с family_id и разбиением
для всех модулей поставляет автор по [правилам данных](../data-readiness.md). Студент проверяет
пересечения и использует готовый split, а не восстанавливает семейства из испорченного корпуса.
Используйте `data/course_pack/`: 160 примеров, по 40 каждого типа. Разбиение по смысловым
семействам: train — 95, dev — 31, test — 34. Близкие переформулировки остаются вместе;
число строк каждого типа внутри split нужно показать в отчёте, квоты между splits не выравниваются
ценой разрыва семейства. Dev предназначен для настройки, test — для финального эксперимента A5.
Эталоны проверены ассистентом и автоматическими проверками; независимое review не заявляется.

Новый test мал и синтетичен: показывать n/N и support, не выводить из него качество реального потока.

## M4.1 — Векторы и ближайшие примеры

**Проблема.** Совпадение слов плохо отражает смысл; смысловая близость тоже может перепутать намерение.

**Что уже работает.** Есть тексты и правила разметки §0.

**Что сделать.**

1. Использовать фиксированную модель `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, revision `e8f8c211226b894fcb81acc59f3b34ba3efd5f42`, CPU, размерность 384, лимит модели 128 токенов. Имя и revision — конфиг. Обоснование и официальные источники — [M4.2](details/M4.2-embedding-model-choice.md).
2. Реализовать пакетное `embed(texts) -> vectors`, L2-нормализацию и cosine. На единичных векторах cosine равен скалярному произведению.
3. Реализовать поиск `k=3` ближайших train-примеров. Равную близость упорядочивать по стабильному ID. Сохранить матрицу, метки и manifest модели/данных, чтобы повторить поиск без повторного вычисления базы.
4. Показать соседей для нескольких обращений, в том числе тематически близких жалобы и заявки. Зафиксировать выбор модели и конфигурацию в записи M0.

**Пример входа и результата.** «Нужен ремонт розетки» и «После вашего ремонта розетка не работает» могут оказаться близко, но ожидаемые типы — заявка и жалоба. Показывается измеренный cosine, не выдуманное заранее число.

**Контракт.** `embed` возвращает конечную матрицу `(n, 384)`; `nearest` — ID, близость, метку из train. База содержит только train, никогда dev/test.

**Краевые случаи.** Пустой список → `(0, 384)`; пустой текст не превращается в нулевой «нормальный» вектор: контролируемый отказ классификации. Текст свыше лимита усекается токенизатором с признаком усечения; локальное решение по такому тексту не принимается, LLM получает полный вход в пределах лимита M2. Если он не помещается и туда — неподтверждённый результат. Нулевая норма/NaN, отсутствие модели или несовместимая версия базы → явная причина, без случайного соседа; возможен переход к LLM.

**Проверка.** Сценарии A1–A2 в [приёмке](kriterii-priyomki.md).

## M4.3 — Локальный способ и сравнение с LLM

**Проблема.** Общая тема и большинство класса могут скрывать ошибки на жалобах и спаме.

**Что уже работает.** M4.1 возвращает соседей; M2 делает проверенный вызов модели и учитывает расходы.

**Что сделать.**

1. На трёх ближайших примерах голосовать за тип. Доля голосов победителя — `type_confidence`, эвристика согласованности, **не вероятность правильности**. При равенстве голосов не принимать решение; при менее трёх примерах или отсутствии одного из четырёх типов в базе переходить к LLM, фиксируя ограничение базы.
2. Приоритет определить правилами §0 независимо от соседей. Неоднозначный приоритет также требует LLM, даже если все соседи согласны о типе.
3. Стартовый `CLASSIFY_CONFIDENCE_MIN=0.8`: при `k=3` локально проходит 3/3, а 2/3 отправляется к LLM. На dev сравнить с `2/3`, показать изменение числа вызовов и ошибок, затем зафиксировать один порог до test. Большее значение увеличивает число LLM-вызовов. Это техническая эвристика, не бизнес-константа и не обещание точности.
4. Через M2 выполнить LLM-классификацию с правилами §0 и строгой схемой: `req_type`, `priority` — известная метка или `null`, `reason` — короткое основание/неоднозначность. Лишние поля и неизвестные значения отвергаются. Модель не вызывает инструменты. Инструкция лежит артефактом `prompts/classify_v1.md` по правилу M2.3 (`prompts/<step>_v<N>`), в коде строк промпта нет; ID примера, метка и `_ground_truth` в промпт не попадают. Каждый фактический вызов пишется в журнал `llm_calls` (M2.8) со `step="classify"`, номером `attempt`, `model` и `prompt_version`. Использовать один ограниченный повтор ошибки формата по M2: повтор даёт вторую строку журнала, а не правку первой. Неоднозначность не лечится бесконечными повторами.
5. На одном test сравнить три способа ниже. Большинство определять **на train**, отдельно по типу и приоритету; при равенстве использовать заранее зафиксированный порядок меток. Локальный способ в таблице — без LLM; отказы не удалять, показывать отдельно и учитывать как несовпадение при общей accuracy. Реальный LLM прогнать на том же входе, без эталонов и тестовых примеров в промпте.
6. Разобрать три конкретные ошибки: текст, эталон, прогноз, соседи/основание, причина. Ошибки типа и приоритета считать отдельно. Если расхождение вызвано недостоверной меткой, сохранить его и объяснить; не менять test ради улучшения цифр.

| Способ | Ошибки типа n/N; accuracy | F1 и support по каждому типу | Ошибки приоритета n/N | Отказы n/N | Время: всего и мс/вход | Фактические LLM-вызовы | Стоимость |
|---|---|---|---|---|---|---|---|
| Большинство train | … | … | … | … | … | 0 | 0 API |
| Соседи + правило приоритета | … | … | … | … | … | 0 | 0 API |
| LLM через M2 | … | … | … | … | … | … | … |

Показывать `n/N` вместе с процентами, количество примеров каждого приоритета, версию входа и спорных меток. Время локального поиска измерять вместе с embedding входа; создание базы и загрузку модели показывать отдельно. «0 API» не означает отсутствие расходов CPU. Для LLM фиксировать модель, промпт, usage/тариф и неизвестную либо оценочную стоимость; не заменять её нулём. Низкая температура не гарантирует одинаковый ответ при каждом запуске. Превосходство над большинством не является обязательным результатом.

**Пример входа и результата.** Для контролируемых соседей `[заявка, заявка, жалоба]` доля `2/3`, при пороге `0.8` нужен LLM. Для `[заявка, заявка, заявка]` и «Искрит розетка, нужен электрик» правила дают `срочный`; это не требует наличия адреса.

**Контракт.** Локальный результат содержит кандидат типа, долю голосов, решение правила приоритета, ID соседей и причину отказа. Артефакт — база векторов с метками и manifest, а не обученная нейросеть.

**Краевые случаи.** Три похожих примера могут ошибаться одинаково: согласие 3/3 не защищает от нового намерения. При тематически далёком входе тоже нет гарантии низкого числа; это ограничение метода отражается в разборе ошибок, а не обещание обнаружить любой неизвестный тип.

**Проверка.** A3–A5 в [приёмке](kriterii-priyomki.md).

## M4.6 — Выбор способа классификации и подключение

`text` — доступный текст обращения; для продолжения M6 передаёт `classification_text`, собранный
M3 по [contracts §8](../contracts.md#8-порядок-исполнения-c08). Не классифицировать один адрес
в отрыве от вопроса и просьбы клиента; не фиксировать прежний тип навсегда. В M4 достаточно
заданных текстов «просьба → вопрос об адресе → адрес» и «просьба → уточнение → вопрос о гарантии»;
настоящая сборка из БД проверяется в M6.

**Проблема.** Неуверенный или сломанный классификатор не должен молча разрешать бизнес-действие.

**Что уже работает.** Локальное решение и LLM M4.3 проверены отдельно.

**Что сделать.**

1. Собрать `classify(text)`: локальные соседи + правила → при достаточной согласованности и однозначном приоритете принять локально; иначе LLM. Пустой вход — сразу неподтверждённый результат без платного вызова.
2. Проверить ответ LLM и нормализовать его в контракт ниже. Невалидный ответ после ограниченного повтора, неоднозначность, таймаут или исчерпание лимита → неподтверждённость с причиной. Не сохранять локального кандидата «спам» как окончательный тип при ошибке LLM.
3. Добавить запланированную миграцию `requests`: nullable `req_type`, `priority`, `routing_method`, `type_confidence`. В адаптере `route(request)` сохранить актуальные четыре поля одной операцией; диагностическую причину передать в результат/trace, отдельная колонка не требуется. Старое успешное решение не должно маскировать неуспех нового прогона.
4. Передать результат будущему M6. M4 не меняет `status`, не создаёт ticket, не отправляет сообщение/уточнение. Подтверждённый спам в M6 → reject без ответа; жалоба → оператор; вопрос → RAG без обязательного адреса; заявка → извлечение и проверки. Неподтверждённый результат → оператор.

**Пример входа и результата.** Контролируемая низкая согласованность и LLM с неоднозначным ответом дают `{req_type: null, priority: null, routing_method: "llm", type_confidence: null, classification_reason: "ambiguous"}`. M4 сохраняет отсутствие решения, M6 не продолжает автоматическое действие.

**Контракт.** `classify(text)` и результат `route(request)` возвращают:

| Поле | Смысл |
|---|---|
| `req_type`, `priority` | Значения §0; при неуспешной классификации оба `null` |
| `routing_method` | `classic` — окончательно решено локально; `llm` — решение/неуспех после обращения к M2; `null` — классификация не запускалась, например пустой текст |
| `type_confidence` | Только доля локальных голосов при `classic`; при `llm`/отказе — `null`, это не самооценка модели |
| `classification_reason` | Диагностика результата: `local_agreement`, `llm_confirmed`, `ambiguous`, `invalid_output`, `timeout`, `empty_input` или конкретная причина отказа клиента M2; передаётся M6 и в trace |

Непустые допустимые тип и приоритет после проверки — подтверждённое решение; `null` хотя бы в одном означает неподтверждённость. Для `classic` дополнительно действует порог согласованности. Для `llm` отсутствие численного confidence нормально; не сравнивать `null` с порогом и не ставить выдуманное `1.0`. Синтаксически валидный ответ всё равно может ошибаться по смыслу — это оценивается реальными примерами.

**Краевые случаи.** Отсутствие адреса не снижает согласованность типа и не требует LLM само по себе. Смена текста в следующем прогоне требует нового решения. Обрыв LLM учитывается по правилам M2: неизвестная стоимость не становится нулевой.

**Проверка.** A6–A8 в [приёмке](kriterii-priyomki.md); полный бизнес-маршрут проверяется в M6, здесь достаточно spy-заглушки потребителя.
