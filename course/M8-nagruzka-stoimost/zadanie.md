# M8 — Нагрузка и стоимость · Задание

Сохранённое событие → Redis Streams → один отдельный worker → сохранённый результат прогона
или пауза → подтверждение обработки. Затем добавляем ограниченные повторы, fallback, кеш знаний,
бюджет и локальный прогон. Работаем поверх M1–M6; [общие контракты](../contracts.md) задают
статусы и идентичность. Номера M8.1–M8.8 сохраняются.

Приложение и данные в рамках редакции курса не реализованы. Студент расширяет свой проект.
Обязательный стек прежний: Redis, PostgreSQL, API/worker, основной и запасной LLM-адаптеры.
RabbitMQ, outbox/CDC, Kubernetes, распределённые транзакции и новая платёжная система не нужны.
Очередь не даёт безусловной гарантии доставки между записью в PostgreSQL и публикацией в Redis.

`zadanie.md` задаёт поведение, `kriterii-priyomki.md` — сценарии, `detalnoe-review.md` — риски,
`details/` — объяснение. Процесс M0, отдельное ревью и записи понимания сохраняются.

## M8.1 — Асинхронная обработка через очередь

**Проблема и исходное состояние.** Приём M1/M3 уже сохраняет обращение и сообщения; M6 даёт
запускаемый граф и проверенный путь от приёма до действия через локальный runner. Теперь
явный запуск обработки заменяется доставкой события одному worker через Redis Streams.
Собирать бизнес-пайплайн заново или впервые соединять приём и граф в M8 не нужно.

**Что сделать.** После сохранения входа публиковать событие в Redis Streams. Отдельный процесс
`worker` с consumer group читает его, загружает данные из БД и запускает/возобновляет M6. API
отвечает, не дожидаясь графа. Redis URL, имя stream/group и предел backlog — в конфиге;
в compose добавляется worker. Начальный worker обрабатывает события последовательно.

**Вход и контракт.** Конверт события из M6.4, например:

```json
{"event_id":"form:submission-42","event_type":"client_message",
 "request_id":"REQ-2026-0042","message_id":"MSG-42",
 "received_at":"2026-09-19T10:00:00Z"}
```

`message_id` здесь — ссылка на сохранённую реплику, а не полный текст или эталон. Для события
оператора используется `escalation_id`; тип `recovery` восстанавливает незавершённый run M6.
Повтор публикации сохраняет `event_id`. Новая реплика того же обращения получает другой
`event_id` и `message_id`, но прежний `request_id`. ID записи Redis — транспортная диагностика.
Стабильный ID берётся из сохранённого события/идентичности производителя, не генерируется заново
при каждом HTTP-повторе.

**Краевой случай: публикация не удалась.** Учебный исход один: явная ошибка 503 с безопасным
кодом `enqueue_failed` и идентификаторами сохранённого обращения/события. Запись в БД могла
сохраниться. Клиент повторяет доставку с прежним внешним `message_id`; приём находит прежнее
событие и повторяет публикацию, а не прекращает работу только потому, что вход — дубль.
Если публикация прошла, но подтверждение потеряно, повторный XADD допустим: M8.2 дедуплицирует
по `event_id`. При заполненном backlog возвращается явная ошибка перегрузки; непроцессированные
события не обрезаются ради лимита. Без повторения клиентом окно «БД записана, Redis нет» может
оставить событие необработанным; обязательного outbox здесь нет.

**Проверка и понимание.** Сценарии 8.1 в приёмке. Почему сохранённая запись и успешная публикация —
два разных факта, и что должен сделать клиент после 503?

## M8.2 — Идемпотентность обработки

**Проблема и исходное состояние.** Redis доставляет повторно, а M6 уже хранит checkpoint и
идемпотентность действий. Требуется отличить повтор доставки от новой реплики.

**Что сделать.** Добавить `processed_messages(event_id UNIQUE, request_id, processed_at)`;
`broker_msg_id` можно сохранять для диагностики, но он не ключ дедупа. Перед обработкой проверять
`event_id`. Уже обработанное событие → `XACK` без графа и LLM. Новое → граф → сохранить результат
и маркер обработки → `XACK`. Маркер нельзя фиксировать раньше состояния/результата.

**Результат.** Обработано событие, а не обязательно всё обращение. Сохранённые `need_info` и
`escalated` завершают прогон и разрешают ack. Ответ клиента/решение оператора придёт новым
событием с новым `run_id`; `thread_id=request_id`. Повтор после падения восстанавливает прежний
run и checkpoint. В `escalated` новая реплика сохраняется оператору, но не разрешает авто-действие.

**Падение.** До сохранения результата → запись остаётся pending; worker читает/перехватывает
зависшие pending-записи по ограниченному idle-времени и возобновляет работу. `XACK` снимает
запись из pending consumer group, но не удаляет её из stream. У Redis Streams нет RabbitMQ-nack:
повтор организуется чтением pending, а не вымышленной командой. После лимита постоянных ошибок исполнения незавершённого run — диагностическая dead-letter
запись в другом stream того же Redis и `failed` только при допустимом переходе состояния M6,
затем ack. Если результат run уже сохранён (включая done/rejected/need_info/escalated),
ошибки записи маркера или ack не разрешают менять его на failed: восстановить только
processed-маркер и ack. Если необходимое сохранение не удалось, ack нет. Нового брокера не добавлять.

**Граница гарантии.** Если checkpoint и маркер не могут записаться одной транзакцией,
сначала надёжно сохранить результат M6, затем маркер. Сбой между ними допускает возобновление;
действия защищает M6.8. Не обещать отсутствие повторного вычисления или оплаты LLM после сбоя.
Каждый реально повторённый вызов — новый `call_id`. Локальный ticket создаётся один раз по M6,
но внешнее exactly-once без поддержки получателя не обещается.

**Проверка и понимание.** Сценарии 8.2. Почему ack на `need_info` правилен, а дедуп по
`request_id` съест следующую реплику?

## M8.3 — Retry, timeout, circuit breaker

**Проблема и исходное состояние.** Клиент M2 и инструменты M6 имеют ошибки; теперь их ожидание
и повторы должны быть ограничены одной политикой. Повторять произвольную функцию с эффектом нельзя.

**Что сделать.** Таймауты по виду зависимости из конфига; retry только временных ошибок с
экспоненциальным backoff и jitter; общий предел попыток/времени. Одно место управляет повторами,
SDK и внешняя обёртка не умножают их. Для каждой зависимости breaker: closed → open после
серии сбоев → half-open после паузы → closed при успехе. Пример тестового конфига: timeout 0,1 с,
2 попытки, открытие после 2 последовательных неудач, cooldown 0,2 с; это учебные параметры мока,
а не обещание подходящих production-лимитов.

| Событие | Результат |
|---|---|
| timeout / временная сеть / 429 / 503 | ограниченный retry; затем fallback или контролируемый исход |
| неверный ключ / неверные аргументы / запрет прав | не повторять как временный сбой |
| серия отказов зависимости | breaker open; запрос к ней не уходит до пробного half-open |
| таймаут после возможного бизнес-эффекта | возобновление через журнал M6, не слепое повторение функции |

Retry и fallback внутри ограниченного tool-use цикла M6 расходуют его общий остаток
реальных LLM-вызовов (максимум 5), а не получают собственные 5 попыток на каждую итерацию.
Проверка общего остатка выполняется перед каждой сетевой попыткой; исчерпание даёт
контролируемую эскалацию M6 без шестого вызова. Число шагов/таймаут цикла также не сбрасываются.
Каждая фактическая LLM-попытка пишется в M2-журнал; отказ до сети (open breaker, бюджет)
вызовом модели не считается. Проверка: 8.3; вопрос — какой сбой безопасно повторить и почему?

## M8.4 — Graceful degradation

**Проблема и исходное состояние.** M5 проверяет условия, M6 выбирает действия. Недоступность
источника не превращает неизвестное условие в подтверждённое.

**Что сделать.** Использовать существующие ветки M6 и фиксировать причину в результате:

| Недоступно | Допустимый результат |
|---|---|
| основная модель | запасная M8.5, та же схема и проверки |
| обе модели | `escalated`, причина недоступности; без LLM-заявления об успехе |
| retrieval для ответа на вопрос | оператор, без ответа о неподтверждённых условиях |
| прайс/зона/договор для обязательной проверки | неизвестный результат → оператор; авто-действие запрещено |
| кеш | повторить разрешённый запрос без кеша, с теми же правами и бюджетом |
| проверка доступа | не выдавать документ, не расширять scope |
| БД/checkpoint/журнал действий | не подтверждать результат, не ack; ограниченный повтор M8.2/M8.3 |

Можно сохранить уже известные поля и техническую причину сбоя. «Ответ без RAG с оговоркой»
не разрешает выдумывать условия. Нового статуса «частично» не вводить: используются состояния
[контракта](../contracts.md). При нескольких сбоях сначала сохраняется запрет небезопасного
действия; если БД жива — эскалация, если нет — незавершённое событие без ack.

Проверка: 8.4. Что останется в БД и что увидит клиент, если источник обязательной цены недоступен?

## M8.5 — LLM-fallback

**Проблема и исходное состояние.** Один адаптер M2 не переживает отказ своего провайдера.
Теперь обязателен запасной адаптер: второй облачный провайдер либо локальная Ollama по железу.
Третью модель и GPU-инфраструктуру не добавлять.

**Что сделать.** `LLM_MODEL_CHAIN=[основная, запасная]` из конфига; первая по умолчанию —
`LLM_MODEL`. Явный `model=` из правила M8.7 выбирает стартовую модель из настроенной цепочки,
после неё допускается только настроенный совместимый fallback. Внутри `LLMClient` после лимита
временных сбоев перейти к следующей модели. Сигнатура `complete`/поля `LLMResult` прежние,
`result.model` — фактически ответившая модель. Схема, инструменты, права и лимиты не ослабляются.
Вся цепочка недоступна → `LLMError` → эскалация M8.4.

**Расходы.** Один `complete` может включать несколько фактических вызовов. Использовать журнал
M2 на границе каждого адаптера/попытки, а не только после окончательного `LLMResult`: отдельный
`call_id=llm_calls.id`, фактическая модель, usage или неизвестная стоимость, request/run/step и
версия промпта. Контекст журнала передаётся существующей внутренней обёртке шага; новая публичная
сигнатура не нужна. Внешний шаг не должен вторично записывать успешный вызов другим ID.

Проверка: 8.5. Основная дала таймаут без usage, запасная ответила за 0,02: в журнале две строки,
известная сумма 0,02 плюс один неизвестный расход, а не «весь вызов стоил 0,02». Это пример
до подключения budget gate; после M8.7 неизвестный расход может запретить следующий fallback.

## M8.6 — Кеш: строковый и семантический

**Проблема и исходное состояние.** M5 умеет отвечать по знаниям и фильтровать доступ. M2.10
кеширует префикс на стороне провайдера; здесь повторно используется уже проверенный ответ.

**Что сделать.** Строковый кеш — Redis, семантический — существующий pgvector. Сначала фильтр
доверенного `access_scope`, версии KB, промпта и применимой модели/конфига, затем сравнение
текста/эмбеддинга. В кеше хранить ответ с источниками и тем же scope. TTL и смена версии исключают
устаревшие записи. Порог похожести выбрать на dev-примерах по M0.4, включая близкий неверный вопрос.

**Пример.** «Какая гарантия на работы?» и безопасная перефразировка могут использовать один ответ
по общему документу `access=all`. «Какая гарантия в договоре клиента 7?» не получает этот ответ
или ответ другого клиента только из-за высокой похожести. Для учебной системы без доверенного
клиентского логина доступен лишь `all`; scoped-кеш проверяется серверной тестовой фикстурой M5.10.

Извлечённые поля, маршрут, валидация и действие конкретной заявки не кешируются. Новый адрес
означает новые проверки; похожесть не идентифицирует клиента. Кеш стабильного текста инструкции
не подменяет ответ модели. Cache hit без вызова LLM не создаёт расход LLM; фактические вызовы
эмбеддинга учитываются по принятой схеме учёта, не исчезают из отчёта.

Проверка: 8.6. Почему смена прав должна дать промах даже при идентичном тексте?

## M8.7 — Стоимость: бюджеты и выбор модели

**Проблема и исходное состояние.** M2 считает вызовы, M6 добавляет run_id; теперь ограничиваем
новые расходы. `route_decision` (действие), `routing_method` M4 (классификатор) и выбор LLM-модели
здесь — разные решения.

**Что сделать.** `usage_counters(period, scope, scope_id, tokens, cost)` — пересчитываемый агрегат
`llm_calls`; период — сутки UTC, scope global/user. `scope_id` пользователя берётся из доверенной
идентичности приложения/канала, а не телефона во входе. Если такой идентичности нет, применяется
глобальный лимит; тест user-лимита использует явную серверную фикстуру.

Перед каждым реальным вызовом, включая retry/fallback, проверить известный расход + оценку
следующего вызова против лимита. Ровно лимит разрешён, превышение запрещает вызов. Учебный исход
превышения — эскалация с причиной `budget_exceeded`, без дополнительного платного объяснения.
При неизвестном расходе или невозможной оценке бюджет не считается свободным: эскалация с
причиной `budget_unknown`. Агрегат помечает оценённые суммы/число неизвестных; null не становится 0.
Один последовательный worker упрощает проверку; абсолютную финансовую гарантию при нескольких
процессах, неизвестном usage или неточной оценке не обещать и новую систему резервов не строить.

Выбор модели: правило `pick_model(step, complexity, confidence)` из конфига выбирает среди уже
двух настроенных моделей простую/сложную ветку по явному признаку (например, длине контекста).
Оно не меняет тип обращения и запрет действий; жалоба остаётся у оператора. Дорогая модель не
объявляется автоматически качественнее. Результат правила и фактическая модель видны в журнале.

**Фикстура.** Лимит 0,03, A=0,01, B=0,02; повтор записи A не меняет сумму. Следующая оценка 0,01
запрещает сетевой вызов; новая дата UTC сбрасывает окно, но не стирает журнал. Числа — арифметика,
не тарифы. Проверка: 8.7.

## M8.8 — Локальная проверка под нагрузкой

**Проблема и исходное состояние.** Весь путь уже собран. Нужно увидеть очередь, задержку и отказ
на своём окружении, не доказать универсальный RPS.

**Что сделать.** Один конкурентный скрипт на localhost; внешние платные LLM/эмбеддинги — моки с
фиксированной задержкой/usage. Начать с 10 событий и concurrency=1, затем 2 и 5; увеличение
останавливается при видимой перегрузке. Данные можно взять ограниченной выборкой `data/course_pack/inputs/replay.jsonl`;
преобразовать по M1, не отправлять строки с эталонами напрямую в API. Каждое логическое сообщение
получает стабильный ID; намеренные повторы используют прежний. Пулы/таймауты ограничены конфигом.

В отчёте различать: успешно опубликованные уникальные события; обработанные (маркер M8.2,
включая сохранённые паузы/контролируемый failed); ожидающие опубликованные без маркера;
ошибки приёма/публикации. HTTP-повторы и Redis-дубли не увеличивают уникальные количества.
На снимке `опубликовано = обработано + ожидает`; статусы обращений считаются отдельно.
Снимать p50/p95 приёма и обработки одного события, число ошибок, backlog и cache hit/miss.
Время ожидания клиента между событиями не включать в рабочую latency.

Прогоны: нормальный поток; всплеск; отказ retrieval; суженный пул БД с ограниченным ожиданием.
Пул исчерпан → контролируемый таймаут/повтор, а не бесконечное ожидание или потеря события.
После прекращения подачи backlog разбирается либо остаётся явно объяснённым. Записать пределы
машины, параметры, узкое место и результаты; абсолютную производительность не обещать.

Проверка: 8.8. Почему завершённое событие и завершённое обращение дают разные количества?
