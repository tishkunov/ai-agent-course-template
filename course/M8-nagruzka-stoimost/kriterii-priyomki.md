# M8 — Критерии приёмки

Проверяется код студента после M6. Общие условия: отдельная БД, Redis Streams, один worker,
локальные эффекты M6; LLM/эмбеддинги замоканы, часы и ожидания подменяются там, где указано.
Использовать одну фиксированную полную допустимую заявку M6 с явными полями и подтверждёнными
условиями, а не скрытые поля синтетики. Во всех опытах IDs новых событий уникальны;
намеренный повтор сохраняет event_id. Внешних платных нагрузочных вызовов нет.

Для retry/fallback после подключения M8.7 мок неудачной попытки несёт известный usage, а лимит
заведомо достаточен: так проверка бюджета не подменяет проверяемый механизм. Неизвестные расходы
проверяются отдельно в 8.7. Реальный запасной адаптер демонстрируется единичным ручным прогоном.

## M8.1 — Приём и worker

| ID | Предусловие и вход | Действие | Наблюдаемый результат | Признак ошибки |
|---|---|---|---|---|
| 8.1a | worker остановлен, Redis жив, новое сообщение | POST, прочитать stream; затем запустить worker | HTTP возвращает ID до обработки; конверт содержит event/request IDs; после старта есть сохранённый результат | HTTP ждёт модель, либо stream содержит полный контекст/эталон |
| 8.1b | Redis публикация подменена отказом после записи БД | POST; восстановить Redis; повторить тот же message_id | сначала 503 enqueue_failed, затем прежние request/message/event IDs опубликованы; БД не задвоена | успешный приём обещает запуск при отказе; повтор не публикуется из-за дедупа входа |
| 8.1c | маленький лимит backlog, worker остановлен | подать больше лимита | явная ошибка перегрузки; уже опубликованные события не удалены | молчаливое trimming необработанных записей |

## M8.2 — Повторы, паузы, восстановление

| ID | Предусловие и вход | Действие | Наблюдаемый результат | Признак ошибки |
|---|---|---|---|---|
| 8.2a | один event_id опубликован двумя XADD с разными ID stream | обработать обе записи | один processed-маркер; второй граф/LLM не вызван после завершения первого; один ticket | дедуп по ID stream или второй эффект |
| 8.2b | заявка без адреса | обработать E1, затем доставить ответ E2 с адресом | E1: persisted need_info и ack; E2: новый run того же request, обработка продолжается | ожидание клиента держит E1 pending; E2 съеден дедупом по request_id |
| 8.2c | жалоба или исчерпанный fallback, БД жива | обработать событие и проверить pending | persisted escalated, processed-маркер, ack; новая реплика сохраняется оператору | worker ждёт решения оператора до ack или запускает авто от клиентской реплики |
| 8.2d | локальный ticket создан, ответ ещё не отправлен | внедрить падение до ack, перезапустить worker, дождаться reclaim pending | прежние run/action IDs, один ticket, оставшаяся работа выполнена, событие ack | второй ticket, новый run восстановления, pending никто не читает |
| 8.2e | сохранение результата подменено ошибкой БД | обработать событие | нет processed-маркера и ack; после восстановления повтор возможен | событие подтверждено раньше результата |
| 8.2f | незавершённый run в in_progress, постоянно падающий mock узла, лимит 2 обработки | дать две ошибки и проверить исход | сохранён failed и диагностическая запись dead-letter того же Redis, затем ack | бесконечный цикл; ack до сохранения failed; новый брокер |
| 8.2g | run уже сохранил done, затем сбой перед processed-маркером; отдельно повторить для rejected/need_info/escalated | исчерпать несколько ошибок записи маркера/ack, восстановить зависимости | прежний результат и статус сохранены; worker восстанавливает marker/ack без нового графа/эффекта | статус переписан на failed из-за транспорта |

8.2d доказывает отсутствие повторного локального эффекта. Если при восстановлении реально
повторился LLM-вызов, его новый call_id и расход обязательны; бесплатность recovery не требуется.

## M8.8 — Локальный поток

Предусловия: 10 уникальных событий, внешние платные вызовы — моки, фиксированные задержки и
тарифная фикстура; запуск concurrency 1, 2, 5 по очереди. Действие: обычный поток, всплеск,
отказ retrieval, ограничение пула БД; после каждого прекратить подачу и снять снимок.
Результат: таблица `опубликовано/обработано/ожидает/ошибки публикации`, уникальность по event_id,
баланс опубликованных событий, p50/p95 приёма и события, backlog, cache hit/miss. Паузы входят
в обработанные; HTTP/Redis-повторы не увеличивают объём. Признак ошибки: потерянное событие без
объяснения, бесконечное ожидание пула, платный массовый прогон, обязательный абсолютный RPS.
M9 для этого сценария не нужен: достаточно скрипта и запросов к БД/Redis.
