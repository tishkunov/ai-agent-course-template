# M8.7 — Бюджет по журналу вызовов

## Что это и зачем

Агрегат не заменяет журнал. Повтор сохранения A не должен снова прибавить A в usage_counters.
Здесь нужен простой пересчёт и ограничение новых вызовов одного worker, а не платёжная система.
Стоимость неизвестного вызова не равна нулю: бюджет с таким расходом нельзя считать свободным.

Выбор модели означает выбор ресурса для шага, а не route_decision обращения. Жалоба не становится
автоматической заявкой от того, что выбрана более дорогая модель.

## Разобранный пример

Лимит 0,03; журнал A=0,01, B=0,02. Повтор записи A оставляет 0,03. Следующий вызов с оценкой
0,01 не происходит, сохраняется budget_exceeded. При cost=null — budget_unknown, без платного
объяснения. До включения бюджета M8.5 показывает fallback после неизвестного расхода; после
включения лимита этот fallback также проходит gate и может быть запрещён.

## Что сделать по шагам

1. Агрегируй по суткам UTC, global и доверенному user scope; не создавай пользователя из телефона.
2. Проверяй known cost + оценку перед каждой попыткой, включая retry и fallback.
3. Неизвестные расходы показывай отдельно и используй консервативный исход задания.
4. Реализуй явное правило simple/hard для двух существующих моделей и записывай фактический выбор.
5. Проверяй UTC-границу подменой часов; история расходов не стирается при смене периода.

## Промпт-контракт к ИИ

Дай арифметическую фикстуру, trusted scope и выбранный исход превышения — оператор. Попроси агрегат журнала и gate каждой попытки, без финансовых резервов или новых сервисов.

## Риски и проверка

Инкремент агрегата на повтор записи; null превращён в ноль; бюджет проверяется только до первой модели; user scope из произвольного текста; расход параллельных процессов объявлен строго гарантированным.

Поведение задаётся в [задании](../zadanie.md), точная проверка — в соответствующем пункте
[приёмки](../kriterii-priyomki.md). После кода нужен отдельный вызов ревью по M0.
