# M8.5 — Основная и запасная модель

## Что это и зачем

Fallback — внутренняя цепочка клиента M2, не второй клиент в каждом узле. Для M8 нужна
реальная запасная модель: второй облачный адаптер либо Ollama. Локальная модель не имеет тарифа
внешнего API, но не становится автоматически бесплатной в смысле ресурсов или равноценной по качеству.
Схема и ограничения инструментов действуют на оба ответа.

## Разобранный пример

Основная временно отказала, запасная вернула валидный результат: наружу один LLMResult с model
запасной, внутри два call_id. Известный usage отказавшей попытки также записан. Если usage
неизвестен, журнал показывает null, а не ноль. При включении M8.7 бюджет может запретить fallback;
переключение не является способом обхода лимита.

## Что сделать по шагам

1. Настрой цепочку ровно двух совместимых моделей; согласуй её с явным model= от pick_model.
2. После ограниченного retry перейди к запасной; не повторяй постоянную ошибку бесконечно.
3. Перенеси запись M2-журнала на границу каждой попытки внутри адаптера, сохранив публичный complete.
4. Передавай контекст request/run/step/prompt внутренней обёртке; не записывай итог ещё одним ID.
5. Общий лимит tool-loop M6 проверяется перед каждой попыткой основной/запасной; их
   суммарно не больше 5 внутри цикла, даже если локальная retry-политика допускает больше.
6. Обе недоступны → типизированная ошибка и оператор, если состояние можно сохранить.

## Промпт-контракт к ИИ

Дай прежнюю сигнатуру клиента, цепочку и поля M2-журнала. Попроси fallback с отдельным call_id на каждую попытку; не добавляй третью модель или новую сервисную архитектуру.

## Риски и проверка

Учитывается только окончательный ответ; model показывает исходную модель; fallback ослабляет схему/права; незаметно меняет бюджет.

Поведение задаётся в [задании](../zadanie.md), точная проверка — в соответствующем пункте
[приёмки](../kriterii-priyomki.md). После кода нужен отдельный вызов ревью по M0.
