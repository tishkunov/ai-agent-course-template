# M8.2 — Повтор доставки и завершение события

## Что это и зачем

У одного обращения несколько событий и несколько run. Дедуп по request_id блокирует ответ
на уточнение. Дедуп по ID записи stream пропускает повторный XADD того же события. Поэтому
processed_messages имеет уникальный event_id производителя.

XACK снимает запись с pending-list группы, а не удаляет её из stream. Упавший worker должен
прочитать/перехватить pending после idle-времени. Без этого сообщение не исчезло, но и не продвинется.

## Разобранный пример

E1 → run R1 → сохранён need_info и исходящий вопрос → processed E1 → ack.
Новая реплика E2 того же request → R2. Повтор E1 уже не запускает модель. Если R1 упал до
сохранения результата, повтор восстанавливает R1 и checkpoint, а не открывает новый run.

## Что сделать по шагам

1. Добавь unique event_id; различай проверку готового маркера и незавершённый run M6.
2. Сохрани результат/паузу прежде processed-маркера и ack. При доступной общей транзакции используй её.
3. Восстанавливай pending с теми же IDs. Сбой между checkpoint и маркером допускает повтор вычисления.
4. Оставь бизнес-эффекты под журналом M6. Постоянная ошибка исполнения незавершённого run
   допускает failed лишь по разрешённому переходу и dead-letter в том же Redis. Уже сохранённый
   done/rejected/need_info/escalated не переписывай при сбое маркера/ack: восстанови только их.
   Не ack при ошибке необходимого сохранения.

## Промпт-контракт к ИИ

Передай Event и run-result M6, требование ack для persisted pauses, unique event_id и пример повторного XADD. Не проси RabbitMQ nack или новую exactly-once инфраструктуру.

## Риски и проверка

Маркер раньше результата; ожидание done перед ack; дедуп по request_id/transport ID; обещание бесплатного повторного LLM; pending никто не читает после рестарта.

Поведение задаётся в [задании](../zadanie.md), точная проверка — в соответствующем пункте
[приёмки](../kriterii-priyomki.md). После кода нужен отдельный вызов ревью по M0.
