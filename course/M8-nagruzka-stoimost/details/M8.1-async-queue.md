# M8.1 — Приём и Redis Streams

## Что это и зачем

Приём сохраняет вход быстро; граф работает отдельно. Очередь разделяет эти скорости,
но запись PostgreSQL и XADD не становятся одной транзакцией. После таймаута публикации сервер
может не знать, дошло ли сообщение. Повтор с тем же event_id позволяет пережить эту неопределённость.

Redis Streams уже использует Redis проекта. Один consumer group и один последовательный worker
достаточны для обязательного пути; смена брокера и несколько worker не нужны.

## Разобранный пример

Первый POST сохранил MSG-42/REQ-42, но Redis недоступен: клиент получил 503 enqueue_failed.
Второй POST с тем же внешним message_id находит те же данные и повторяет XADD. Он не создаёт
другую реплику. Если первая публикация всё-таки прошла, обе записи stream содержат один event_id.

## Что сделать по шагам

1. Замени явный запуск из runner M6 на publisher после сохранения в приёме; используй прежние event/request IDs и конверт из задания.
2. Подними worker в существующем compose; он получает IDs и читает данные из БД.
3. Проверь публикацию при повторе входа после 503; не ограничивай её веткой «создали новую запись».
4. Ограничь backlog и ожидание Redis. Перегрузка даёт явный отказ, не удаление pending-событий.

## Промпт-контракт к ИИ

Попроси соединить существующий приём и граф через Redis Streams с одним worker. Передай точный конверт и сценарий 503; запрети синхронный граф в HTTP и обещание атомарности БД+Redis.

## Риски и проверка

Новый UUID при каждом повторе; граф в HTTP; приём отвечает успехом после неудачной публикации; дубль входа не допубликуется; обрезание необработанных записей ради длины очереди.

Поведение задаётся в [задании](../zadanie.md), точная проверка — в соответствующем пункте
[приёмки](../kriterii-priyomki.md). После кода нужен отдельный вызов ревью по M0.
