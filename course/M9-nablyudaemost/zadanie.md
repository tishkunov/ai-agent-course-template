# M9 — Наблюдаемость · Задание

Один прогон → trace → связанные события в логах → технические и бизнес-агрегаты → Grafana →
воспроизводимый alert. Расширяются граф M6, журнал M2 и worker M8; номера M9.1–M9.6 сохранены.
Langfuse, Prometheus и Grafana остаются заявленным стеком. Используй локальное окружение;
если Langfuse уже подключён к облаку, допустим этот экземпляр. Деплой, новые коллекторы и
отправка уведомлений реальным людям не входят. [Контракты](../contracts.md) — источник статусов,
событий, расходов и границ доступа. M0 и отдельное ревью остаются обязательными.

## Один пример через весь модуль

Используй локальную фикстуру полной допустимой заявки из M6: все обязательные поля и подтверждённые
условия заданы явно, сумма ниже 15000, эффект — локальный ticket. Внешние модели в проверочном
прогоне замоканы. Для демонстрации retry/fallback ошибки мока содержат известный usage,
бюджет заведомо достаточен; неизвестные расходы проверяются отдельной фикстурой M9.4. Сначала обработай её штатно (A). Затем создай отдельное обращение с тем же
текстом и новым внешним message_id (B), подмени ответ модели на таймаут и исчерпай допустимый
fallback: B сохраняется `escalated` с причиной. Повторять extract на терминальном A ради сбоя
не нужно. В каждом пункте сравни A и B на том же инструменте: шаг, лог, метрика, панель, alert.
Это два обращения одного сценария, а не изменение истории уже завершённого обращения.

## M9.1 — Трейсинг прогона агента (Langfuse)

**Проблема и исходное состояние.** M6 возвращает результат с request/run/event/call/action IDs.
Теперь нужно увидеть, где внутри прогона возникла задержка или ошибка.

**Что сделать.** Trace на один `run_id`, связан с `request_id` и `event_id`; span на исполненный
узел, инструмент и каждый фактический LLM-вызов. Для LLM: `call_id=llm_calls.id`, фактическая
модель, step, prompt_version, latency, доступный usage/cost и признаки оценки/неизвестности.
Метаданные брать из M2-журнала; не пересчитывать отдельной таблицей тарифов SDK Langfuse.

**Вход и результат.** A даёт успешную ветку с разрешённым действием; B — span неудачной попытки,
лимита/fallback и эскалации. Неисполненные узлы не требуют фиктивных span-ов. При `need_info`
или `escalated` trace закрывается. Поздний ответ клиента или решение оператора создаёт новый run
и новый trace при прежнем request_id. Recovery сохраняет run_id; после рестарта допустима
связанная часть trace с тем же run_id, без удерживания span в памяти весь период ожидания.

**Контракт и граница.** Сумму вызовов одного run сравнивать с `llm_calls WHERE run_id=...`,
сумму всех run обращения — с известной частью `requests.cost_total`. Идентичный call_id нельзя
суммировать дважды из-за повторного экспорта. Обязательны только ограниченные диагностические
поля: не сохранять полный сырой контекст, PII, чужие документы, системные секреты или аргументы
инструмента без фильтра M6/M7.

**Best-effort.** Экспорт ограничен таймаутом и размером буфера; при недоступности коллектора
ошибка изолируется от обработки, локально фиксируется безопасный факт потери телеметрии.
Часть span-ов может потеряться. Проверка сходимости trace с БД выполняется при исправном экспорте;
при сбое БД-журнал остаётся источником расходов, неполный trace помечается неполным.
Проверка: 9.1. Почему один span на сутки ожидания клиента искажает время работы системы?

## M9.2 — Структурные логи

**Исходное состояние.** Логгер M1 и маскирование M6/M7 уже есть. Расширь контекст, не создавая
вторую систему логирования.

**Что сделать.** JSON-события с `ts`, `level`, `event`, `request_id`, `run_id`, `event_id`,
`trace_id`, `step`, `status`, безопасным `error_code`; при вызове — call_id/action_id. Контекст
передаётся в worker и снимается после события, чтобы соседнее обращение не унаследовало чужой ID.
В логах HTTP до запуска run допустимы null run/trace IDs: транспортный X-Request-ID M1 не
подменяет доменный request_id. Уровни: info — ход обработки, warning — retry/degradation,
error — исчерпанный сбой; обычная жалоба у оператора сама по себе не инфраструктурная ошибка.

**Пример.** У B найти `event=llm_timeout`, затем `event=escalated` по run_id и перейти к trace;
у A эти события отсутствуют. Телефон/адрес из фикстуры, токен и полный prompt отсутствуют в
логе. Маскирование/исключение применяются до экспорта, а не при отображении.

**Сбой.** Ошибка лог-синка не меняет результат бизнес-обработки; локальный stdout — назначение
для учебной демонстрации. Потеря логов возможна. Проверка: 9.2.

## M9.3 — Технические метрики

**Исходное состояние.** Есть события логов и временные границы worker. Теперь агрегируй их в
Prometheus и подключи Grafana, сохранив конфигурацию в проекте студента.

| Метрика | Тип и значение |
|---|---|
| latency шага, активного сегмента run, HTTP-приёма | histogram в секундах; отдельные p50/p95 |
| время события до сохранённого исхода | отдельная histogram: очередь + работа, без ожидания следующего сообщения |
| вызовы/ошибки внешних зависимостей | counters по зависимости и безопасному коду, включая каждую реальную попытку |
| backlog | gauge: уникальные опубликованные события без processed-маркера; транспортные pending отдельно |
| cache hit/miss | counters только выполненных lookup; hit rate = hits / (hits + misses) в выбранном окне |
| расходы | агрегат M2/M8, отдельно известная сумма, оценённые/неизвестные строки |

Восстановление run после падения добавляет активный сегмент; downtime не считается активной
работой. Ожидание клиента/оператора показывается отдельно по состояниям и не прибавляется к
latency одного прогона. Для error rate назвать знаменатель: неуспешные внешние попытки / все
внешние попытки за окно; это не доля HTTP 500 и не доля эскалаций.

Лейблы — ограниченный набор шагов/моделей/исходов; request_id, event_id, телефон, prompt и адрес
не лейблы. Экспорт `/metrics`, Prometheus scrape и Grafana — как в исходном стеке. Сбой экспорта
не прерывает worker и может дать пробел в наблюдениях, а не «нулевые ошибки».

Проверка: 9.3. Для A счётчик успехов, для B — неудачные попытки и latency timeout; p95 на двух
наблюдениях иллюстративен. Почему Prometheus-label request_id хуже ссылки на trace?

## M9.4 — Бизнес-метрики и стоимость

**Исходное состояние.** `requests`, `actions`, `escalations`, `llm_calls` — источник, без новых
параллельных бизнес-счётчиков. Опциональная `daily_stats` лишь материализует те же определения;
новая таблица не обязательна.

**Период и снимок.** Выбрать UTC-интервал `[T0,T1)` и время снимка `S >= T1`. Когорта `C` —
обращения, созданные в интервале; `N=|C|`. Их состояния и история берутся на момент S. В отчёте
явно указывать оба времени: молодая когорта ещё содержит ожидающие обращения. Для воспроизводимого
теста достаточно замороженной БД/часов; произвольную историческую реконструкцию не добавлять.

| Метрика | Числитель / знаменатель |
|---|---|
| доля завершённых автоматически | обращения C со status=done, разрешённым авто-результатом и **без истории эскалации/участия оператора до S** / N |
| доля обращений с эскалацией | уникальные обращения C, у которых была запись escalations до S / N |
| доля reject | обращения C со status=rejected на S / N; причина спам или решение оператора показывается отдельно |
| успешные действия | actions со status=done / все actions обращений C, созданные до S; pending и failed показаны рядом |
| стоимость на обращение | сумма известных cost всех уникальных call_id обращений C до S / N |
| среднее число уточнений | сумма round_count обращений C на S / N |
| объём | N; дополнительно число C в new/in_progress/need_info/escalated/failed/done/rejected на S |

Доли авто и эскалаций не обязаны складываться в 100%: есть ожидание/reject/failed; завершённое
после оператора обращение учитывается в эскалациях, но не в авто. Один ticket с повторной доставкой
действия — одна строка actions, а не две успешных попытки.

Расходы всей жизни когорты до S отличаются от расходов календарного периода. Для отдельной
панели «расходы за период» суммировать `llm_calls.created_at ∈ [T0,T1)` независимо от даты
создания обращения; не делить эту сумму на объём другой когорты. Retry, fallback, несколько run
и вызовы судьи, если они относятся к отчётной обработке, учитываются по своей явной области.
Нельзя приравнивать HTTP-запрос к LLM-вызову. `cost=null` — неизвестно; вместе с известной суммой
показывать число таких строк и число/сумму estimated. Валюта и версия тарифов те же, что M2.
Пустой знаменатель → `n/a`, не 0% успеха. Неполное окно помечается.

**Фикстура для ручной арифметики.** Четыре обращения C: A done без человека; B escalated;
C done после оператора; D need_info. У A два вызова 0,01 и 0,02; у B один неизвестный;
у C один 0,04; у D нет вызовов. Уникальных actions три: два done, один failed.
Итого авто 1/4, эскалации 2/4, успешные действия 2/3, известная стоимость 0,07,
известная стоимость на обращение 0,0175 плюс один неизвестный расход. Числа не тарифы.
Проверка: 9.4. Почему `status=done` недостаточно для определения автообработки?

## M9.5 — Дашборд

**Исходное состояние.** Сначала получены данные A/B и проверены формулы; только теперь строится
один Grafana dashboard с двумя блоками. Технический: p95 приёма/работы, error rate внешних попыток,
backlog, cache hit rate. Бизнес: объём/ожидания, авто/эскалации, действия, известная стоимость и
неизвестные расходы, стоимость на обращение, среднее round_count.

В каждой панели подписать единицу, окно/когорту и знаменатель. Источники — существующие
Prometheus и PostgreSQL (или уже выбранная daily_stats). Для бизнес-данных не нужен доступ к
сырому тексту клиентов. Сохранить dashboard JSON и конфиг источников без секретов в проекте.
На A показать нормальный путь; на B найти рост ошибок/эскалаций и перейти по ID к trace через
безопасную диагностическую связь, не добавляя request_id в labels.

Если exporter недоступен, панель показывает отсутствие данных/устаревший снимок, не зелёную
нулевую линию. Проверка: 9.5. Почему разные временные окна могут дать разные верные цифры?

## M9.6 — Воспроизводимые алерты

**Исходное состояние.** Grafana уже показывает метрики. Добавить правила на существующие
симптомы: error rate, p95, backlog, стоимость на обращение и долю эскалаций. Пороги/окна — в
конфиге; технические тестовые числа выбираются для управляемого сценария, качество модели ими
не оценивается. Для долей нужны минимальное число наблюдений и явный знаменатель.

**Демонстрация.** Разделить lookback (окно расчёта) и hold/for (сколько условие держится).
Локальный конфиг: lookback 30 с, минимум 4 внешних попытки за него, error rate > 0,5 с for=30 с;
восстановление при < 0,2 с hold=30 с. Evaluation interval=1 с, breaker cooldown=1 с,
таймаут мока 0,1 с, usage ошибок известен, бюджет достаточен.

Сначала подать штатные события A. Затем на новых событиях B включить timeout обеих моделей
и подавать по одному событию в секунду не менее 75 с. Каждое относится к новому обращению
в отдельном доверенном тестовом диалоге: один новый message_id в уже escalated-треде лишь
добавит реплику оператору и не запустит LLM. Идентичность диалога задаёт серверная фикстура M3,
а не произвольное поле тела API. Контролировать фактический счётчик
внешних попыток: их должно оставаться ≥4 в каждом скользящем окне (open-breaker отказы без сети
попытками не считаются). При необходимости тестового прогона сократить cooldown, не отключая
сам механизм. Поддерживать поток до наблюдаемого firing, а не отправить одну пачку из 4 ошибок.
Увидеть alert в UI и локальную запись лог/консоль. Затем восстановить моки и подавать успешные
новые события ещё не менее 75 с: старые ошибки выйдут из lookback, потом пройдёт hold восстановления,
и появится resolved. Реальных адресатов/секретов не нужно.

Применить окно и гистерезис против дребезга, группировать связанные срабатывания одного
учебного инцидента, чтобы не отправлять отдельный сигнал на каждый retry. Проверить короткий
всплеск короче окна — без alert. Тестовые часы/сэмплы можно подменять в автоматическом тесте;
ручная демонстрация проходит на реальном стеке наблюдения.

Best-effort сохраняется: сбой мониторинга не останавливает обработку, но alert может не прийти.
Нельзя одновременно обещать отсутствие блокировки и гарантированную доставку телеметрии без
соответствующего механизма. Проверка: 9.6.

## Материалы сдачи

Команда запуска, версии конфигурации и промптов, ID A/B, безопасный вывод trace/логов,
арифметика метрик, экспорт dashboard и события firing/resolved — в существующих артефактах M0.
Объяснить: почему у обращения несколько run; почему done не равно «без человека»; что теряется
при отключении Langfuse. Сценарии приёмки и DoD — в `kriterii-priyomki.md`.
