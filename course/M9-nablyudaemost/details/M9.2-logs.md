# M9.2 — Связанные JSON-события

## Что это и зачем

Лог сообщает факт: шаг начался, попытка не удалась, сохранена пауза. Полный текст клиента
для этого не нужен. Контекст worker отличается от HTTP-контекста: транспортный X-Request-ID
не является ID обращения, а run_id появляется только при запуске обработки.

## Разобранный пример

{"event":"llm_timeout","level":"warning","request_id":"REQ-42","run_id":"R2",
"event_id":"E2","trace_id":"T2","step":"extract","error_code":"timeout"}

По R2 находятся timeout и escalation. В следующем событии worker контекст уже другой;
телефон из обращения не попадает ни в msg, ни в exception payload.

## Что сделать по шагам

1. Расширь JSON-логгер M1 контекстом M6, явно очищай contextvars после события.
2. Логируй безопасные коды и IDs; маскирование M6/M7 выполняется до записи/экспорта.
3. У A покажи info-успех, у B warning попытки и error исчерпанного сбоя.
4. Подмени sink на ошибку: бизнес-результат остаётся; потеря логов возможна.

## Промпт-контракт к ИИ

Попроси дополнить существующий логгер и контекст worker. Передай разрешённые поля и тестовый секрет-маркер; запрети сырой raw_text и новый сервис логирования.

## Риски и проверка

Контекст предыдущего request остаётся в worker; рекурсивный лог ошибки логгера; редактирование PII только в UI; обычная жалоба считается инфраструктурным error.

Поведение задаётся в [задании](../zadanie.md), точная проверка — в соответствующем пункте
[приёмки](../kriterii-priyomki.md). После кода нужен отдельный вызов ревью по M0.
