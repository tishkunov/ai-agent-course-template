# M9 — Критерии приёмки

Предусловия: рабочий путь M6/M8 студента, отдельная тестовая БД и локальный стек
Langfuse/Prometheus/Grafana. Внешние платные модели — моки. Используются A (штатная заявка)
и B (новое обращение того же сценария с исчерпанным timeout/fallback) из задания;
ошибки мока несут известный usage, budget gate допускает эти попытки; их реальные
request/run/event IDs записаны проверяющим. Новые обязательные сервисы не требуются.

## M9.1 — Trace

| ID | Предусловие и вход | Действие | Наблюдаемый результат | Признак ошибки |
|---|---|---|---|---|
| 9.1a | исправный коллектор, A и B | выполнить оба run, открыть по IDs | trace каждого run, span исполненных узлов/инструментов/каждой LLM-попытки; у B видны timeout и исход | виден только финал, пропал retry, неисполненные узлы выданы за исполненные |
| 9.1b | need_info, затем новая реплика через fake clock +1 час | выполнить оба события | один request, два run/trace; первый закрыт на паузе; час ожидания не входит в latency работы | один вечный span или новый request без причины |
| 9.1c | два run одного request, A-call=0,01 B-call=0,02 | сверить trace с llm_calls по run и request | суммы по run 0,01/0,02, по обращению 0,03; повтор экспорта call не увеличивает стоимость | каждый trace сравнивается с 0,03; расход посчитан SDK по другой цене |
| 9.1d | коллектор выключен/мок экспортёра зависает | обработать новое событие, затем восстановить коллектор | бизнес-исход сохранён, ожидание экспорта ограничено; безопасный локальный сигнал потери; trace может быть неполон | worker упал/завис; потерянные span-ы объявлены полностью восстановленными без механизма |

9.1c выполняется при исправном экспорте. При 9.1d неполная телеметрия не подменяет журнал БД.

## M9.4 — Формулы бизнеса и расходов

Предусловия: локальная арифметическая фикстура четырёх обращений из M9.4 задания, фиксированные
`[T0,T1)` и S. Действие: посчитать показатели и сравнить с ручным расчётом. Результат:
авто 1/4, эскалации 2/4, действия 2/3, известная стоимость 0,07, средняя известная часть
0,0175 плюс один неизвестный расход. Повтор записи A-call ничего не меняет. Признак ошибки:
done после оператора засчитан как авто, cost размножен JOIN-ом, null стал нулём.

Дополнительные действия с той же фикстурой:

- Сдвинуть один llm_call за календарный T1, оставив до S: расходы когорты его включают,
  календарные расходы `[T0,T1)` — нет. Ошибка: обе панели обязаны совпасть при разных областях.
- Выбрать пустую когорту: доли/средние n/a, объём 0, исключения нет. Ошибка: показано 100% успеха.
- Добавить estimated-строку: её сумма входит в известную/оценённую часть с явной пометкой.
  Ошибка: весь итог назван точным биллингом.

Проверка не зависит от «правильной» разметки data/: это явная тестовая БД, которую готовит студент.

## M9.5 — Дашборд

Предусловия: данные 9.1–9.4 собраны; экспорт dashboard и конфиг источников сохранены.
Действие: импортировать dashboard в чистый локальный экземпляр Grafana, выбрать нужное окно,
показать A/B и бизнес-фикстуру; затем остановить источник метрик.
Результат: технический/бизнес блоки заполнены, единицы и знаменатели подписаны, стоимость
совпадает с областью SQL-расчёта; остановленный источник даёт no-data/устаревший снимок.
Признак ошибки: ручная непереносимая панель, секреты в JSON, no-data выглядит как здоровый ноль.

## M9.6 — Алерт и восстановление

Предусловия: rule из задания, lookback=30 с, for/hold=30 с, ≥4 сетевых попытки в окне,
evaluation interval=1 с, cooldown=1 с; usage ошибок известен и бюджет достаточен. Назначение —
stdout/консоль и UI. Действие: штатные события A → непрерывный поток B (1 событие/с, минимум
75 с и до firing, каждое обращение в отдельном доверенном тестовом диалоге M3) → восстановить мок → такой же поток успешных новых событий минимум 75 с
и до resolved. Проверять ≥4 реальных попытки в каждом скользящем окне; open-breaker отказ
не считается сетевой попыткой. Одна пачка из 4 ошибок этот сценарий не заменяет.
Результат: нормальное состояние → firing с локальной записью → resolved. Связанные сигналы
сгруппированы, один retry не создаёт отдельное уведомление. Признак ошибки: показано только
firing без восстановления; alert не имеет видимого назначения; требуется отправка человеку.

Автотест с fake clock/метриками: всплеск короче окна не срабатывает; дребезг между порогами
не создаёт повторные firing/resolved. При отключённом мониторинге бизнес-обработка живёт,
доставка alert не гарантируется — это ограничение best-effort, а не пройденная проверка доставки.

## Сдача

Показать A/B от trace до dashboard, управляемый отказ коллектора и firing/resolved alert;
приложить команды, версии конфига/промптов, экспорт dashboard и ручной расчёт с `n/N`.
В артефактах M0 объяснить несколько run одного request, влияние оператора на долю авто и
ограничение best-effort. Выполнить отдельное ревью и гейты кода студента. Источник расходов —
БД-журнал; потеря телеметрии не оправдывает потерю строки оплаченного вызова в приложении.
