# course/ — техническая карта заданий

Один обязательный маршрут M0–M9. Это навигация по работе и проверкам;
вводная, аудитория и prerequisites остаются за автором курса.

## Приоритет документов

[contracts.md](contracts.md) задаёт общие правила сервиса; `zadanie.md` — поведение модуля;
`kriterii-priyomki.md` — наблюдаемые проверки; `detalnoe-review.md` — риски реализации;
`details/` — объяснение и примеры. [ai_context](../ai_context/README.md) помогает ориентироваться,
но не задаёт второй набор требований. `data/SCHEMA.md` описывает формат текущего пакета, и не переопределяет поведение сервиса.

| Файл модуля | Когда читать |
|---|---|
| README | Результат, зависимости и порядок чтения |
| zadanie | Перед реализацией: проблема, доступное исходное состояние, работа, вход/результат, контракт и границы |
| details | Вместе с соответствующим пунктом: теория, пример, ошибки и scope промпт-контракта |
| kriterii-priyomki | Сценарий: предусловия → вход → действие → наблюдаемый результат → признак ошибки |
| detalnoe-review | Отдельный ревью-вызов по M0: где реализация может нарушить требование |

## Приёмка и рабочий цикл

Сквозной путь растёт вместе с модулями: в M2 уже проверяется приём API → extract → БД;
в M3 тот же приём ведёт через вопрос и новую реплику; в M6 — через граф до локального действия.
До M8 запуск обработки допустим явной командой/тестовым runner после приёма. M8 заменяет
этот запуск доставкой через Redis Streams; впервые соединять компоненты только там нельзя.

Процесс [M0](M0-start/zadanie.md) сохраняется целиком: промпт-контракт → реализация →
**отдельное ревью** → проверки → запись понимания своими словами → отметка прогресса.
Уровни приёмки, рабочее соглашение и существующие артефакты M0 обязательны.

Каждый модуль предъявляет рабочий путь, значимый воспроизводимый сбой и объяснение решения.
Минимальные материалы: команда запуска, вывод сценариев/отчёт, версии конфигурации и промптов,
оставшиеся ограничения. Не нужна отдельная папка отчётов на каждый подпункт.

Функциональные инварианты (не выдуман адрес, не выдан чужой документ, не создан второй ticket)
проверяются на контролируемых входах и не усредняются с качеством модели. Качество оценивается
реальными предсказаниями отдельно от моков: показываются n/N, ошибки по группам, спорные эталоны
и неисполненные случаи. Бизнес-порог 15000 фиксирован; технические стартовые лимиты проверяются
по назначению; качество/эвристические пороги выбираются на dev до итогового test, по процессу M0.
