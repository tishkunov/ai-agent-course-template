# M6 — Агент и оркестрация · Задание

**Проблема.** Извлечение, классификация и поиск по отдельности не определяют, когда разрешено создать заявку, когда ждать ответа и как восстановиться после сбоя. Нужен один процесс, где видны состояние, основания решения и уже выполненные действия.

**Что уже работает.** M1 принимает обращения, M2 вызывает модель и учитывает каждый вызов, M3 хранит диалог и уточнения, M4 определяет тип/приоритет, M5 проверяет условия и отвечает по источникам. Узлы M6 вызывают эти компоненты, а не переписывают их. Общие правила — [contracts.md](../contracts.md); разметка `data/` не переопределяет их.

**Результат.** Один workflow в LangGraph. Внутри узла проверки модель выбирает разрешённые инструменты чтения и получает наблюдения; код ограничивает цикл, проверяет права и решает бизнес-маршрут. Запись ticket, выбор слота и отправка выполняются отдельным исполнителем действий. Оператор разбирает неоднозначность и редактирует факты, но не отключает ограничения.

**Порядок работы.** M6.1 → M6.4 → M6.2 вместе с правилами M6.10 → M6.7 → M6.6 → M6.5 → M6.8 → M6.9 → M6.3 → M6.11 → [сценарии](scenarios.md). Нумерация прежняя. M6.10 не является разрешением отложить защиту до конца. Мультиагенты, отдельная reflection-система, отмена/перенос/оплата и несколько ticket на исходную заявку не входят.

## 0. События, результат и схемы хранения

**Промежуточные результаты.** Сначала соберите T01 на реальном приёме и локальном исполнителе,
затем T05 (пауза/restart), T09 (сбой после эффекта), T12–T13 (редактирование/конфликт оператора)
и T16 (MCP). Остальные проверки выполняются вокруг этих состояний по мере реализации пунктов.
Инварианты, журнал действий и защиты остаются обязательными; новых заданий/отчётов нет.

**Сквозной запуск до очереди.** Локальный runner принимает исходный текст через `POST /requests`,
получает сохранённые request/message/event IDs и передаёт событие в граф. M3 собирает контекст (не запускает уточнение до выбора ветки),
M4 классифицирует, M2 извлекает, M5 проверяет реальные тестовые справочники, M6 фиксирует эффект.
В этом проходе не подменяйте целые M3/M4/M5 готовым State: фиксировать можно внешние LLM-ответы,
часы и симулятор канала. Изолированные T01–T18 по-прежнему используют свои моки. Существующую
живую демонстрацию tool loop выполните через этот runner; дополнительных платных серий не нужно.
M8 заменит явный запуск доставкой события worker-у, сохранив тот же вход графа.

На входе приложение создаёт `Event {event_id, event_type, request_id, message_id?, escalation_id?, received_at}`. `event_type` — `client_message`, `operator_decision` или техническое восстановление `recovery`. Доверенный контекст доступа передаётся отдельно сервером, не в аргументах модели. Для восстановления сохраняются исходные event_id и run_id; `recovery` обозначает способ запуска, не новую пользовательскую реплику. Повтор доставки сохраняет event_id; новый клиентский/операторский event получает новый run_id.

| Событие / состояние | Вход и работа | Итог |
|---|---|---|
| Новое сообщение, `new` | M3 регистрирует вход один раз → начало графа | новый run_id, `in_progress` |
| Новая реплика в `need_info/in_progress` | Обновить историю/контекст, инвалидировать зависимые факты, классифицировать заново | тот же request_id, новый run_id |
| Новая реплика в `escalated` | Только добавить сообщение оператору по M3; не запускать автоматический граф | тот же статус, без нового LLM-вызова |
| Решение оператора в `escalated` | Проверить JWT/роль, версию эскалации и состояния → применить один раз | новый run_id, переход по M6.9 |
| Повтор обработанного event_id | Вернуть сохранённый результат | без нового запуска/эффекта |
| Повтор незавершённого события / recovery | Поднять сохранённый run_id и актуальный checkpoint; проверить журнал действий | завершить остаток без повторного эффекта |
| Новая реплика после `done/rejected/failed` | Корреляция M3 определяет новое обращение или неоднозначность | прежний терминал не открывается |

Результат прогона: `{request_id, run_id, event_id, status, route_decision, route_reason, action_ids, call_ids}`. `need_info/escalated` завершают **текущий прогон**, обращение остаётся открытым. `done` — все необходимые действия подтверждены, `rejected` — отклонено, `failed` — сохранённая неустранимая техническая ошибка по общему контракту. Если сама БД недоступна, нельзя заявить, что ошибка/эскалация уже сохранена; событие остаётся незавершённым для восстановления.

**Миграция M6.** Добавить `requests.route_decision/route_reason`, персистентный Postgres checkpointer, `actions`, `escalations`, `tickets`. В `llm_calls` добавить nullable `run_id` для прежних записей; новые вызовы графа связываются с текущим запуском через обёртку шага M2, без изменения `LLMClient.complete`. `call_id` — ID фактического вызова (`llm_calls.id`); повтор записи использует тот же ID, новый вызов при recovery — новый ID.

- `actions`: `id`, `request_id`, `action_type`, уникальный `idem_key`, неизменяемые `args` и их fingerprint, `status=pending/done/failed`, `result`, `error`, `created_at/updated_at`; связь с run_id и `logical_intent`; уникальность `(request_id, action_type, logical_intent)` защищает резервирование намерения до выбора ключа сообщения.
- `tickets`: `id`, уникальный `request_id`, подтверждённые service/address/contact, nullable slot/master_id, status, created_at. Никакого мастера/слота из скрытого эталона.
- `escalations`: `id`, `request_id`, reason, ссылка/снимок версии состояния, `operator_decision`, patch/reason оператора, decided_by/decided_at. Решение применяется атомарно один раз; новая причина после нового прогона создаёт новую эскалацию, а повтор прежнего прогона — нет.
- Метаданные обработанных событий/запусков можно хранить рядом с checkpoint или в отдельной таблице: фиксируются начало, последний шаг и завершённый результат. Таблица очереди `processed_messages` остаётся M8; отдельный брокер в M6 не нужен.

## M6.1 — Где модель действительно принимает решение

**Проблема.** Линейная цепочка функций не объясняет, зачем здесь модель с инструментами.

**Что сделать.** На примере полной заявки разделить ответственность: модель предлагает `check_zone`, затем `check_price`; код проверяет аргументы, доступ, обязательные основания и порог суммы; оператор разбирает неразрешённый конфликт. Модель может выбрать порядок разрешённых чтений, но не отменить проверки и не вызвать запись. Зафиксировать эту границу в записи M0.

**Пример.** Модель предлагает `create_ticket` до цены → исполнитель read-only инструментов блокирует вызов; ticket не появляется, граф передаёт отказ оператору. Успешная и ошибочная трассы даны в [scenarios.md](scenarios.md).

**Контракт.** Предложенный вызов не равен выполненному. Trace содержит имя, проверенные аргументы/ссылку, исход и краткую причину; скрытые рассуждения модели не запрашиваются и не сохраняются.

**Проверка.** T01, T06 и объяснение границы в [приёмке](kriterii-priyomki.md).

## M6.4 — Состояние обращения и запуска

**Проблема.** После новой реплики старый адрес или разрешение могут незаметно остаться в плане.

**Что уже работает.** История и происхождение фактов — M3, результаты компонентов — M2/M4/M5.

**Что сделать.** Описать сериализуемый `State` с группами:

| Группа | Поля / источник |
|---|---|
| Идентичность | request_id, event_id, run_id; checkpoint thread_id=request_id |
| Версии | state_schema_version, facts_version, версия правил/промпта, версия источников/доступа |
| Вход | message_id, history_ref, граница summary, необходимый контекст M3 |
| Классификация | req_type, priority, routing_method, type_confidence, classification_reason M4 |
| Факты | extracted_fields с происхождением M2/M3, missing, clarification_reasons |
| Проверки | checks yes/no/unknown + reason/source + версия зависимых фактов; validation outcome/reason/sources M5 |
| Ответ по знаниям | found, text/ref, sources, reason M5.8 |
| Диалог | round_count, last_question_at; живут дольше одного запуска |
| Запуск | current_step, step_count, tool_proposals_count, tool_trace_ref, call_ids, error |
| Решение/эффект | route_decision/reason, план разрешённых action_id, подтверждённые action results |

История хранится в БД; в State только нужный контекст/ссылки, без бесконечного списка tool outputs. Клиенты SDK, соединения, ORM-объекты, JWT и секреты не сериализуются. Права при новом запуске и перед эффектом заново проверяются сервером; сохранённая версия доступа помогает инвалидировать результат, но не выдаёт разрешение.

**Пример.** Клиент меняет район: facts_version растёт, прежний check_zone становится неактуален; цена сохраняется только если услуга/объём и версия прайса не изменились. Проверки с неизвестной зависимостью безопасно выполнить заново.

**Контракт.** Вход/выход узла — данные State; каждый check имеет происхождение и версию. Нет общего выдуманного `confidence` для извлечения, RAG и классификации.

**Краевые случаи.** Старый checkpoint неизвестной схемы → контролируемая ошибка/оператор, без попытки выполнить старые args. При одновременных событиях одного обращения изменения сериализуются; не держать открытую SQL-транзакцию во время ожидания LLM.

**Проверка.** T12–T14.

## M6.2 — Инструменты чтения и ограниченный цикл

**Проблема.** Модель может выдумать аргумент, неизвестный инструмент или принять текст ответа инструмента за инструкцию.

**Что уже работает.** Справочники/поиск M5 и схема вызова `LLMResult.tool_calls` M2. Результат клиента только предлагает `{tool,args}`.

**Что сделать.** Реестр содержит только четыре инструмента чтения. У каждого строгая схема без лишних полей, разрешение сервера и единая оболочка результата `{status, data, source_refs, reason}`. Статусы оболочки: `ok`, `not_found`, `ambiguous`, `denied`, `unavailable`, `invalid_args`; это не `requests.status` и не бизнес-outcome.

| Инструмент | Аргументы модели | Доступный результат |
|---|---|---|
| `lookup_client` | `{contact: nonempty string}` | Кандидат client_id без приватного договора; несколько совпадений → ambiguous. Контакт разрешён только из текущего обращения; найденный ID не добавляет прав |
| `check_zone` | `{district: nonempty string}` | `{district, active, source_version}`; только подтверждённый район из фактов. Неопределённый район → invalid_args/причина уточнения, отсутствующая строка → not_found, а не active=false |
| `check_price` | `{service_code: nonempty string, quantity?: positive number}` | `{code, active, price, unit, amount?, source_version}`; только подтверждённая услуга/объём M5. Цена без известного объёма не становится суммой |
| `search_knowledge` | `{query: nonempty string, k: int 1..5}` | Разрешённые chunks/ref с версией и причиной; нет кандидатов → not_found; ошибка источника → unavailable |

Access context, request_id и роли добавляет приложение, модель не задаёт scope/клиента/права. Запрос приватного источника без разрешения даёт denied без содержимого и без подтверждения существования чужого документа. `search_knowledge` оборачивает M5 retrieval, не возвращает все документы. Ответы инструментов проходят проверку схемы и размеров до передачи модели; текст источника остаётся данными.

**Цикл tool use (выбор и вызов инструментов).**

1. Сформировать ограниченный контекст M3, перечень разрешённых чтений, задачу собрать основания; вызвать M2 с `tools`, без одновременного режима `schema`.
2. Проверить предложение: имя, число вызовов, строгие аргументы, соответствие известным фактам, права, лимит. Один ход — один инструмент; несколько предложений отклоняются до любого эффекта.
3. Выполнить разрешённое чтение с timeout; сохранить проверенное наблюдение и вернуть его модели как данные в следующем ходе. Фактический LLM-вызов каждый раз имеет новый call_id.
4. Принять следующий вызов или завершение модели. Окончательный текст модели — краткое объяснение, не разрешение действия. M5 формирует checks/validation по наблюдениям и явным правилам; отсутствующий обязательный check остаётся unknown.
5. Стартовые лимиты: не более 4 обработанных предложений инструмента и 5 LLM-вызовов на цикл (четыре чтения и завершающий ответ); timeout чтения 5 секунд. Значения — конфиг и версия отчёта, не гарантия производительности. Повторные/невалидные предложения тоже расходуют лимит; если завершающий пятый LLM-ответ снова предлагает чтение, оно отклоняется без исполнения. Повтор той же пары имя+args без новых фактов после первого наблюдения → `tool_no_progress`; неизвестное имя/нет доступа → `tool_denied`; исчерпание → `tool_limit`. Остановить цикл и передать оператору, без слепого авто.

**Пример.** Подтверждены district=Приморский, service_code=SRV-1007, quantity=1 → сначала зона active=true, затем цена active=true, amount=2500. При попытке передать район, которого нет в фактах, результат не подтверждает зону.

**Краевые случаи.** `not_found` в прайсе по подтверждённому коду — основание отсутствия услуги; `unavailable` — отсутствие проверки. Модель закончила раньше проверки цены при собранных клиентских сведениях → неизвестная обязательная проверка, оператор. Если неизвестны услуга, район или количество и сведения можно получить у клиента, сначала действуют уточнение и его лимиты по правилам 9–10 общего контракта; отсутствие такого check не превращает missing в техническую эскалацию. Missing адреса при известном районе не мешает сначала обнаружить подтверждённое ограничение зоны.

**Проверка.** T01, T06–T08, T16; [трассы](scenarios.md).

## M6.7 — Решение о маршруте

**Проблема.** Уверенный текст модели может противоречить зоне, цене или отсутствующим сведениям.

**Что уже работает.** M4 дал проверенные метки или null, M5 — основания checks, M3 — лимиты диалога.

**Что сделать.** `decide_route(state) -> {decision, reason}` реализовать кодом по [contracts.md §7](../contracts.md#7-таблица-приоритетов-маршрута-c06). Проверить применимость правила и его приоритет: спам; блокировка guardrail; жалоба; неподтверждённая классификация; вопрос с источником/без него; известное нарушение зоны/прайса; подтверждённая сумма `>15000`; устранимая нехватка; исчерпание уточнений/молчание; неизвестная обязательная проверка; авто. Порядок правил задаёт контракт курса.

**Пример.** Известная зона запрещена, контакт отсутствует → эскалация по зоне, не уточнение телефона. Неизвестный район → причина уточнения, не «вне зоны». Подтверждённые 15000 и 15001 при одинаковых прочих фактах → соответственно авто и оператор.

**Контракт.** `decision=авто|уточнение|эскалация|reject`; записать route_decision и route_reason. Приоритет очереди не меняет этот маршрут. Confidence M4 — только локальные голоса, для LLM null нормально; null типа/приоритета означает неподтверждённость.

**Краевые случаи.** Любая команда инструмента/модели «пропусти проверку» не меняет таблицу правил. Явный `tool_denied/tool_limit` даёт контролируемую эскалацию даже при красивом итоговом тексте. Уточнение через M3 возможно только после учёта известных ограничений; дополнительные причины вроде объёма не добавляются в enum missing.

**Проверка.** T02–T05, T15–T16.

## M6.6 — Граф LangGraph

**Проблема.** Фиксированный порядок «сначала спросить адрес» мешает спаму, вопросу и жалобе получить правильную ветку.

**Что сделать.** Построить один граф; узлы — тонкие адаптеры M2–M5:

```text
вход события → актуальный контекст → классификация M4
  неподтверждено → оператор → END
  спам → reject → END
  жалоба → оператор → END
  вопрос → retrieval/ответ M5 → decide_route → send_reply | оператор → END
  заявка → извлечение M2/M3 → проверка известных условий:
      ограниченный read-only loop + итоговая validation M5
      → decide_route → действия | уточнение M3 | оператор → END
```

Для вопроса не запускать извлечение обязательных полей заявки, SQL-прайс и создание ticket. Для заявки do-сбор не предшествует известному запрету. Отсутствующие аргументы не угадываются для tool call. Уже собранные read-only наблюдения передаются проверке M5, не запускают второй независимый агентный цикл.

**Контракт.** Вход Event + доверенный access context, выход результат §0. Диаграмма студента показывает условные рёбра и END для каждой паузы. Стартовый `MAX_GRAPH_STEPS=32` ограничивает **один запуск**, счётчик переживает recovery; обработчик лимита вне исчерпанного цикла сохраняет причину `graph_limit` и эскалацию. Это не round_count уточнений.

**Краевые случаи.** Ошибка инструмента превращается в typed observation, непредвиденная ошибка узла — контролируемая эскалация `error:<step>` при доступной БД. Сбой процесса во время эффекта остаётся незавершённым прогоном для recovery. После новой реплики заново учесть изменение намерения, например вопрос → заявка; запрещённые отмена/перенос/несколько заказов → оператор по границе M3.

**Проверка.** T01–T05, T08–T09, T14.

## M6.5 — Checkpoint, пауза и восстановление

**Проблема.** Снимок в памяти исчезает при перезапуске; снимок графа сам по себе не устраняет повтор побочного эффекта.

**Что сделать.** Подключить Postgres checkpointer LangGraph, `thread_id=request_id`. Фиксировать состояние после значимых узлов и перед действиями; версии зависимостей сохранить в lock. На `need_info/escalated` сохранить бизнес-состояние и завершить текущий запуск через END. Новый клиентский/операторский event поднимает состояние обращения, но входит в соответствующий обработчик событий §0, а не слепо продолжает старый action plan.

При техническом recovery восстанавливать прежний run_id и незавершённый шаг. Узел может исполниться повторно; защищает журнал M6.8, а не предположение «LangGraph никогда не повторяет». Сериализовать обработки одного thread и проверять версию перед commit, не удерживать SQL-транзакцию во время внешнего вызова. Checkpoint может отстать от бизнес-коммита: при старте сверить авторитетные messages/actions/requests и текущую версию, не повторять уже записанный вопрос или эффект.

**Пример.** q1 и need_info уже закоммичены в M3, процесс упал до checkpoint → recovery видит q1 по ключу и сохранённый round_count, завершает прежний run. Новая реплика e2 начинает новый run с обновлённым адресом.

**Контракт.** `resume(request_id, event)` различает восстановление и новое событие; API служебный, доступ к нему не выдаётся клиентским текстом. Persisted result одного события возвращается повторной доставке без запуска LLM.

**Краевые случаи.** Два одновременных resume не создают параллельных действий. Смена прав/версии фактов между паузой и запуском инвалидирует прошлое разрешение. Ожидание клиента/оператора не держит поток, транзакцию или HTTP-запрос открытым.

**Проверка.** T05, T09, T12–T14.

## M6.8 — Исполнитель действий и частичный сбой

**Проблема.** Ticket уже создан, но ответ не записан; повтор узла без журнала создаст второй ticket.

**Что уже работает.** Решение кода и проверки актуальны, M3 умеет идемпотентно регистрировать исходящее в локальном симуляторе.

**Что сделать.** Разделить read-only tools модели и исполнитель разрешённых действий:

| Действие | Разрешение и граница | Идентичность |
|---|---|---|
| `create_ticket(fields)` | Только подтверждённая заявка, актуальные допустимые проверки и decision=авто; один ticket исходной заявки | `request_id:create_ticket`, unique tickets.request_id |
| `schedule_slot(ticket_id, slot)` | Ticket существует, клиент явно выбрал конкретный допустимый слот, локальная фикстура доступности подтверждает его; бронирование атомарно защищено от гонки | `ticket_id:schedule_slot`; один слот на ticket, перенос вне объёма |
| `send_reply(request_id,text,kind,action_id)` | Вопросу — подтверждённый M5 ответ с источниками (`reply`); заявке — подтверждение выполненных действий (`confirm`) | `request_id:kind:action_id`; новое допустимое сообщение имеет новый сохранённый action_id |

Если пожелания времени нет, ticket без слота допустим и не вызывает вопрос о времени. «Завтра» само по себе не является выбранным доступным интервалом; сохранить пожелание без обещания брони. Если конкретный выбранный слот недоступен, передать оператору причину, не выдумывать альтернативу/не создавать второй ticket. Локальная фикстура доступности необходима для сценария слота; готового внешнего календаря в курсе нет.

Создание плана действий — кодом после проверки полномочий и route. До эффекта атомарно сохранить action_id/idem_key, неизменяемые args, версию разрешённых фактов и `pending`. Логическое намерение определяется типом действия и причиной сообщения: для ticket — `initial`, для слота — ticket_id, для reply — `answer:<event_id>`, для confirm — `ticket_confirm:<ticket_id>`. Уникальная тройка `(request_id, action_type, logical_intent)` создаёт одну запись даже при гонке; найденная запись возвращает уже выделенный action_id. Нельзя при каждом retry генерировать новый action_id. Для нового разрешённого ответа/уточнения ключ отличается; общий `request_id:send_reply` подавил бы будущие сообщения.

Выполнение:

1. Найти/зарезервировать намерение под уникальностью и сериализацией. `done` → вернуть сохранённый result. Те же ключ и другие args → `action_conflict`, не изменить старый эффект.
2. Перед ещё не выполненным действием снова проверить актуальные факты/права. Изменившееся разрешение отменяет исполнение pending, сохраняет failed с причиной и передаёт оператору.
3. Для локальных БД-действий эффект и `done/result` фиксируются **одной транзакцией**: ticket + journal, слот + journal, исходящее M3 + journal. `pending` может быть закоммичен заранее. До commit сбой не оставляет половину эффекта; после commit recovery возвращает result.
4. Известный неуспех без эффекта → failed с причиной; разрешённый технический retry использует тот же ключ/args и возвращает запись в pending под сериализацией. Не повторять неизвестный внешний эффект вслепую. Неустранимое/исчерпавшее допустимый retry действие → оператор, без done.
5. Когда все необходимые действия подтверждены, установить requests.status=done. При сбое после ticket до ответа сохранить in_progress для recovery; следующий запуск доигрывает только ответ.

Расширить `send_outbound` M3 keyword `action_id` для confirm/reply; clarify сохраняет `request_id:round:clarify` и атомарное увеличение круга. В обязательном локальном канале запись messages является отправкой; внешнюю сеть и exactly-once delivery этим не обещаем. Новый ответ не отправляется после терминального done произвольно: только новая разрешённая обработка по правилам корреляции.

**Пример.** act-T done, act-C pending → падение процесса → recovery с прежним run_id → act-T возвращает прежний ticket_id → act-C записывает одну confirm → done.

**Проверка.** T01, T09–T11, T17.

## M6.9 — Решения оператора

**Проблема.** Кнопка «подтвердить» не должна превращать устаревший адрес или запрещённый доступ в разрешённый эффект.

**Что сделать.** Создать минимальный защищённый JWT экран/эндпоинт: исходный текст, текущие поля и происхождение, тип/приоритет, неизвестные/отрицательные checks, разрешённые источники, предложенные действия, уже выполненные action results, причина эскалации и версия состояния. Показ приватного источника требует прав оператора; простое наличие JWT не даёт доступ ко всем клиентам.

`resolve_escalation(id, decision, expected_version, patch?, reason)` проверяет роль/область доступа, незавершённость эскалации и актуальность версии. Запись решения и резервирование его события атомарны. Повтор того же решения возвращает сохранённый результат, другое конкурентное решение/устаревшая версия — конфликт без эффекта.

| Решение | Переход и последствия |
|---|---|
| `confirm` | `escalated → in_progress`; повтор проверить необходимые актуальные основания → decide_route. Только разрешённое действие ведёт к done; прежний запрет оставляет/создаёт актуальную эскалацию |
| `edit` | Валидировать patch допустимых фактов (услуга, адрес, контакт, время/объём, тип/приоритет с основанием); записать происхождение от оператора, увеличить facts_version, сбросить зависимые checks/план → revalidate → decide_route |
| `reject` | `route_decision=reject`, `route_reason=operator_reject`, статус `rejected`, без автоматической заявки/ответа. Уже выполненные эффекты не откатываются: их видно оператору; отмена ticket не реализуется |
| `return` | `in_progress`; явная причина целевого уточнения, M3 регистрирует один вопрос в пределах лимита → need_info. При известном запрете заявки вопрос не разблокирует действие; запрет сначала проверяется и сохраняет эскалацию |

Для жалобы/вопроса return — явный запрос оператора уточнить конкретный факт, а не автоматическое требование адреса/контакта. После ответа начинается новый прогон и проверка типа; жалоба снова требует оператора. Пустой return без причины отклоняется. Если круги исчерпаны, нового вопроса нет, остаётся эскалация.

**После edit.** Адрес/район → повтор check_zone и связанных регламентов; услуга/объём → check_price, amount и применимые условия; контакт → lookup_client, но не расширение доступа; тип → новая применимая ветка; права/версия источника → заново retrieval и проверка источников. При неясной зависимости повторить все проверки. Проверенный операторский факт не перезаписывается старым summary. Новые клиентские сообщения, появившиеся после снимка, делают решение по старой версии конфликтным.

**Граница подтверждения.** В обязательном варианте оператор не отменяет запреты прав, guardrail, зоны, неактивной услуги и суммы >15000. Не добавляется отдельный механизм бизнес-исключений. Жалоба при confirm не становится заявкой; для изменения типа нужны явный patch и основание. Состояние с неизвестным обязательным условием не проходит авто.

**Краевые случаи.** При отсутствии решения обращение остаётся escalated в очереди, без автоматического confirm по таймеру. Редактирование уже выполненного ticket/перенос слота не поддерживаются: action_conflict/оператор, а не новый ticket.

**Проверка.** T10, T12–T13, T18.

## M6.10 — Проверки прав и границ с первого вызова

**Проблема.** Инструкция может прийти из текста клиента, документа, OCR, summary или tool output.

**Что сделать.** Системные инструкции задаёт приложение; данные отделяются от них, но одного разделителя недостаточно. Перед каждым инструментом проверить allowlist, схему и доверенный доступ; перед route/действием — актуальные основания и разрешение кода. Модель не выдаёт сама себе capability. Массовые/финансовые/отменяющие действия отсутствуют в реестре и не разблокируются словом confirm.

В ответах показывать только разрешённые факты и источники. В технических trace/log хранить безопасные ID, причины и маскированные аргументы; контакт/адрес нужны в рабочем состоянии и защищённом операторском интерфейсе, но не в общем логе. Чужой приватный chunk не должен сначала попасть в модель, а затем «спасаться» маскированием. Показывать точный запрещённый эффект в тесте: spy create_ticket не вызван, чужой фрагмент не попал в retrieval/ответ/trace, права не изменились. Прохождение нескольких тестов не доказывает невозможность всех инъекций.

**Контракт.** Guardrail применяется к dispatch инструментов и к входу/выходу решения/действия. Блокировка сохраняет причину и ведёт к оператору; полезные разрешённые запросы продолжают работать.

**Проверка.** T06–T07, T18; расширение набора атак — M7.

## M6.3 — Один инструмент через MCP

**Проблема.** Способ подключения меняется, а схема и ограничения инструмента должны остаться одинаковыми.

**Что уже работает.** `check_zone` напрямую выполняет чтение M5 под проверками M6.2.

**Что сделать.** Один локальный MCP-сервер stdio экспонирует только `check_zone`. Клиент приложения заменяет транспорт прямого вызова на MCP; модель видит прежнее имя/схему. Использовать общий валидатор и доменный адаптер; доступ выдаётся сервером приложения локальному каналу, не tool arguments. MCP-сервер принимает только чтение зон, перепроверяет схему/разрешённую операцию; он не выдаёт SQL write и не принимает путь/команду от модели. Сервер конфигурируется доверенным приложением, произвольные серверы из текста не подключаются.

**Пример.** Одинаковый подтверждённый district даёт один domain-result по direct и MCP. Для отсутствия разрешения read_zone оба пути дают denied до выполнения; timeout MCP → unavailable, а не «район вне зоны» и не скрытый переход в обход доступа.

**Контракт.** Доменная схема M6.2 неизменна, transport-errors нормализованы; протокольная версия/SDK закреплены в lock и конфиге. MCP — подключение инструмента, не отдельный агент и не сертификат безопасности.

**Проверка.** T16: один реальный локальный server/client roundtrip, затем контролируемые отказ/таймаут; внешняя LLM для транспортного теста не нужна.
