# M6 — Критерии приёмки

Требования — [задание](zadanie.md), конкретные фикстуры и trace — [scenarios.md](scenarios.md). M0, отдельное ревью и записи понимания сохраняются. M8/M9, брокер и дашборд не требуются: события запускаются локальным адаптером, результат и trace читаются из сохранённых данных.

Функциональные сценарии подменяют ответы M2/M4/M5 управляемыми результатами и проверяют реальный граф/БД/диспетчер. Отдельно показать один реальный LLM tool loop на той же безопасной фикстуре и один локальный MCP roundtrip. Реальный ответ может не совпасть с ожидаемым порядком; сохраняется фактическая трасса и ограничение, а не выдуманный успешный выбор. Мок доказывает ветвление, не способность модели выбирать инструменты.

## Сдача

В T05/T14 перехватить вход настоящего M4: в нём просьба, актуальные исправления, последний
вопрос и новая реплика по contracts §8. «Адрес: …» продолжает заявку, явный вопрос о гарантии
меняет ветку. Мок LLM получает этот контекст; тест не подставляет окончательный тип вместо M4.

Один рабочий путь T01 провести через приём API и локальный runner из задания: входной текст →
сохранённое событие → настоящие компоненты M3/M4/M5 → граф → ticket/confirm в БД. Подмена всего
классификатора, извлечения или validation готовым состоянием допустима в изолированных тестах,
но не заменяет этот проход; фиксированные ответы подставляются на границе LLM-клиента.
Существующую живую tool-демонстрацию выполнить этим же путём. В объяснении M6.11 сравнить
фактическое число вызовов выбора tools с фиксированными двумя чтениями без LLM-планирования.

Показать три результата: рабочий путь T01 и реальную tool-трассу; воспроизводимый сбой T09 с восстановлением; объяснение трёх вопросов задания. Приложить схему узлов/переходов, команды запуска, вывод T01–T18, версии конфигурации/промптов/схем и ссылки на trace/action results. Это один комплект материалов в процессе M0, не новая папка отчётов на каждый пункт.

Инварианты — отсутствие запрещённого эффекта, чужих данных и дублей — обязательны. Конкретный выбор инструмента моделью оценивается отдельно на фактической трассе; единичный успех не доказывает общего качества агента. Старые routing-эталоны сверяются с правилами курса и доступным входом; известные расхождения фиксируются, не используются для подгонки.

Применимые проверки кода и типов проходят по M0. Полное приложение в процессе редакторской переработки курса не создаётся; перечисленные сценарии выполняет студент при реализации.
