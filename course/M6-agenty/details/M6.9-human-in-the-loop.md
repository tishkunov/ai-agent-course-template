# M6.9 — Решение оператора тоже проходит проверки

Переходы и patch — [M6.9 задания](../zadanie.md), проверки — T10/T12/T13/T18.

HITL означает участие человека в процессе: система сохраняет причину и основания, человек принимает явное решение. Ожидание не держит воркер. Новая реплика в escalated попадает в историю для оператора, а не автоматически продолжает действия.

Пример: эскалация вызвана недоступностью зон. После восстановления сервиса confirm разрешает повторить проверку. Если зона теперь подтверждена и остальные условия допустимы, код допускает действие. Если зона запрещена, confirm не отменяет ограничение.

При edit адреса старый yes зоны не относится к новому адресу. Patch получает provenance оператора и новую facts_version, зависимые проверки сбрасываются, затем заново принимается маршрут. Изменение contact не выдаёт доступ к договору. UI показывает уже выполненные действия: reject не отменяет существующий ticket автоматически.

Две вкладки могут видеть одну эскалацию. expected_version и атомарная запись решения отличают повтор того же решения от нового конфликтующего. Если клиент успел добавить сообщение, решение по прежнему снимку нельзя молча применить.

Return имеет конкретную причину уточнения и использует механизм M3; он не означает «спроси все поля заявки» для жалобы. Лимит вопросов продолжает действовать. Политика отсутствия решения проста: обращение остаётся в очереди без автоматического confirm.

Промпт-контракт M0: запросить безопасный путь confirm/edit→revalidate→route и конфликт версий, а не прямой переход кнопки в act.
