# M6.8 — Один эффект при повторном исполнении

Ключи, схемы и границы — [M6.8 задания](../zadanie.md); fault-трасса — [scenarios.md](../scenarios.md); проверки — T09–T11/T17.

Проверка «done уже есть?» защищает только завершённую запись. Если процесс успел создать ticket, но ещё не отметил done, одного SELECT перед действием недостаточно. В локальном варианте ticket и actions.done/result фиксируются одной транзакцией, tickets.request_id уникален. При падении транзакция либо целиком есть, либо эффекта нет.

Pending означает зарезервированное намерение с неизменяемыми аргументами. Оно не означает, что эффект уже был, и не разрешает выполнить его повторно без сверки. Failed содержит известную причину; технический повтор допустим только с тем же логическим ключом и актуальным разрешением.

Разные эффекты имеют разные ключи. Один create_ticket на request допускает ключ request:create_ticket. Для исходящих этого мало: повтор confirm должен вернуть прежний результат, новое разрешённое сообщение — получить новый заранее сохранённый action_id. Связь action_id с намерением фиксируется до эффекта; UUID на каждом retry не обеспечивает идемпотентность.

Слот — конкретный разрешённый выбор из локальной фикстуры доступности. Пожелание «завтра» и отсутствие времени не являются подтверждённым бронированием. Перенос и несколько слотов здесь не реализуются.

M3 считает запись исходящего отправкой локального симулятора. Журнал и исходящее можно объединить транзакцией в одной БД. Для сетевого канала такая атомарность не возникает автоматически; курс не обещает внешнюю exactly-once доставку.

Промпт-контракт M0: спросить о гонке, pending и окне сбоя после эффекта, а не только о happy-path повторном вызове done.
