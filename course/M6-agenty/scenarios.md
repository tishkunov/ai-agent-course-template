# M6 — Учебные трассы и переходы

Это конкретные фикстуры для будущей реализации и объяснения [задания](zadanie.md), не новые исправленные файлы в `data/`. Проверки T01–T18 — в [приёмке](kriterii-priyomki.md).

## Фикстура полной заявки

Вход e1, request R1: «Замените смеситель по адресу ул. Учебная, д. 10, кв. 2, Приморский район. Телефон +7 921 000-11-22. Один смеситель». Доверенный канал подтверждает право обрабатывать это обращение, но не даёт доступ к частным договорам. Тестовый классификатор даёт заявка/средний; извлечение сохраняет указанные адрес/контакт/объём; сопоставление M5 явно подтверждает service_code=SRV-1007. Фикстура зоны: Приморский active=true, версия z1. Прайс: SRV-1007 active=true, price=2500, unit=услуга, quantity=1, amount=2500, версия p1. Применимые регламенты в этой фикстуре не добавляют ограничений, что явно записано в проверке; это не предположение о любых реальных данных.

## Успешный цикл и действие (T01)

| Шаг | Кто решил / вход | Наблюдение и состояние |
|---|---|---|
| 1 | Код принял e1 и создал run U1 | R1=in_progress, facts_version=1 |
| 2 | M4 → заявка; M2/M3 извлекли факты | missing=[], услуга/район/объём подтверждены |
| 3 | LLM call L1 предложил check_zone({district: Приморский}) | Код проверил имя, совпадение с фактами, read_zone; выполнил чтение |
| 4 | Tool observation | status=ok, data={active:true}, source_refs=[z1]; checks.zone=yes |
| 5 | LLM call L2 после наблюдения предложил check_price({service_code:SRV-1007,quantity:1}) | Код проверил схему и подтверждённый код/объём; выполнил чтение |
| 6 | Tool observation | status=ok, active=true, price=2500, amount=2500, refs=[p1]; checks.price/amount=yes |
| 7 | LLM call L3 без tool_calls завершил сбор | Краткий итог; разрешение создавать ticket из текста не извлекается |
| 8 | M5 проверил актуальные основания; код decide_route | validation=ок, decision=авто, reason=ок |
| 9 | Код зарезервировал action T с ключом R1:create_ticket | pending, args/facts_version зафиксированы |
| 10 | Транзакция эффекта T | Один ticket K1 + T=done/result={ticket_id:K1} |
| 11 | Код зарезервировал confirm C с устойчивой связью с K1 | Ключ R1:confirm:C; send_outbound(...,action_id=C) |
| 12 | Транзакция M3 исходящего и действия | Одна messages(out,confirm) + C=done; R1=done |

Слота нет: пожелание не поступило, вопрос о времени не отправляется. L1/L2/L3 здесь **call_id**, а T/C — **action_id**; это разные сущности. В рабочем trace использовать отдельные поля call_id и action_id, а не неоднозначный общий id.

## Ошибочное предложение (T06)

После шага 2 модель предлагает `create_ticket({address: "другой адрес"})`. Инструмента нет в allowlist чтений. Диспетчер сохраняет `tool_denied`, spy create_ticket имеет 0 вызовов, records tickets/actions эффектов нет. Граф завершает запуск с `escalated`, reason=guardrail:tool_denied. Даже валидные адрес/цена в тексте предложения не меняют запрет. Исполнитель действий получает разрешение только от кода после проверок.

## Пауза и новая реплика (T05)

| Событие | Изменение | Что не повторяется |
|---|---|---|
| e1 без адреса, район тоже неизвестен | U1: тип заявка → извлечение → проверены доступные условия → уточнение адреса q1 → need_info, round_count=1, END | Ни ticket, ни выдуманная отрицательная зона |
| Перезапуск | История/вопрос/round_count и checkpoint доступны | Не создаётся q2 |
| e2 «Адрес: ул. Учебная 10, Приморский район» | U2: обновить контекст → классификация → факты версии 2 → check_zone → остальные актуальные условия → действия | Адрес не берётся из старого summary |
| Повтор e2 после завершения | Сохранённый результат U2 | Нет U3, новых LLM-вызовов, второго ticket/confirm |

Если e2 вместо адреса содержит «Лучше скажите, какая гарантия?», тип проверяется заново: вопрос идёт по источникам, без автоматического создания ticket. Если источник не подтверждает ответ — оператор. Лимит вопросов ограничивает q1/q2, а не число внутренних шагов U1/U2.

В обоих вариантах перехватить вход M4: это `classification_text` из contracts §8, содержащий
исходную просьбу, последний вопрос и e2 один раз. Передача только «Адрес: …» или подстановка
старого типа вместо классификации — ошибка интеграции. Факты/gold в текст не дописываются.

## Частичный сбой (T09)

1. T=done, ticket K1 создан; confirm C=pending, но исходящего ещё нет. Процесс падает до его транзакции.
2. Recovery поднимает R1/U1/e1, даже если checkpoint старее записи T. Запись actions — основание выполненного эффекта, а не предположение по current_step.
3. Исполнитель возвращает T.result, не создавая K2. Выполняет C с прежним action_id; одной транзакцией сохраняются out и C=done. Статус становится done.
4. Сбой после commit C, но до checkpoint также безопасен: out уже есть, результат возвращается, не отправляется повторно.

Этот сценарий доказывает атомарность **локального симулятора**. Для реального сетевого канала нужен контракт идемпотентности/сверки эффекта; наличие unique actions само по себе не доказывает внешнюю exactly-once доставку.

## Оператор и новое основание (T12–T13, T18)

R2 escalated из-за недоступной зоны. Оператор с разрешением на R2 видит версию 4. Сервис зоны восстановился: confirm создаёт событие op1/run U2, заново проверяет зону/актуальные условия, после разрешения кода выполняет действие. Повтор op1 возвращает результат.

Если оператор edit меняет адрес на район X, а фикстура zones(X).active=false, прежний yes зоны инвалидируется. Новый check_zone даёт no, итог снова escalated; ticket не создаётся. Подтверждение запрещённой зоны не меняет этот исход. Две вкладки отправляют решения на версию 4: одно принимается, второе получает конфликт; два действия не возникают.

## Карта веток

| Вход / основание | Разрешённая ветка | Сохранённый исход |
|---|---|---|
| Реклама без адреса, подтверждённый спам | reject, без извлечения/прайса/уточнения/ответа | rejected |
| «Мастер не пришёл», подтверждённая жалоба | очередь оператора | escalated |
| Вопрос о гарантии, разрешённый источник и подтверждённый ответ M5 | один reply с источником, без ticket | done |
| Тот же вопрос, found=false/конфликт источников | оператор без выдуманного ответа | escalated |
| Заявка, услуга неизвестна | уточнение услуги, прайс не считается отрицательным | need_info |
| Заявка, известный район запрещён и контакта нет | оператор по зоне, без сбора телефона | escalated |
| Заявка, неизвестный район и нет других запретов | уточнение, затем лимит/оператор | need_info / escalated |
| Заявка, все условия допустимы, amount=15000 | ticket + confirm | done |
| То же, amount=15001 | оператор | escalated |
| Модель завершила цикл без обязательного основания при собранных клиентских сведениях | оператор, unknown не превращается в yes; неизвестные услуга/район/количество, доступные клиенту, сначала идут в уточнение по правилам 9–10 | escalated / need_info по причине |
| Повтор одного инструмента без новых фактов | tool_no_progress, без записи заявки | escalated |
| Новая реплика в escalated | только история для оператора | escalated |

Все точные суммы/адреса/права в этих трассах заданы фикстурами или исходным текстом. Старые routing-эталоны с вопросом→эскалация не переопределяют ветку ответа по источникам.
