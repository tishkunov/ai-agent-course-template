# Критерии качества: DoD, пороги, рубрика

## 7. Критерии качества (консолидированный DoD + методика порогов + рубрика)

### 7.1 Три уровня приёмки (см. также `course/M0-start/zadanie.md` §M0.3)

1. **Пункт** (`Готово, когда` внутри M.x) — самый частый уровень, закрывается по циклу M0.2.
2. **Модуль** (`Интеграционная приёмка` + `Definition of Done M{n}`) — сквозной сценарий модуля целиком (см. таблицу 7.2), плюс все пункты внутри закрыты.
3. **Курс** (S1–S10 целиком) — сквозной прогон всего пайплайна, включая HITL, устойчивость (ретраи, чекпоинты), безопасность (M7), нагрузку/стоимость (M8), наблюдаемость (M9).

### 7.2 Где находится Definition of Done

Полная приёмка — в `course/M{n}-*/kriterii-priyomki.md`, ссылки по всем модулям —
[карта ревью](09-master-cheklist-review.md). Сводная копия DoD не ведётся, чтобы снятая практика
не возвращалась через обзорный файл. [Техническая карта](../../course/README.md) показывает
результаты и обязательный объём. M0 не изменён.

Для каждого модуля студент показывает рабочий путь, значимый сбой и объясняет решение своими
словами. Это дополняет все шаги и артефакты M0. Функциональные инварианты проверяют контролируемыми
сценариями; качество моделей — реальными предсказаниями, отдельно от моков. Показываются n/N,
спорные случаи и невыполненные проверки; отсутствие примеров не считается успехом.

### 7.3 Методика обоснования порога (процесс M0 сохраняется)

Бизнес-константа `amount > 15000` не подбирается на данных. Технический лимит проверяется на своём
сценарии отказа; порог качества выбирается на dev до test. Следующие шаги применяются к выбираемым
параметрам по M0, не разрешают менять бизнес-правило или настраивать промпт на итоговом test.

1. Спросить у ИИ 2–3 варианта значения с явным trade-off (что выигрываем/что теряем на каждом).
2. Где есть синтетический eval-набор — прогнать хотя бы 2 варианта и сравнить метрику (не выбирать «по интуиции», если можно измерить).
3. Записать в `docs/decisions.md`: пункт ТЗ, рассмотренные варианты, выбранное значение, причина.
4. Если данных для прогона нет (совсем новый порог без датасета) — фиксировать как гипотезу с явной пометкой «не откалибровано, требует данных» — это честнее, чем выдуманная точность.

### 7.4 Когда модуль считается сделанным

- Модуль сделан = все пункты M.x закрыты по циклу (промпт-контракт → код → отдельное ревью → тесты → «Понять» своими словами) **и** пройдена интеграционная приёмка модуля.
- **Известное ограничение** (см. M0.7) допустимо для некритичных для продолжения пунктов — фиксируется, не блокирует переход дальше, но остаётся в `decisions.md` как долг и должно быть закрыто до сдачи финального сквозного сценария (M9 приёмка курса).
- Пункты, помеченные в `../3-priyomka/09-master-cheklist-review.md` как «критично» (например M8.6 «решения по обращению не берутся из кеша», M6.10 guardrails, M5.10 access-фильтр, M1.7 идемпотентность) — не подлежат отсрочке как «известное ограничение»: это пункты безопасности/корректности данных, а не оптимизации.
