# Детальное ревью кода — чек-лист под стек курса

Как применять: это раскладка встроенного скилла `/review` / сабагента `reviewer` на конкретный стек (Python 3.12 / FastAPI / pydantic v2 / SQLAlchemy 2.0 async + asyncpg / Alembic / Redis / LangGraph / MCP / pgvector / sentence-transformers / Langfuse). Построчные формулировки «Ревью» из ТЗ каждого пункта — в `course/M{n}-*/detalnoe-review.md`; здесь — что именно смотреть в коде, чтобы эти формулировки закрыть.

**Ревью — отдельный вызов (шаг 4 цикла M0.2).** Не тем же ответом, где сгенерирован код: самопроверка систематически мягче. Ревьюим дифф, а не всю базу.

## Вход

- Git-дифф (обязательно)
- `course/M{n}-*/zadanie.md` — Требования/Контракты/Краевые случаи (что код обязан делать)
- `course/M{n}-*/detalnoe-review.md` — строка текущего пункта + сводный чек-лист модуля
- `docs/tech-design.md` (если был), `ai_context/3-priyomka/11-stabilnye-kontrakty.md` (что нельзя ломать)

## Выход → `docs/code-review.md`

Ревью либо actionable, либо шум. У каждой находки: severity, `file:line`, конкретный фикс. «Можно улучшить» — не находка; «упадёт, когда X» — находка.

## Уровни severity

| Уровень | Определение | Пример на этом проекте |
|---|---|---|
| CRITICAL | потеря/порча данных, обход авторизации, утечка секретов, простой сервиса | нет `require_operator` на операторской ручке; решение по обращению берётся из кеша (M8.6); guardrail-обёртка отсутствует на узле S8–S9 (M6.10) |
| HIGH | почти наверняка баг в проде при нормальном использовании | не заатывленный async (`await` забыт); транзакция не откатывается в `except`; ретрай LLM без предела; гонка на `idem_key` даёт 500 |
| MEDIUM | проблема поддерживаемости, неочевидный footgun, перф под нагрузкой | N+1 запрос в цикле; `Any`, скрывающий реальную ошибку типа; отсутствует индекс под новый `WHERE`; промпт-версия не логируется |
| LOW | мелочь, на которую споткнётся следующий разработчик | вводящее в заблуждение имя; нет детали в сообщении об ошибке |

## Чек-лист (по разделам; пропускать неприменимые)

### Корректность
- [ ] Все ветви возвращают значение или бросают исключение (нет неявного `None` там, где ждут объект)
- [ ] Async-функции действительно ожидаются — нет fire-and-forget без намерения; нет синхронных блокирующих вызовов внутри async (`time.sleep`, sync-драйвер, sync `requests`, тяжёлый CPU в loop)
- [ ] `asyncio.gather` обрабатывает частичные отказы (одно исключение не роняет всю пачку молча)
- [ ] Коды ошибок верные: 409 на конфликт, 422 на бизнес-правило, 404 на «не найдено», не всегда 400
- [ ] Транзакция БД коммитится ИЛИ откатывается во ВСЕХ ветвях, включая `except`
- [ ] Границы циклов/пагинации: off-by-one на лимитах, номерах страниц, срезах
- [ ] Проверка `None` перед доступом к вложенным полям (особенно разбор ответа LLM/внешнего)
- [ ] Дата/время: timezone-aware, в БД `timestamptz` в UTC, сравнения корректны

### Типизация (pydantic v2 / mypy|pyright)
- [ ] Нет `Any` ради подавления ошибки типа — найден реальный тип
- [ ] Нет `# type: ignore` без комментария-причины
- [ ] Возвращаемые типы явно объявлены на публичных функциях и методах сервисов
- [ ] Внешний вход (ответы API, `json.loads`) типизирован как узкий тип/схема, не `Any`
- [ ] pydantic-схемы: `extra="forbid"` там, где вход с границы; схема ≠ ORM-модель (не тянут ORM-типы)

### БД: SQLAlchemy 2.0 async + Alembic
- [ ] Сессия — на запрос через `Depends` (открыть → commit/rollback → закрыть); нет утечки соединений
- [ ] Все пользовательские значения параметризованы — нет конкатенации/f-string в SQL
- [ ] N+1: циклы с `session.get`/`find` внутри → батч (`WHERE id = ANY(...)` + dict)
- [ ] Под каждый новый `WHERE`/JOIN-столбец есть индекс; нет `SELECT` без `LIMIT` по большой таблице
- [ ] Миграции совпадают с моделями: повторный `alembic revision --autogenerate` пуст (нет дрейфа); `naming_convention` задан
- [ ] `downgrade()` осмысленный, не падает; дефолты на стороне БД — в миграции, не только в модели
- [ ] Репозиторий не отдаёт «живые» ORM-объекты за пределы сессии без нужды
- [ ] Если трогается `requests`/`llm_calls`/`messages`/`State`-схема прошлых модулей — это decision в `docs/decisions.md`, не тихая правка (`ai_context/3-priyomka/11-stabilnye-kontrakty.md`)

### Кеш / Redis
- [ ] У каждой записи в кеш есть TTL (нет `set` без `ex`)
- [ ] Инвалидация на каждой записи, которая могла повлиять на закешированное — не только TTL
- [ ] Ключ детерминирован, уникален, с namespace (`rag:chunk:{hash}`, не голый id)
- [ ] Роль Redis учитывается по модулю: M1 допускает приём без него, M8 при отказе публикации возвращает enqueue_failed; отказ только кеша допускает поиск без кеша. Клиент не пересоздаётся на запрос
- [ ] **Решения по обращению не берутся из кеша** — кешируются только знания (RAG/под-промпты), не маршрут/действие (M8.6, CRITICAL)
- [ ] Порог семантического кеша выбран на dev; доступ и версии проверяются до похожести, есть инвалидация/TTL

### API / FastAPI
- [ ] Каждая новая ручка имеет явный `Depends` авторизации (`require_api_key` для приёма, `require_operator`/JWT для операторских) или явно помечена публичной
- [ ] У каждой ручки — DTO с валидацией; ответ типизирован `response_model`
- [ ] В роуте нет доступа к БД напрямую и нет бизнес-логики — только делегирование в сервис
- [ ] Единый обработчик ошибок (доменная ошибка → HTTP-код), не try/except в каждом роуте; наружу `{error, detail}`, без стека
- [ ] Списочные ручки пагинированы (нет ручки, возвращающей неограниченное число строк)
- [ ] Чувствительные поля возвращаются только в разрешённом контексте; собственный адрес допустим в подтверждении по M7, чужие данные и технические секреты не выдаются

### LLM-вызовы (M2)
- [ ] Все вызовы модели — через единый `LLMClient`; SDK провайдера не протекает в сервисы/роуты; ключи из env; клиент-синглтон
- [ ] Промпт вынесен в `prompts/<step>_v<N>` и версионирован; версия пишется в `llm_calls.prompt_version`; нет технических секретов и чужих данных; необходимые собственные поля передаются по контракту, raw-контекст не уходит в технические логи
- [ ] `temperature` из конфига промпта/вызова, не хардкод вразнобой; для извлечения ≈0
- [ ] Ответ модели всегда валидируется схемой до использования; ретрай ограничен (не бесконечный); нет парсинга «регэкспом на глаз»
- [ ] Аргументы tool-call валидируются схемой; в M2 tool-call не выполняет реальных действий
- [ ] Каждый фактический вызов имеет новый `call_id` и запись `llm_calls`; повтор сохранения одного вызова идемпотентен по ID. `cost_total` — сумма известных расходов; estimated и unknown показаны отдельно, usage не выдуман
- [ ] Стабильная (инструкция+few-shot) и переменная (текст обращения) части промпта не перемешаны — под prompt caching
- [ ] Таймаут на вызов из конфига; ошибка/таймаут → типизированный `LLMError`, не сырой 500

### Агенты / LangGraph (M6)
- [ ] Состояние графа явное, сериализуемое, персистентное (checkpointer, не in-memory в прод-режиме); нет глобального/in-memory состояния между запросами
- [ ] Граф отражает машину состояний из `ai_context/1-proekt/03-statusy-i-perehody.md`; лимиты шагов, фактических вызовов и кругов различены; после исчерпания сохраняется конкретная причина, recovery не обнуляет лимит
- [ ] Узлы не дублируют логику M2–M5 (LLM — через клиент, retrieval/валидация — через M5, до-сбор — логика M3)
- [ ] Ключ действия соответствует логическому намерению M6.8; намерение резервируется до выдачи action_id, локальный эффект и результат атомарны. Модель предлагает только чтения, запись выполняет код после проверок
- [ ] Инструменты (в т.ч. MCP) валидируют имя, аргументы и права до выполнения, возвращают типизированные ошибки; текст наблюдения остаётся данными
- [ ] Guardrail-обёртка на узлах S8–S9: входной текст — в позиции данных, не инструкции; маскирование технических записей по M7; необходимые собственные данные допускаются в ответе. Правила маршрута по contracts, причина сохраняется
- [ ] Recovery использует прежний run; новая реплика пересобирает контекст и проверки. В escalated реплика только оператору; confirm/edit проверяют роль, версию и условия заново

### RAG / pgvector (M5)
- [ ] Нет пути «ответить без найденного» — источник обязателен, иначе «данных нет», не выдумка
- [ ] Структурные проверки (зона/прайс/клиент) — SQL по справочникам, не через LLM; регламентное — RAG
- [ ] Ошибка retrieval (не нашли) и ошибка генерации (нашли, но исказили) диагностируются раздельно; yes/no/unknown отдельных условий различены; итоговые outcome взяты из contracts
- [ ] Фильтры retrieval (в т.ч. access_scope, M5.10) применяются в запросе, не постобработкой; источник возвращается
- [ ] Чанкинг воспроизводим, метаданные не теряются; индекс на месте, инкрементальное обновление без дублей/сирот; реранк ограниченного N, версия фиксирована, эксперимент не обещает обязательного улучшения

### ML (M4)
- [ ] Модель эмбеддингов зафиксирована в конфиге; векторы нормализованы где нужно; батчинг
- [ ] Одна модель/revision по M4.1; manifest train/dev/test проверен по текстам и семействам. Пересечения старого test явно указаны, метрики не названы независимой оценкой; база векторов воспроизводима
- [ ] Порог согласованности соседей выбран на dev; приоритет проверяется отдельно, невалидный/неоднозначный LLM не разрешает авто. Порог дубля и кластеризация в M4 не требуются

### Наблюдаемость (M9)
- [ ] При исправном экспорте trace одного run покрывает исполненные шаги и фактические попытки; на паузе закрывается. Недоступность коллектора не блокирует бизнес-обработку, но может потерять телеметрию
- [ ] Логи структурные с `request_id`/`event_id`/`run_id`/`trace_id`; PII/секреты не светятся в открытом виде
- [ ] Стоимость по run/обращению сверяется с журналом M2 при исправном экспорте; неизвестные значения не нули. У долей указан знаменатель/период, рабочая latency отделена от ожидания; технические и бизнес-метрики разведены

### Тесты (в этом же диффе)
- [ ] Новый код покрыт — нет непокрытого happy-path в MUST-историях
- [ ] Тесты проверяют поведение (HTTP-ответ / состояние БД), не реализацию (`assert repo.save.called`)
- [ ] Имена тестов описывают ожидаемое поведение (`test_returns_401_when_token_expired`)
- [ ] Интеграционные тесты бьют в реальную тестовую БД (не только моки для запросов к БД)
- [ ] LLM/инструменты замоканы на уровне интерфейса (`LLMResult`), не SDK провайдера; реальный вызов — `@pytest.mark.live`
- [ ] Auth-тесты: с валидным кредом, без креда, с чужой ролью/протухшим токеном

### Безопасность (быстрый проход — полный через `/security-review`)
- [ ] Нет секретов/ключей/токенов в коде и тестах; секреты без дефолтов
- [ ] Нет SQL из конкатенации; нет `eval`/`exec`/shell из пользовательского ввода
- [ ] Недоверенный текст не попадает в промпт в позиции инструкции (f-string склейка system+вход — красный флаг)
- [ ] JWT: алгоритм зафиксирован (не из токена), `exp` проверяется, `alg=none` отбит; ключи сравниваются безопасно
- [ ] Ответ не отдаёт стек-трейсы/внутренние сообщения об ошибках наружу

Этот технический список не добавляет новую инфраструктуру или задания к модулю.

## Режим ревью дизайна (когда на входе `docs/tech-design.md`, не код)

- [ ] У каждого эндпоинта явно указана аутентификация (не «очевидно»)
- [ ] Модель данных: PK, `created_at`/`updated_at`, индексы под запросы; FK с явным `ON DELETE`
- [ ] Ни одна списочная ручка не возвращает неограниченно (пагинация обязательна)
- [ ] Стратегия кеша: у каждого ключа TTL и инвалидация; кеш не влияет на решения по обращению
- [ ] Есть раздел краевых случаев, ≥5 пунктов, специфичных для этой фичи
- [ ] Неочевидные решения — с записью в `docs/decisions.md` или помечены как открытый вопрос

## Принципы ревьюера

1. Ревьюим дифф, а не всю базу — комментируем только то, что изменилось.
2. Одна находка на проблему — не повторять один и тот же дефект на каждом вхождении, если корень один.
3. Не заводим находки на предсуществующие проблемы — только если этот дифф делает их хуже.
4. Не редизайним фичу — если неверен дизайн, это находка ревью дизайна, не кода.
5. Хвалим сделанное хорошо — раздел «Хорошо» не опционален, он закрепляет правильные паттерны.
6. Проверяем «что код обязан делать по ТЗ» (Контракты и Краевые случаи), а не «что код делает».
