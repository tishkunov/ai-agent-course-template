# Расширенный реестр ролей агентов + стратегия привязки

## Стратегия привязки (Binding Strategy)

Claude Code уже реализует часть ролей встроенными сабагентами и скиллами: `designer`, `design-reviewer`, `planner`, `implementer`, `reviewer`, `researcher` + скиллы `/design`, `/design-review`, `/plan`, `/implement`, `/review`, `/security-review`. **Где есть встроенное — использовать его напрямую**, не переизобретать промптом.

Роли без встроенного эквивалента установлены как настоящие проектные сабагенты в `.claude/agents/*.md` (запускаются как `Agent(subagent_type: "analyst"|"plan-reviewer"|"tester"|"final-reviewer"|"debugger", ...)`, каждый со своим системным промптом и набором инструментов; поле `model` не задано — модель на выбор пользователя, ориентир по нагрузке — `../5-instrumenty/16-model-tiering.md`) — это не просто описания ниже, а рабочие файлы.

- **Built-in subagent: `<имя>`** — вызвать `Agent(subagent_type: "<имя>", ...)`.
- **Built-in skill: `/<имя>`** — через `Skill(skill: "<имя>")`.
- **Проектный сабагент (`.claude/agents/`)** — эквивалента среди встроенных нет; здесь живёт стек-специфичная ценность (Python/FastAPI/SQLAlchemy/pgvector/LangGraph паттерны, продуктовое обрамление, ревью плана, холистический pre-ship гейт).

| Роль | Привязка | Почему |
|---|---|---|
| `analyst` | `.claude/agents/analyst.md` | встроенный `researcher` анализирует *код*, не бизнес-требования |
| `architect` | Built-in: `designer` | тот же контракт выхода (`docs/tech-design.md`); подать `requirements.md` доп. входом |
| `design-reviewer` | Built-in: `design-reviewer` | прямое совпадение — READY/BLOCKED |
| `planner` | Built-in: `planner` | прямое совпадение — `tech-design.md` → `implementation-plan.md` |
| `plan-reviewer` | `.claude/agents/plan-reviewer.md` | встроенного шага ревью плана нет |
| `implementer` | Built-in: `implementer` | прямое совпадение — одна итерация из плана |
| `code-reviewer` | Built-in: `reviewer` (или `/review`) | ревью диффа по severity, общий + security проход |
| `security-reviewer` | Built-in: `/security-review` | OWASP-аудит pending changes |
| `tester` | `.claude/agents/tester.md` | нет встроенного, пишущего тесты против матрицы покрытия критериев |
| `final-reviewer` | `.claude/agents/final-reviewer.md` | нет встроенного холистического pre-ship гейта |
| `debugger` | `.claude/agents/debugger.md` | нет встроенной роли корневого анализа причины |
| `formatter` | инлайн, без сабагента | достаточно просто сделать в оркестрирующей команде без отдельного вызова |

## Проектные сабагенты — контракты

Полные системные промпты — в `.claude/agents/*.md`. Здесь только сводка контрактов.


### `analyst`
Неоднозначный запрос → точные тестируемые требования. **Вход**: сырой запрос (+ опц. существующий `requirements.md`). **Выход**: `docs/requirements.md`.
Разделы: постановка проблемы (только проблема, без решения и технологий); роли-акторы; user stories (одна цель на историю; критерии Given/When/Then; одно утверждение на критерий; у каждой MUST ≥1 error-path; без деталей реализации); NFR с числами; вне скоупа (≥3); затронутые сущности данных (что трогаем, не как структурируем); открытые вопросы (допущение либо эскалация 🔴); DoD фичи.
Техники: детектор неоднозначности (для каждого глагола — что именно значит); сканер противоречий; флаги scope creep (новый внешний сервис; >3 несвязанных модуля; L без MUST).

### `plan-reviewer`
Аудит плана до написания кода. **Вход**: `implementation-plan.md` + `tech-design.md` + `requirements.md`. **Выход**: `docs/plan-review.md`. Чек-лист и severity — см. `../4-process/18-sdlc-pipeline.md` фаза 5.

### `tester`
Осмысленные тесты как настоящие гейты качества. Первый вопрос к любому тесту: «если он проходит — про какой баг я теперь знаю, что его нет?»
**Вход**: `requirements.md` (критерии → интеграционные тест-кейсы), `tech-design.md` (контракт + краевые → сценарии), файлы текущей итерации. **Выход**: набор тестов + `docs/test-report.md` с матрицей покрытия критериев.
Пирамида: много юнит (логика, ветки), средне интеграционных (все эндпоинты + БД, **никогда не мокать БД** — отдельная тестовая БД), мало E2E (критические пути). Правила: имя описывает поведение; одно утверждение на тест; падение диагностично; нет тайминговой флакости; тесты независимы (`afterEach` чистит); проверять контракт (HTTP-ответ/состояние БД), не «сервис был вызван».
Цели покрытия: ≥80% нового кода, ≥90% ветвей новых методов, 100% auth/критических путей, 100% MUST-критериев имеют интеграционный тест. Покрытие ≠ качество: тест, который всегда проходит, не считается.

### `final-reviewer`
Холистическое pre-ship ревью (не код-ревью — оно уже было). Вопрос: «держится ли вся система вместе? готов ли я быть на дежурстве сегодня ночью?»
**Вход**: все доки + запущенное приложение (staging). **Выход**: `docs/final-review.md` — APPROVED | APPROVED WITH CONDITIONS | BLOCKED.
Измерения: трассируемость требований (каждый MUST-критерий → чем проверен; непроверенный → BLOCKED); соответствие API-контракту (реальный запрос без токена → 401); целостность данных (миграция прогнана, `down()` протестирован, нет орфанов); наблюдаемость (бизнес-события в INFO, ошибки с контекстом, нет PII в логах, request_id есть); производительность под нагрузкой vs NFR; спот-чек безопасности; готовность отката (план отката задокументирован, feature flag на рискованное).

### `debugger`
Систематический корневой анализ. Научный подход: наблюдать → гипотеза → тест → вывод. Никогда не чинить симптом.
Протокол: (1) собрать доказательства до мнений — полный стек, точное сообщение, время, частота, охват, последние 10 коммитов; (2) классифицировать (логическая ошибка / гонка / порча данных / конфиг-окружение / регрессия зависимости / утечка памяти); (3) `git bisect` если воспроизводимо и есть pass/fail кейс; (4) на каждую гипотезу — что подтвердит, что опровергнет, самый дешёвый тест (лог-строка < юнит-тест < запрос к БД < полный репро).
**Выход**: `docs/bug-report.md` — корневая причина (1 абзац), триггер, доказательства, затронутый код (`file:line`), фикс (минимальный, с диффом), регресс-тест (падает до, проходит после), похожие паттерны (grep).

### `formatter`
Сырой вывод агентов → структурированный док / описание PR / сводка. Без рассуждения.
