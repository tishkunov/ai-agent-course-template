# Плейбуки: bug-hunt / refactor / perf-audit / db-migration / full-verify

## Bug Hunt — глубокое расследование

Триггер: баг не пойман тестами; прод-инцидент; флакающий тест; регрессия производительности.
Вход: сообщение/стек, шаги репро (или «интермиттентно»), окружение, последние коммиты, логи.

1. **Триаж** (`debugger`) — классифицировать тип, затронутые слои (БД/API/кеш/фронт/инфра), blast radius, severity P1/P2/P3 → `docs/bug-triage.md`.
2. **Гипотезы** (`debugger`) — 3–5 штук по убыванию вероятности; на каждую: что должно быть истинно, что подтверждает/опровергает, дешёвый тест → `docs/bug-hypotheses.md`.
3. **Расследование** — по одной гипотезе (сначала вероятная): минимальный репро/диагностический запрос → подтвердить/отбросить. Инструменты: `git bisect`, запрос к БД на снапшоте, временное debug-логирование, чтение состояния кеша, `EXPLAIN ANALYZE`.
4. **Корневой анализ** (`debugger`) — трассировать точный путь кода, найти изначально неверное допущение/недостающий guard, grep похожих мест → `docs/bug-report.md`.
5. **Фикс + тест** (`implementer`) — сначала регресс-тест (TDD для фикса): падает до, проходит после; проверить похожие паттерны.
6. **Верификация фикса** (`reviewer`) — быстрый проход по диффу фикса: адресует причину, а не симптом; новых проблем нет; регресс-тест осмыслен.

## Safe Refactor — рефакторинг без смены поведения

Ключевое ограничение: поведение до и после идентично.

1. **Зафиксировать текущее поведение** (`tester`) — характеризационные тесты, ловящие текущее поведение (включая краевые и известные причуды); 100% проходят на текущем коде → это страховочная сеть. Гейт: без 100% зелёных характеризационных тестов рефакторинг не начинать.
2. **Определить скоуп** (`designer`) — какие файлы меняются, какие точно НЕ (граница blast radius), целевая структура, ломающие изменения публичного API → `docs/refactor-plan.md`.
3. **Инкрементально** (`implementer`) — одно логическое изменение за раз (переименовать / извлечь / переместить — не вместе); прогонять характеризационные тесты после каждого шага; коммит после каждого зелёного; тесты сломались → откат немедленно.
4. **Пост-ревью** (`reviewer`) — все характеризационные проходят; новых `Any` нет; публичный API не изменён (или версия поднята); код реально проще, а не просто другой; нет смены поведения, замаскированной под рефакторинг.

## Perf Audit — производительность

Триггер: регрессия времени ответа; всплеск CPU БД; безлимитный рост памяти; жалобы на медленность.

1. **Базовая линия** — записать текущие метрики (p50/p95/p99); найти медленный путь профилированием/трейсингом; поставить чёткую цель («p95 800ms → 200ms») → `docs/perf-baseline.md`. Гейт: без измеренной базовой линии не оптимизировать. Оптимизация «по наитию» запрещена.
   Инструменты: `EXPLAIN ANALYZE` (Postgres), `redis-cli --latency`, `py-spy` / `cProfile` (Python), трейс Langfuse (M9).
2. **Корневая причина** (`debugger`) — БД (N+1, нет индексов, seq scan, блокировки); кеш (высокий miss, нет кеша горячего, cache stampede); API (последовательные await вместо параллельных, нет пагинации, лишние LLM-вызовы); ранжированный список узких мест с оценкой эффекта → `docs/perf-analysis.md`.
3. **Оптимизировать** (`implementer`) — по одной, сначала с наибольшим эффектом; измерять после каждой; нет улучшения → откат и переанализ. Частое: индекс Postgres/pgvector; слой кеша (TTL + инвалидация); `asyncio.gather` вместо последовательных await; пул соединений; пагинация; выбор дешёвой модели (M2.9), prompt caching (M2.10), семантический кеш (M8.6).
4. **Верифицировать** — перемерить всё; подтвердить цель; `docs/perf-results.md` (до/после); добавить регресс-тест производительности (assert число запросов < N).

## DB Migration — безопасная миграция (M1.6 и любой ALTER растущей `requests`)

Только миграции, `create_all` в проде запрещён. У каждой миграции план отката до продакшена.

1. **Валидация файла миграции** (`designer`) — аддитивная? если деструктивная (DROP, смена типа) — есть ли бэкап-шаг? в транзакции? идемпотентна? `down()` полностью реверсит `up()`? полная блокировка таблицы (ALTER на большой таблице блокирует чтение/запись)? оценка времени на проде.
   🔴 ГЕЙТ: тип / оценка блокировки / обратимость / рекомендация → Approve / изменить / блок.
2. **Dry run на staging** (`implementer`) — `BEGIN; <SQL миграции>; EXPLAIN ANALYZE <главный запрос>; ROLLBACK;` (никогда не commit). Проверить: нет неожиданных ошибок, план как ожидается (нет Seq Scan на большой), время приемлемо, нет нарушений FK.
3. **Скрипт отката** — до продакшена готов `migrations/rollback/YYYY-MM-DD-name.sql`. 🟡 ГЕЙТ: путь / протестирован на staging? / оценка времени отката.
4. **Применить на прод** — staging-прогон успешен; откат протестирован; окно низкого трафика; дашборд открыт; второй инженер на подхвате (для P1). Прогнать, сразу проверить `alembic_version` / список миграций.
5. **Проверка целостности данных** (`tester`) — счётчики строк как ожидается; нет NULL где не должно; FK-целостность (LEFT JOIN на orphan). 🔴 ГЕЙТ: все проверки прошли — готово / нашли проблемы — выполнить откат.

**Zero-downtime паттерны:**
- *Добавить NOT NULL колонку*: (1) добавить nullable → (2) backfill дефолта батчами → (3) добавить NOT NULL → (4) деплой кода, использующего колонку.
- *Переименовать колонку*: (1) добавить новую, старую оставить → (2) писать в обе (dual-write) → (3) backfill новой из старой → (4) деплой кода, читающего новую → (5) удалить старую (отдельная миграция, отдельный деплой).
- *Удалить колонку*: (1) деплой кода, который её больше не читает → (2) затем DROP (отдельная миграция). Никогда не дропать до деплоя — ORM всё ещё будет её SELECT-ить.

## Full Verify — полная верификация перед релизом модуля

Оркестратор (главная сессия) читает полный дифф + `requirements.md` + `tech-design.md`, разветвляет трёх воркеров-сабагентов параллельно с Worker Brief каждому (см. `../4-process/17-orchestrator-workers.md`):
- **A. Code review** (`reviewer`) → `docs/code-review.md` — только дифф, `file:line`, severity.
- **B. Функциональная проверка** (`tester`) → `docs/test-report.md` — критерии COVERED/MISSING, не писать новые тесты, только отчёт.
- **C. Security** (`/security-review`) → `docs/security-review.md`.
Оркестратор агрегирует: конфликты LOW-MEDIUM решает сам (лог в `decisions.md`), HIGH/CRITICAL и все security-находки → человеческий гейт 🔴. Фиксы → `implementer` с точным скоупом → перезапустить только затронутого воркера. Все три PASSED → роль `formatter` (инлайн) генерирует описание PR.
