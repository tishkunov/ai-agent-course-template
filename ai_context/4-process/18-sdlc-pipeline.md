# SDLC-пайплайн: 7 фаз с гейтами

| Фаза | Вход | Скилл / агент | Выход | Гейт после |
|---|---|---|---|---|
| 1. Требования | запрос/ТЗ модуля | `analyst` (кастомный: встроенный `researcher` анализирует код, не бизнес) | `docs/requirements.md` | 🔴 требования одобрены |
| 2. Тех-дизайн | `requirements.md` | `design` → `designer` (+ подать `requirements.md` как доп. вход) | `docs/tech-design.md` | 🟡 ключевые решения показаны |
| 3. Ревью дизайна | `tech-design.md` + `requirements.md` | `design-review` → `design-reviewer` (свежие глаза, другой инстанс) | `docs/design-review.md` | 🔴 вердикт READY FOR PLANNING |
| 4. Планирование | одобренный `tech-design.md` | `plan` → `planner` | `docs/implementation-plan.md` | — |
| 5. Ревью плана | план + дизайн + требования | `plan-reviewer` (кастомный: встроенного шага ревью плана нет) | `docs/plan-review.md` | 🔴 план одобрен |
| 6. Реализация | одобренный план | `implement` → `implementer`, по одной итерации | код + тесты + отметки в плане | 🟡 scope creep |
| 7. Финальное ревью | все доки + запущенное приложение | параллельно: `reviewer` + `tester` + `/security-review` | `code-review.md`, `test-report.md`, `security-review.md` | 🔴 HIGH/CRITICAL |

## Фаза 1 — Требования (`analyst`)

Прояснить: кто пользователи; какую проблему решаем, которую нельзя решить сейчас; ограничения (срок, стек, бюджет).
Гейт-чек `docs/requirements.md`: постановка проблемы (1 абзац); ≥1 user story с критериями приёмки (Given/When/Then, одно утверждение на критерий, у каждой MUST-истории ≥1 error-path); раздел NFR с числовыми целями; раздел «вне скоупа» (≥3 пункта); нет нерешённых вопросов, блокирующих дизайн.

## Фаза 2 — Тех-дизайн (`designer`)

Дизайн покрывает каждую user story и критерий. Разрешить: какие таблицы создаём/меняем; эндпоинты (метод, путь, auth, запрос/ответ); что в кеш и зачем; sequence-потоки основных сценариев; краевые случаи.
Гейт-чек `docs/tech-design.md`: диаграмма архитектуры; модель данных со схемой; API-контракт всех эндпоинтов; ≥1 sequence-диаграмма; стратегия кеша (если применимо); ≥5 краевых случаев; все требования покрыты.

## Фаза 3 — Ревью дизайна (`design-reviewer`)

Другой агент, не тот, что писал дизайн. Фокус: полнота (каждый критерий покрыт, связи сущностей определены, error-состояния у каждого эндпоинта); техническая прочность (нормализация, индексы под запросы, безопасный кеш, корректный async); безопасность (auth на каждом непубличном эндпоинте, авторизация ≠ аутентификация, валидация входа до БД); масштабируемость (держит 10× без переписывания, нет очевидных узких мест).
Вердикт: **READY FOR PLANNING** (нет CRITICAL/HIGH) либо **BLOCKED** (список). BLOCKED → назад в фазу 2.

## Фаза 4 — Планирование (`planner`)

Итерации размера S/M/L, никогда XL. Порядок: (1) миграции БД → (2) типы/DTO → (3) слой доступа → (4) сервис + юнит-тесты → (5) API-слой + интеграционные → (6) фронт-компоненты → (7) фронт-интеграция → (8) E2E. ≤5 файлов на итерацию (лучше 3), один новый концепт на итерацию. Тесты вплетены в каждую итерацию, не отложены на конец.

## Фаза 5 — Ревью плана (`plan-reviewer`)

Категории: полнота (каждый эндпоинт → итерация; каждая таблица → миграция; интеграционный тест на каждый MUST-критерий); порядок (миграции раньше кода; типы раньше использования; бэкенд раньше фронт-интеграции; нет циклов в «Depends on»); размер итерации (>5 файлов → split; L-описано-как-XL → переоценить); покрытие тестами (юнит в той же итерации, что и код; интеграционные на реальной БД; ≥1 негативный тест на метод; auth-тесты: валидный/без токена/чужая роль); риск и откат (у высоко-рисковых — заметка отката; ломающие API-изменения — путь миграции; большие таблицы — zero-downtime паттерн); допущения (нет итерации, опирающейся на несуществующий файл/env).
Severity: BLOCKER / MAJOR → **NEEDS_REVISION**; только MINOR → **APPROVED** с заметками. Один BLOCKER или два MAJOR → NEEDS_REVISION.
Красные флаги: «Итерация N: связываем всё вместе», «Итерация N: тесты» (отдельной последней), «фронт + бэк в одной итерации», «Effort: S» на изменении схемы, «Depends on: none» на модификации модуля, отсутствие финальной verify-итерации, маппящейся на критерии.

## Фаза 6 — Реализация (`implementer`)

Цикл на итерацию: прочитать итерацию N → прочитать все её файлы → реализовать → написать/обновить тесты → сборка проходит → тесты проходят → отметить критерии готовности → коммит `feat: iteration N — [name]` → к N+1.
Тесты упали — не идти дальше, чинить текущую. Ошибки типов — чинить, не подавлять `# type: ignore` / `Any`. Не коммитить падающие тесты и отладочный вывод.

## Фаза 7 — Финальное ревью (параллельно)

Три ревью на полном диффе фичи:
- **A. Качество кода** (`reviewer`) → `docs/code-review.md` — баги корректности, целостность типов, полнота обработки ошибок, качество тестов.
- **B. Функциональная проверка** (`tester`) → `docs/test-report.md` — каждый критерий приёмки покрыт тестом, happy-path сквозняком, краевые из дизайна протестированы, интеграционные на реальной БД.
- **C. Безопасность** (`/security-review`) → `docs/security-review.md` — OWASP, auth/authz на всех эндпоинтах, нет векторов инъекций, нет чувствительного в логах.

Агрегированный гейт — блок merge, если: CRITICAL/HIGH в code-review; пропущено покрытие критериев в test-report; CRITICAL/HIGH в security-review.
Фикс-цикл: для каждой блокирующей находки — кто чинит (implementer для кода, tester для тестов) → фикс → перезапустить только затронутое ревью → обновить док. Все три PASSED → сгенерировать описание PR (роль `formatter`, инлайн).
