# Паттерн «Оркестратор + воркеры»

Один умный оркестратор планирует и маршрутизирует; специализированные воркеры исполняют; оркестратор агрегирует.

```
              ОРКЕСТРАТОР — планирует + маршрутизирует
                     │ декомпозиция
             ┌───────┼───────┐
         Воркер A  Воркер B  Воркер C   (backend / frontend / тесты)
             │ reflect │ reflect │ reflect
             └───────┬─┴─────────┘
              ОРКЕСТРАТОР — агрегирует, разрешает конфликты
                     │
              Человеческий гейт 🔴 (если нужно решение)
```

## Обязанности оркестратора

1. **Декомпозировать** — разбить входную задачу на независимые подзадачи.
2. **Маршрутизировать** — назначить каждую подзадачу нужному воркеру с полным контекстом.
3. **Разветвлять** — запускать воркеров параллельно там, где нет зависимостей.
4. **Мониторить** — замечать, если воркер заблокирован или уходит в сторону.
5. **Агрегировать** — слить выходы, разрешить конфликты.
6. **Гейтить** — выносить человеческие решения, не одобрять высоко-рисковое сам.

Оркестратор **не** пишет код, не пишет тесты, не принимает единолично высоко-рисковых решений.

Цикл оркестратора:
```
1. Прочитать задачу + все контекст-доки
2. Декомпозировать на подзадачи
3. Назначить каждую воркеру с Worker Brief
4. Разветвить параллельно там, где подзадачи независимы
5. Собрать выходы воркеров
6. Прогнать reflection-проверку воркеров (каждый ответил на свою задачу?)
7. Агрегировать → разрешить конфликты
8. Вынести человеческий гейт, если нужно решение
9. Продолжить или вернуться на шаг назад
```

## Обязанности воркера

1. **Принять скоуп-задачу** — одна чётко определённая подзадача со всем нужным контекстом.
2. **Исполнить** — реализовать / отревьюить / протестировать конкретную вещь.
3. **Отрефлексировать** перед возвратом (см. промпт ниже).
4. **Вернуть структурированный вывод** в формате, который ждёт оркестратор.

Промпт рефлексии воркера (прогнать до возврата):
```
Перед возвратом вывода я проверяю:
- Мой вывод прямо отвечает на поставленную задачу?
- Есть ли допущения, о которых оркестратор должен знать?
- Я остался в рамках своего скоупа? (если нет — flag, не расширять самому)
- Формат вывода — тот, что ждёт оркестратор?
```

## Передача контекста: Worker Brief

Воркер получает не всю историю, а только нужное:

```markdown
## Worker Brief

**Твоя задача**: [конкретное описание подзадачи]
**Релевантные файлы**: [список файлов для чтения]
**Ограничения**: [конкретные правила для этой задачи]
**Формат вывода**: [что именно вернуть]
**НЕ делать**: [явные границы скоупа]
```

Так контекст воркера остаётся маленьким и сфокусированным. Полный контекст держит оркестратор.

## Стратегия разветвления

| Ситуация | Как запускать |
|---|---|
| Воркеры независимы | **параллельно** |
| Воркер B нужен выход воркера A | **последовательно** |
| Воркеры трогают один файл | **последовательно** |

Пример (полная верификация перед релизом): оркестратор одновременно запускает code-reviewer + security-reviewer + tester на одном диффе → агрегирует 3 отчёта.

## Разрешение конфликтов

Когда два воркера дают противоречивые находки (code-reviewer: «добавь кеш здесь»; security-reviewer: «этот ключ кеша инъектируемый»):
1. Оркестратор явно называет конфликт.
2. Предлагает решение, удовлетворяющее обоим.
3. Если решение требует trade-off → **человеческий гейт** 🔴 (см. `../4-process/15-human-gates.md`).

| Задача | Оркестратор | Воркеры |
|---|---|---|
| Пройти модуль M{n} по SDLC (`../4-process/18-sdlc-pipeline.md`) | держит состояние фаз | analyst, architect, design-reviewer, planner, implementer, reviewers |
| Полная верификация модуля | запускает параллельные ревью, агрегирует | code-reviewer, tester, security-reviewer |
| Bug hunt (`../4-process/20-pleybuki.md`) | ведёт цикл гипотез | debugger, implementer |
